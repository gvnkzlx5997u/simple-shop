# simple-shop 自动化验收测试说明

> 用 Playwright 驱动系统已装的 Edge 浏览器，自动把网站"点一遍"，逐条核对需求规格说明书第 13 章的验收标准。

## 〇、这份脚本对应的要求（组长下达）

> **原话**：「**配好两个地址，启动浏览器自动点一遍**」。

| 要求 | 落实在哪 |
| --- | --- |
| 「配好**两个地址**」 | `helpers/config.ts`：买家端 `http://localhost:8080` + 卖家端 `http://localhost:5173`（改地址只改这一个文件）；双击 `1-启动测试环境.bat` 会**同时**把这两个服务开起来 |
| 「**启动浏览器**自动点一遍」 | `playwright.config.ts`：驱动系统已装的 **Edge**，默认**有头模式**（能看见浏览器自己点击），不是无头 |
| 「自动**点一遍**」的**范围** | ⚠️ **这句话没限定范围**。下面第一节起是按规格书第 13 章 `V-04`（端到端流程演练）与 `AC-25`/`AC-26`（每条状态迁移至少 1 个端到端用例）展开的 **36 条**用例 |

> ⚠️ **第三行（范围）是补充的，不在那两句原话里。** 原话推不出"点哪些、点到什么程度"。
> 若本意只是"跑起来演示一下"，本脚本属超出；若希望它承担端到端验收，则正好对应。

## 一、三步使用（都是双击）

> 注意：跑这个测试有前置条件，你需要先保证后端已构建过`simple-shop.war`，且前端工程、验收测试工程依赖已通过`npm install`安装完毕。

| 顺序 | 双击这个 | 作用 | 大概等多久 |
| --- | --- | --- | --- |
| 1 | `1-启动测试环境.bat` | 起"测试后端"和"卖家端前端"两个黑窗口 | 后端约 10 秒、前端约 5 秒 |
| 2 | `2-跑验收测试.bat` | 复位测试数据 → 弹出浏览器自动点一遍 → 输出结果 | 约 20 秒 |
| 3 | `3-查看测试报告.bat` | 在浏览器里打开中文 HTML 报告（每条用例通过/失败） | 立刻 |

**结果在哪看？** 第 2 步那个窗口里会一行行打印（`ok 1 …`、`ok 2 …`），
**最后一行是总结**：全过会打印 **`ALL TESTS PASSED`**，并显示 `36 passed`。
第 3 步只是把这些结果用**网页形式**再看一遍（**可选**，给老师投屏用更直观）。

**只想赶紧看结果、不想等启动？** 如果 8080 / 5173 已经在跑（比如刚开始调试过），
可以**直接双击第 2 步**，跳过第 1 步。

**跑完别急着关那两个黑窗口** —— 关了服务就停了，第 3 步的报告和以后再跑都要重新启动。

> 📌 **第一次换到别的电脑上跑？** 先看第六节「口令放在哪里」：要先把
> `local-config.example.bat` 复制成 `local-config.bat` 并填好口令，否则第 1、2 步会提示
> `local-config.bat is missing or empty`。**你这台机器已经配好了，直接双击就行。**

## 二、最重要的一件事：**测试用的是"测试库"，不是你的正式库**

| | 你的正式库 | 测试库 |
| --- | --- | --- |
| 库名 | `simple_shop` | **`simple_shop_test`** |
| 谁在用 | 你平时演示/开发 | **只有这套自动化测试用** |
| 会被测试改掉吗 | ❌ **完全不会被碰** | ✅ 随便改，跑之前自动清空重来 |

之所以能这样，是因为后端的数据库地址是通过环境变量 `DB_URL` 读的（`application.yml` 里本来就写成 `${DB_URL:...}`），
启动脚本把它指到 `simple_shop_test` 即可 —— **不需要改项目的任何文件**。

**"复位"** 就是把这个测试库清空（`reset-test-db.sql`），`2-跑验收测试.bat` 会自动做，
所以**这套测试可以无限次重复跑**。

> ⚠️ 复位脚本里有一处不能动：`simpleshop_queue_sequence` 表**不能 TRUNCATE**，
> 它是 Flyway 的种子数据，缺了 `id=1` 那一行提交意向会直接 HTTP 500
> （实测踩到过：`queue sequence row (id=1) is missing`）。脚本里已改成重置计数为 0。

| 角色 | 地址 | 说明 |
| --- | --- | --- |
| 买家端 | `http://localhost:8080/` | 后端直接渲染 JSP |

## 五、**没有**覆盖的 / **只覆盖一部分**的（如实列出）

> **怎么读这张表**（老师若追问"还有没有没测的"）：
> 1. 规格书 §13.2.2 列出 **5 种验收方式**（`V-01` 数据库断言｜`V-02` 接口调用｜`V-03` 页面走查｜
>    `V-04` 端到端演练｜`V-05` 交付文档检查），**各自分派了适用对象**；§13.2.4 的通过判定要求
>    **全部 `P0`／`P1` 条目通过**。§13.2.2 里**没有任何一种方式被标为"可不做"**。
> 2. 本脚本天然覆盖 `V-02`/`V-03`/`V-04`。**`V-01` 查库断言不是"不好测"**——写个连库脚本即可，
>    只是不该塞进"浏览器点击"脚本里（它验的是数据一致性，不是用户可用性）。
> 3. 真正"**规格书明确不要求**"的只有两类：`AC-29`（`V-05` 人工看文档）与 §13.2.3 明确不纳入验收的
>    视觉设计／`【建议】`项／`OPEN-01~03`。

| 未覆盖 / 只覆盖一部分 | 为什么 |
| --- | --- |
| `AC-01` ~ `AC-06`（6 条不变量的**查库断言**） | 规格书规定的验收方式 `V-01` 是**直接查库比对**，本脚本不做数据库断言。其中 `AC-03` 已由 `D1` 用接口口径验证"提交被拒且**不新增记录**" |
| `AC-01`/`AC-02` 的"行数／条数 ≤ 1"统计 | 拒绝行为已由 `D4`/`D7` 实测，但最后那一步"查库数行数"没做 |
| `AC-05`/`AC-06`（下架时意向全终态、成功意向 0 或 1 条） | `S11` 走完了归档全流程，但没断言历史表里"无排队中／交易中"、也没统计"成功恰 1 条" |
| `AC-16` 的 ①／②／④（记录唯一、原始提交时间不变、其余买家位次前移 1） | `S10` 只验证了"口令码仍有效 + 位次仍显示"（③） |
| `AC-09` 的 ③（离开后刷新不再展示、买家侧无"查看口令码"入口） | 未建断言 |
| `AC-03`/`AC-17` 的"**交易冻结**来源" | `D1` 实测的是**手动冻结**来源；交易冻结来源的绕过提交未测 |
| `AC-18` 队列 1000 上限 | 需要 SQL 造 1000 条数据，属数据准备而非点击 |
| `AC-24` 已发布四字段不可修改 | `S14` 已覆盖判据③（页面无编辑入口）+ 确认弹窗声明四字段发布后不可修改；判据①「**接口清单中不存在**修改接口」属人工核对接口文档；**判据②「直接以任意参数调用均不改变已发布字段（数据库值不变）」属查库断言，未做** |
| `AC-25` 的 `PS-07`、`AC-26` 的 `IS-08`~`IS-10` 负向 | 未单独建用例（`S15` 归档后「当前商品」为空态、`A7` 中终态口令码连同改信息／撤销入口一并收起，已**间接**证明"无出边"） |
| `AC-26` 的 `IS-07`「**不经过任何终态**」（P0） | `S10` 断言了「重排后口令码仍有效 + 位次仍显示」——这是**间接**证明（若经过终态，口令码必然失效），但**没有直接断言**"路径中未出现终态" |
| `FR-24` 卖家端查看口令码 | **不算缺口，也不是缺陷**：卖家端负责人已在 `simple-shop-frontend/src/api/intention.ts:9` 注明「查看口令码原文。**本期（最小可行性产品）不做**，后端有预留接口」⇒ 属**已声明的范围裁剪**，故不建用例 |
| `AC-27` 非功能（性能/并发/兼容性/可用性） | 属压测与兼容性矩阵（另有 JMeter 实验） |
| `AC-29` 交付文档检查 | 验收方式 `V-05`，人工检查文档 |
| 视觉设计、全部 `【建议】` 项（二次确认等） | 规格书 §13.2.3 明确**不纳入验收** |

## 六、技术说明（换电脑 / 出问题时看）

| 项 | 说明 |
| --- | --- |
| 浏览器 | 驱动系统已装的 **Edge**（`channel:'msedge'`），**不下载 chromium**（省约 130MB，也避开网络问题） |
| 卖家端登录账号 | 账号名写在 `helpers/config.ts`（`seller`）；**口令不写在任何被提交的文件里**，见下面「口令放在哪里」 |
| 为什么串行跑 | 系统只有 1 个商品槽位（`INV-01`），用例之间有顺序依赖，`workers:1` 必须串行 |
| 报告与证据 | `report/`（HTML 报告 + JSON 结果）、`evidence/`（失败截图与 trace） |
| 只想看浏览器点、不弹窗 | 命令加 `--headless`，或设环境变量 `HEADLESS=1` |
| 环境要求 | `DB_URL` 里的 MySQL 能连上即可；8080 与 5173 没被别的程序占用 |
| **可以连续跑几次吗** | ✅ **可以无限次连续跑**（`2-跑验收测试.bat` 每次都会先复位测试库）。见下面「关于提交限流」 |

### 口令放在哪里（首次使用 / 换电脑必看）

**两条口令**（MySQL 的、卖家测试账号的）**都不写在会被提交的文件里**。
它们统一放在一个本地文件 `local-config.bat`，而它**已被 `.gitignore` 排除**。

| 文件 | 在不在版本库 | 内容 |
| --- | --- | --- |
| `local-config.bat` | ❌ **不入库**（已 git-ignore） | 两条真口令 |
| `local-config.example.bat` | ✅ 入库 | 同一套变量名，值是 `CHANGE_ME` |

**换电脑、或别人拿到这份代码，只多做一步**：

1. 把 `local-config.example.bat` 复制一份，改名成 `local-config.bat`（放同一层）
2. 打开它，把两个 `CHANGE_ME` 换成真口令，保存
3. 然后照常双击第 1、2、3 个文件

**忘了做会怎样**：双击第 1 或第 2 个文件时，窗口会**停在原地**并提示
`[ERROR] local-config.bat is missing or empty`，**不会一闪而过**。

> **为什么这样设计**：项目自己定的规矩是「真实口令不得进版本库、一律走环境变量」
> （《开发方决策记录》`DEC-DB-12` 第 3 条）。现在后端启动脚本与 `helpers/config.ts`
> 都只读环境变量，**文件里一个真口令都没有** —— 可用 `git grep -i password` 自查，只会看到变量名。

### ⚠️ 关于「提交限流」——这一点一定要知道

**产品本身有一条限流**（需求 `NFR-17`）：**同一个 IP 每分钟最多提交 10 次购买意向**，超出就提示"请稍后重试"。这是**产品的正确行为，不是 bug**。

**但它和自动化测试有冲突**：一套验收测试要在**十几秒内提交 6 次**意向（实测整套约 17 秒）。如果**连着跑两次**（半分钟内共 12 次），第二次就会撞上限流 → 用例 `D0` 会失败、并连带 4 条跳过。

**所以本脚本的做法**（只影响测试，不影响产品）：

| 项 | 值 | 说明 |
| --- | --- | --- |
| 产品默认（`application.yml`） | **10 次 / 分钟** | **一字未改**，正式部署、正式库照旧 |
| 本测试后端（`run-backend.bat`） | **1000 次 / 分钟** | 只在启动测试后端时用命令行参数覆盖 |

**为什么这样做是合理的**：

1. 限流**不是**验收标准（`AC-01`~`AC-29` 里没有它），属于 `AC-27` 非功能项，规格书已明确不纳入本脚本；
2. 限流本身**有专门的单元测试**（后端测试 `SubmitRateLimiterTest`）覆盖，不靠本脚本验证；
3. 自动化测试是"高频机器人"，天然会触发为**人类用户**设计的限流。若不放宽，测的就不是功能对不对，而是"机器人手速快不快"。

> 如果老师问起限流，可以这样答：
> "系统对提交意向做了同 IP 每分钟 10 次的限流（NFR-17），这是产品行为、有单元测试覆盖。
> 自动化测试为了能连续演示，只在**测试后端**把阈值临时调高，产品配置没有改。"

| 现象 | 原因 / 办法 |
| --- | --- |
| 用例报"前置失败：测试库无法准备在售商品" | 服务没起，或商品处于冻结态 → 双击 `1-启动测试环境.bat` 后重跑 |
| 提交意向返回 HTTP 500 | 测试库的序号表被清空了 → 重新跑 `2-跑验收测试.bat`（它会正确复位） |
| 卖家端页面打不开 | 确认用的是 `localhost:5173`，不是 `127.0.0.1:5173` |
| 双击 `3-查看测试报告.bat` 后**窗口一闪而过**、浏览器没打开 | 已修正（原命令没告诉它报告目录叫 `report`，它按默认去找 `playwright-report`，找不到就立刻退出）。若仍打不开：① 确认 `report\index.html` 存在——没有就先跑第 2 步；② 报告服务固定用 **9323** 端口，被占用时会报错，关掉占用它的程序再双击 |
| 想把测试数据恢复干净 | 双击 `2-跑验收测试.bat` 前它自己会复位；也可单独执行 `reset-test-db.sql` |

## 七、目录结构

**本目录位于项目仓库根下**，与 `simple-shop-backend/`、`simple-shop-frontend/` 平级：

> ⚠️ 启动脚本是按**相对路径**去找 `..\simple-shop-backend`（后端 war 包）和
> `..\simple-shop-frontend`（卖家端）的，所以本目录必须待在仓库根下、与它们平级。
> 要搬到别处，这两项得跟着搬，或改 `run-backend.bat` / `run-frontend.bat` 里的
> `WAR=` / `FE=` 两行。

```
simple-shop-test-e2e/
├── 1-启动测试环境.bat          ← 双击①
├── 2-跑验收测试.bat            ← 双击②（自动复位 + 跑测试）
├── 3-查看测试报告.bat          ← 双击③
├── local-config.bat            （本地真口令 —— **不入库**，见第六节）
├── local-config.example.bat    （口令模板 —— 入库）
├── .gitignore                  （排除 node_modules / report / evidence / logs / data / local-config.bat）
├── run-backend.bat             （内部用：起测试后端，连 simple_shop_test）
├── run-frontend.bat            （内部用：起卖家端 dev server）
├── reset-test-db.sql           （复位测试库）
├── reset-test-db.java          （复位用的 JDBC 小工具：按 run-backend.bat 的 DB_URL 连库，不需要 MySQL 客户端）
├── playwright.config.ts        （配置：浏览器、超时、报告）
├── package.json                （Node 依赖清单，只依赖 @playwright/test）
├── package-lock.json           （依赖版本锁定）
├── 验收测试说明.md             （本文件）
├── helpers/
│   ├── config.ts               （两个地址 + 卖家账号名 ← 要改地址改这里）
│   ├── api.ts                  （接口调用辅助）
│   └── ui.ts                   （页面操作辅助）
├── tests/
│   ├── 01-buyer.spec.ts        （买家端 10 条）
│   ├── 02-seller.spec.ts       （卖家端 19 条，有序剧本）
│   └── 03-security.spec.ts     （服务端拦截 7 条，绕过前端）
├── report/                     （HTML 报告，跑完才有 —— 不入库）
├── evidence/                   （失败截图 / trace，跑完才有 —— 不入库）
├── logs/                       （启动脚本日志 —— 不入库）
└── data/                       （后端图片上传目录，跑过才有 —— 不入库）
```

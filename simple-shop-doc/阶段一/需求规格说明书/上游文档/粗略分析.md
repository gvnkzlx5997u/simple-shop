## 2. 项目概述

### 2.1 一句话定位

一个**只有一个卖家、同一时间只经营一件商品、线下当面钱货两清**的极简在线购物系统：卖家在线发布商品，买家在线留下联系方式排队，卖家在线下完成交易后回到系统登记结果。

### 2.2 设计意图

系统的核心复杂度不在交易本身，而在**「一件商品面对多个排队买家」时的队列秩序与状态一致性**。因此本系统的需求重点应放在：

1. 商品状态与意向状态的**联动规则**（冻结、恢复在售、下架）；
2. 队列的**先到先得**判定与位次维护；
3. 无账号体系下买家的**身份凭证（口令码）**及其生命周期。

### 2.3 范围边界

**范围内（本期实现）**

- 卖家登录、修改密码；
- 商品发布（名称、描述、图片、价格）；
- 商品冻结 / 解冻；
- **商品手动下架**（队列为空时，`DEC-01` 开发方新增）；
- 买家提交购买意向、获取口令码；
- 买家凭口令码查询位次与交易状态、修改姓名电话、撤销意向；
- 卖家发起与某位买家的交易（商品冻结）；
- 卖家标记交易成功 / 交易失败，及失败后对买家意向的处置（作废 / 重新排队）；
- **卖家查看非终态意向的口令码**（`DEC-03`、`DEC-05` 开发方新增）；
- 卖家查看在售与历史商品、查看意向购买人名单。

## 3. 名词与角色

| 名词 | 定义 |
| --- | --- |
| 卖家 | 系统唯一账号持有者，商品的发布者与所有状态裁决者 |
| 买家 | 无需注册的访客，提交购买意向后成为「意向购买人」 |
| 商品 | 卖家发布的一件待售物品，含名称、描述、图片、价格 |
| 购买意向 | 买家对某件商品提交的一次购买申请，是排队与交易的载体 |
| 意向队列 | 某件商品下所有处于「排队中」状态的意向，按提交时间升序排列 |
| 队首 | 意向队列中提交时间最早的那条意向 |
| 口令码 | 系统在买家提交意向成功后当场生成并展示的唯一凭证，买家凭它查询与操作自己的意向 |
| 进入交易 | 卖家选定某条意向、双方开始线下协商的动作，此动作使商品进入「已冻结」状态 |
| 冻结 | 商品的一种状态：详情仍可浏览，但不能提交新意向、不能进入交易 |
| 下架 | 商品的终态：商品被撤下并进入历史记录，永久不可再售 |

| 能力 | 卖家 | 买家 |

## 4. 业务主线

### 4.1 主流程

1. 卖家登录后台，发布商品（名称、描述、图片、价格），商品进入**在售**。
2. 买家浏览商品详情，填写**姓名、联系电话**提交购买意向，系统排队并返回**口令码**。
3. 后续买家继续提交，意向依次入队；买家可凭口令码查询位次、修改姓名电话、撤销意向。
4. 卖家查看意向购买人名单，选定**队首**买家**进入交易**，商品转为**冻结**；此后不再接受任何新意向。
5. 双方线下协商、当面交钱交货。
6. 卖家回到后台登记结果：
   - **交易成功** → 商品**下架**进入历史；本次意向记为成功；队列中其余意向全部记为失败（原因「商品已卖出」）；该商品所有口令码作废。
   - **交易失败** → 商品**恢复在售**；卖家裁决该买家意向为**作废**或**重新排队**；其余排队买家的位次依次前移；排队中的口令码继续有效。
7. 卖家可在商品**在售且自己冻结**的情形下**手动解冻**，使商品回到在售。

### 4.2 系统外业务（不在系统内实现，但影响系统状态）

- **线下协商与交割**：系统不承载议价、付款、交付过程，只记录卖家登记的最终结果。
- **卖家与买家的直接联系**：卖家可从后台取得买家姓名与电话并在系统外联系。

## 5. 状态模型

### 5.1 商品状态机

商品状态仅三种：**在售**、**已冻结**、**已下架**。冻结需额外记录**冻结来源**（交易冻结 / 手动冻结），因为它决定后续允许的解除方式。

| 编号 | 当前状态 | 触发动作 | 执行者 | 目标状态 | 关联功能 |
| --- | --- | --- | --- | --- | --- |
| PS-01 | 在售 | 卖家进入交易（选定队首买家） | 卖家 | 已冻结（来源：交易冻结） | FR-07 |
| PS-02 | 在售 | 卖家手动冻结（**在售即可，不要求队列清空**） | 卖家 | 已冻结（来源：手动冻结） | FR-05 |
| PS-03 | 已冻结 | 卖家标记交易成功 | 卖家 | 已下架（终态） | FR-09 |
| PS-04 | 已冻结 | 卖家标记交易失败 | 卖家 | 在售 | FR-10 |
| PS-05 | 已冻结（**来源：手动冻结**） | 卖家手动解冻 | 卖家 | 在售 | FR-06 |
| PS-06 | 已冻结（**来源：交易冻结**） | 卖家手动解冻 | 卖家 | **不允许**——按钮禁用，须改走 PS-04/PS-03 | FR-06 |
| PS-07 | 已下架 | —（终态，无出边） | — | — | — |
| **PS-08** | **在售** | **卖家手动下架（前置条件：队列为空）** | **卖家** | **已下架（终态）** | **FR-23** |

> **PS-08 为开发方新增**（`DEC-01`）：业务方原始需求中并无「手动下架」，Q2、Q12 列举后台功能时均无此项。新增理由是：「冻结 → 标记交易结果 → 下架」这条路径上**只有交易成功才能下架**，标记交易失败不会使商品下架，因此需要一条不依赖成交的撤下通道。
>
> **前置条件的确定性**：因 `DEC-02` 要求「商品下架前所有意向均需处于终态」，且 PS-08 要求队列为空，两条规则**互相印证**——下架动作不会产生悬空的排队意向，因此**不需要**在下架时批量处理队列（批量转失败只是防御性逻辑）。

> **已闭合的风险点**：上一版指出「交易冻结时手动解冻会产生『商品在售 + 有人交易中』的不一致状态」。澄清 Q16 确认该漏洞存在，Q17 确认修正方案：**交易中的商品禁止手动解冻，结束交易必须走「标记交易结果」**。因此 §8 的 INV-04 由「业务约定」升级为**系统强制保证**。
> 另注：Q17 确认「手动冻结 / 交易冻结共用一个『已冻结』状态，系统原有设计分不开」——本版要求**区分冻结来源**（字段级要求），否则无法实现该禁用逻辑。见 §7.1「冻结来源」。

### 5.2 购买意向状态机

| 编号 | 当前状态 | 触发动作 | 执行者 | 目标状态 | 关联功能 |
| --- | --- | --- | --- | --- | --- |
| IS-01 | — | 提交购买意向 | 买家 | 排队中 | FR-13 |
| IS-02 | 排队中 | 卖家选定其进入交易 | 卖家 | 交易中 | FR-07 |
| IS-03 | 排队中 | 买家撤销意向 | 买家 | 已撤销（终态，退出队列） | FR-16 |
| IS-04 | 排队中 | 卖家标记交易成功（他人成交） | 卖家 | 交易失败（类型：商品已售出） | FR-09 |
| IS-05 | 交易中 | 卖家标记交易成功 | 卖家 | 交易成功（终态） | FR-09 |
| IS-06 | 交易中 | 卖家标记交易失败 + **作废** | 卖家 | 交易失败（终态，类型：卖家作废） | FR-10 |
| IS-07 | 交易中 | 卖家标记交易失败 + **重新排队** | 卖家 | 排队中（**复用原意向记录**，排序序号刷新至队尾） | FR-10 |
| IS-08 | 交易成功 | —（终态，无出边） | — | — | — |
| IS-09 | 交易失败 | —（终态，无出边） | — | — | — |
| IS-10 | 已撤销 | —（终态，无出边） | — | — | — |

> **IS-07 的关键设计（`DEC-04`）**：选择「重新排队」时**不新建意向、也不产生终态**——原意向记录被复用，状态从「交易中」直接回到「排队中」，**口令码保持有效**。仅当卖家选择「作废」（IS-06）、交易成功（IS-05）、买家撤销（IS-03）时，意向才进入终态。
>
> **IS-07 的连带要求**：因复用原记录，每次失败的过程会被覆盖，**必须**另建「意向交易流水表」保留每次失败的类型与备注，否则无法满足业务方 Q15「每次失败记录都能查到」的要求。见 §7.3。

### 5.3 两状态机的联动规则（关键）

| 编号 | 规则 |
| --- | --- |
| BR-01 | 商品进入交易冻结时，仅**该条**意向变为「交易中」，队列中其余意向保持「排队中」。 |
| BR-02 | 商品被交易冻结期间，**任何**新意向都不允许提交，页面提示「商品交易中」。 |
| BR-03 | 交易成功时，先将其余排队意向置为「交易失败（类型：商品已售出）」，再把本次意向置为「交易成功」，最后商品下架。（顺序保证结果一致） |
| BR-04 | 交易失败时，商品恢复在售；该买家意向按卖家裁决变为「作废」或「重新排队」；其余排队意向状态不变、位次前移。 |
| BR-05 | 「重新排队」= 复用原意向记录，状态回到「排队中」，**排序序号刷新**至队尾（`DEC-04`、`DEC-15`）。 |
| BR-06 | 买家的「撤销意向」与卖家的「作废 / 重新排队」是两回事，不可互相触发。 |
| BR-07 | 手动解冻**仅对来源为「手动冻结」的商品开放**；来源为「交易冻结」的商品，解冻入口禁用。 |
| BR-08 | 处于「交易冻结」的商品，结束与买家交易的**唯一路径是「标记交易结果」**（成功或失败）。 |
| BR-09 | 手动下架**仅对「在售」且队列为空**的商品开放（`DEC-01`）。 |
| BR-10 | 商品下架前，其名下所有意向**必须已处于终态**；交易成功时由系统自动将其余排队意向转为「交易失败（商品已售出）」（`DEC-02`）。 |

> **编号说明**：§5.3、§6.4、§8 三处的 `BR` 编号为**全局连续编号**，不重复。

### 7.1 商品

| 字段 | 必填 | 说明 | 依据 |
| --- | --- | --- | --- |

| 图片 | 否 | **选填**，不传则显示占位图；最多 1 张主图，JPG 或 PNG，单张 ≤5MB（超出给提示）；**存服务器文件系统，数据库存路径**（`DEC-09`）；**不生成缩略图**（`DEC-34`） | 澄清 Q13、Q21、`DEC-09`、`DEC-34` |
| 价格 | 是 | 人民币（元），保留两位小数，**>0 且 ≤999,999.99** | 基线需求 7、澄清 Q21、`DEC-21` |
| 状态 | 是 | 在售 / 已冻结 / 已下架 | 澄清 Q4 |
| 冻结来源 | 条件必填 | 交易冻结 / 手动冻结（仅「已冻结」时有值） | 澄清 Q14、Q17 `【推断】` |
| 发布时间 | 是 | 用于历史列表排序与列表展示 | 澄清 Q12、**Q22** |
| 更新时间 | 是 | 状态变更时间；**卖家点「进入交易」时也写入（即交易开始时间）** | `【推断】`、**Q22** |
| **交易开始时间** | 条件必填 | **系统记录**（卖家点击「进入交易」时的时间戳）。**但不作为历史商品的展示字段** | 澄清 Q12、**Q22** |
| **交易结束时间** | 条件必填 | **交易出结果的时间点**；历史商品列表与详情中展示的就是这个（**「交易时间」= 结束时间**） | 澄清 Q12、**Q22** |
| 交易结果 | 条件必填 | 商品最终结果：成功卖出 / 手动下架 / 交易失败收场（进入历史后展示） | 澄清 Q12、Q15、`DEC-01` |

> **时间字段的展示口径（澄清 Q22）**：① **记录**：交易开始（= 冻结）与结束**两个时间都记**；② **展示**：历史商品列表展示「发布时间」+「**交易结束时间**」，**不展示开始时间**；③ 意向购买人列表只展示「**意向提交时间**」+ 对应交易结果，**不单独展示交易开始/结束时间**。

### 7.2 购买意向

| 字段 | 必填 | 说明 | 依据 |
| --- | --- | --- | --- |
| 意向编号 | 是 | 系统内部唯一标识 | 【推断】 |
| 所属商品 | 是 | 关联商品 | 澄清 Q12 |
| **排序序号** | 是 | **独立自增编号**，决定队列位次；**「重新排队」时刷新为新的序号**（排至队尾） | 澄清 Q3、Q11、`DEC-15` |
| **原始提交时间** | 是 | **保留不变**，供买家侧展示（与排序序号分离）；也是历史意向名单中展示的「意向提交时间」 | 澄清 Q3、**Q22**、`DEC-15` |
| 姓名 | 是 | 买家填写；可凭口令码修改 | 澄清 Q5 |
| 联系电话 | 是 | 买家填写；可凭口令码修改 | 澄清 Q5 |
| 状态 | 是 | 排队中 / 交易中 / 交易成功 / 交易失败 / 已撤销 | 澄清 Q4、Q9、Q10 |
| **失败类型** | 条件必填 | **枚举**（系统自动产生）：商品已售出 / 买家撤销 / 卖家作废 / 重新排队。**买家不可见** | 澄清 Q6、Q11、`DEC-24`（已裁定） |
| **失败备注** | 否 | **纯自由文本、可空**，由卖家填写。**买家不可见** | `DEC-24`（已裁定） |
| 口令码 | 是 | **12 位大写字母+数字**，全局唯一；须**可反查原文**（明文或可逆存储） | 澄清 Q1、`DEC-07`、`DEC-05` |

> **「重新排队」不新建意向记录（澄清 Q22）**：业务方明确「重新排队是同一条意向回到队列继续等，**不会新生成一条记录**，历史意向里显示**一条**」。这与 `DEC-04`（复用原意向）**完全一致**，互为印证。
>
> ⚠️ **但由此产生一处需注意的表述张力**：业务方在 Q22 说「历史意向里显示一条，**对应的是它最终的交易结果**」，而 Q15 要求「前两次交易失败、第三次才卖掉，这一路的过程在历史里都查得到」。若「一条记录只存最终结果」，则中间两次失败的过程会丢失。
>
> **分析方建议口径（待确认）**：**显示一条意向记录 + 一条完整交易流水**——即意向记录唯一（符合 Q22），但该记录关联的**流水表保留每一次交易结果**（满足 Q15）。历史意向列表中该意向可显示「交易次数：3」并展开查看每次结果。见 §7.3 流水表。

### 7.3 新增数据表（`DEC-04` 的连带要求）

> 开发方在 `DEC-04` 中决定「复用原意向，历史表是要建的，把原意向存进去，意向表就只保存当前商品的意向」。由此产生两张新表：

| 表名 | 用途 | 关键说明 |
| --- | --- | --- |
| **历史商品表 / 历史意向表** | 商品下架时，把商品与其名下全部意向**整体归档** | 意向表只保留「当前商品」的意向，下架即迁出。满足业务方 Q15「历史里能查到每次失败过程」 |
| **意向交易流水表** | 记录每条意向的**每一次交易结果** | **必需**：因「重新排队」复用原意向记录（`DEC-04` 与澄清 Q22 一致），若只有一张意向表，则每次失败的过程会被覆盖，无法满足 Q15。每次「标记交易结果」时追加一条流水（含**开始时间、结束时间、结果、失败类型、失败备注**） |

> **设计要点（与 §7.2 呼应）**：队列次序若按「提交时间排序」则「重新排队后排至队尾」无法实现，因此须用**独立自增的排序序号**（`DEC-15`），并把「原始提交时间」另存一列供买家侧展示。澄清 **Q22** 已明确买家侧显示**最初**提交时间。

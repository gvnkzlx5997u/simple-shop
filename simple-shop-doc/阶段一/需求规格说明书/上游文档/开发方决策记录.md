## A. 需求范围决策

### DEC-01　本期是否实现「卖家手动下架商品」　✅ 已定

| 项目 | 内容 |
| --- | --- |
| **优先级** | P0（直接决定规格说明书范围） |
| **来源** | 澄清 Q18：业务方表示「这个我其实没细想…我也没有明确的想法」 |
| **选项** | A. 本期不做｜B. 做｜C. 做，但仅限队列为空时 |
| **▶ 开发方决定** | **做，但仅限队列为空时。**「冻结 → 标记交易结果 → 下架」这条路走不通——这条路径上只能交易成功才能下架，标记交易失败不会使商品下架。因此要做一个手动下架入口，先由卖家自行处理完队列中的意向再下架。 |

**决策解读（分析方）**

1. 该决定是**开发方主动新增的功能**，业务方的原始需求中并无「手动下架」（Q2、Q12 列举后台功能时均无此项）。写入规格说明书时须标注来源。
2. 该决定与业务方的既有规则**无冲突**：业务方在 Q18 只说「没细想」，未否定。
3. **前端表现**：卖家后台对「在售」商品提供「手动下架」入口，**队列非空时不可用**（禁用或隐藏），并提示卖家需先处理完队列中的意向。
4. **与「先到先得」承诺的关系**：因要求队列为空，不会出现「队列中的买家被无理由作废」，该决定不破坏系统的核心承诺。
5. **新增状态迁移**：在售 →已下架（手动下架，前置条件：队列为空）。见《粗略分析》PS-08。

### DEC-02　交易失败后口令码的处置方式　⚠️ 有冲突

| 项目 | 内容 |
| --- | --- |
| **优先级** | P0（口令码生命周期的地基，其余决策都依赖它） |
| **来源** | 澄清 Q20：「原口令码：失效。口令码在『交易结束（成功或失败）』后就失效了，这条是明确的」 |
| **选项** | A. 以「单条意向」为粒度｜B. 以「商品」为粒度｜C. 混合 |
| **▶ 开发方决定** | 口令码**跟着意向走**，失效以**意向终态**作为标准，**口令码与商品状态无关**。由 DEC-01 可进一步得出：商品下架前所有意向均需处于终态——交易成功时自动将其他「排队中」意向转为「交易失败（商品已售出）」，口令跟着意向失效。 |

**决策解读（分析方）**

1. **选择了最一致的口径**：口令码校验**只看意向是否终态，不看商品是否下架**。这比"下架时批量作废"更简洁，也避免了「下架动作本身成为口令码失效条件」的耦合。
2. **与业务方答复的关系**：业务方在 Q20 的表述是「交易结束即失效」，本决定将其细化为「意向进入终态即失效」，属**细化而非推翻**，可在规格说明书中作为业务规则的实现化表述。
3. **与 DEC-01 形成的闭环**：既然下架要求队列为空（DEC-01），则任何时刻下架时，该商品下无意向处于非终态，口令码失效链条自然闭合，无需额外的批量作废动作。
4. ⚠️ **与 DEC-04 存在冲突**，见[附一 冲突 1](#冲突-1dec-02-与-dec-04-对重新排队口令码的处理矛盾p0)。

### DEC-03　重新排队后「新口令码」如何让买家获知　✅ 已定

| 项目 | 内容 |
| --- | --- |
| **优先级** | P0（业务方已确认这是漏洞，要求记录，即 GAP-01） |
| **来源** | 澄清 Q20 追问：业务方答复「你抓到点子上了，这确实是个漏洞…只能我在系统外（打电话、当面）告诉他」 |
| **选项** | A. 后台展示新码并转告｜B. 复用原码｜C. 引入通知机制｜D. 接受漏洞 |
| **▶ 开发方决定** | 让卖家在**系统外**告诉买家。**后台需要显示非终态意向的口令码**（这个需求是我们加的业务方无此需求，但如果不做，会引发交易漏洞）。 |

**决策解读（分析方）**

1. 实质选择了 **A（后台展示）+ D（不引入通知机制）** 的组合：系统提供查询手段，告知动作由卖家在线下完成。
2. **该决定倒逼两项存储要求**：① 口令码须**可反查原文**（不可只存哈希），与 DEC-05 一致；② 后台须能列出**非终态意向**（排队中/交易中）的口令码。
3. **需求性质**：此项为**开发方新增需求**，业务方在 Q18 明确「系统里没有主动通知买家这一说」。写入规格说明书时须标注来源，并说明新增理由（防交易漏洞）。
4. **注意**：该决定的必要性在 **DEC-04 采用「复用原意向」后大幅下降**——若重新排队不产生新码，则不存在「新码无法获知」的问题。请与[附一 冲突 1](#冲突-1dec-02-与-dec-04-对重新排队口令码的处理矛盾p0)一并裁定：后台展示口令码的功能**可能仅需保留为兜底能力**（买家丢码时的最后手段），而非重新排队的必需环节。

### DEC-04　「重新排队」是新建意向还是复用原意向　✅ 已定

| 项目 | 内容 |
| --- | --- |
| **优先级** | P0（决定数据模型与历史记录形态） |
| **来源** | 澄清 Q20：业务方答复「需求里没写死这个实现细节」 |
| **选项** | A. 复用原意向（并追加历史流水）｜B. 新建一条意向 |
| **▶ 开发方决定** | 这是一个困难的抉择，最终决定**复用原意向**，改变原意向的状态到「排队中」，**使得口令码仍有效**。**历史表是要建的**，把原意向存进去，意向表就只保存当前商品的意向。 |

**决策解读（分析方）**

1. **同时给出了数据模型结论**：① 复用原意向记录；② 建立**历史表**（原意向归档）；③ **意向表只保存当前商品的意向**——即意向表随商品下架而清空、归档入历史表。
2. **"使得口令码仍有效"与 DEC-02 冲突**：开发方在此处明确表达了「重新排队后口令码应继续有效」的意图，而 DEC-02 的表述是「意向进入终态即失效」，而「重新排队」按业务方 Q11 的定义会先经过「交易失败」。二者需统一，见[附一 冲突 1](#冲突-1dec-02-与-dec-04-对重新排队口令码的处理矛盾p0)。
3. **"历史表"与业务方 Q15 的要求一致**：业务方明确要求「一个商品前两次交易失败、第三次才卖掉，这一路的过程在历史里都查得到」。复用原意向会导致单条意向被多次改写，**必须**有一张流水表来保留每次失败记录，否则历史会丢失过程。

### DEC-05　口令码丢失后能否由卖家后台代查　✅ 已定

| 项目 | 内容 |
| --- | --- |
| **优先级** | P0（影响安全设计与口令码存储方案） |
| **来源** | 澄清 Q19：口令码只展示一次、无自助找回；澄清 Q18：无任何主动通知 |
| **选项** | A. 允许卖家查看并转告｜B. 不允许｜C. 折中（重置新码） |
| **▶ 开发方决定** | **DEC-03 已做决策，允许卖家查询。** 但要在需求规格中**明确指出该需求是我们加的，不是业务方的原始需求**。 |

**决策解读（分析方）**

1. 实质选择了 **A**：口令码须**明文或可逆存储**，卖家后台可查看。
2. **安全影响**：口令码明文存储意味着数据库泄露即凭证泄露。本系统为单卖家小规模场景，可接受；须在规格说明书的安全章节中登记为**已知风险与权衡**。
3. **与 DEC-03 合并理解**：二者共同定义了「后台可查看口令码」这一新增能力，可在规格说明书中合并为一条功能需求。

### DEC-07　口令码的生成格式与防穷举强度　✅ 已定

| 项目 | 内容 |
| --- | --- |
| **优先级** | P0（影响安全性与买家输入体验） |
| **来源** | 澄清 Q20：业务方明确「没有长度限制、也没有格式规定，只要求它是『唯一』的」 |
| **选项** | 长度：8 / 12（推荐）/ 16 位以上；字符集：大写字母+数字（推荐）/ 纯数字 / 全字符集 |
| **▶ 开发方决定** | **12 位大写字母 + 数字**。口令码的生命周期已在 DEC-02 明确。防误输见 DEC-11。 |

**决策解读（分析方）**

1. 长度取推荐值，安全性足够（配合 DEC-12 的「不做限流」，12 位是必要的下限保障）。
2. **未采纳「排除易混字符 0/O/1/I」**：本系统买家需**手动输入**该码，保留易混字符会抬高输错率。开发方接受该取舍，登记为**已知体验代价**，不视为缺陷。
3. **与 DEC-12 的联动风险**：DEC-12 决定「不限制错误次数」，而 DEC-07 选 12 位——组合后的抗穷举能力仍充足（组合空间约 36¹² ≈ 4.7×10¹⁸），但**若未来缩短长度，须同步启用限流**。此约束写入规格说明书。

### DEC-11　口令码校验维度　✅ 已定

| 项目 | 内容 |
| --- | --- |
| **优先级** | P1　**来源**：DEC-02 的连带项（原 DEC-16、DEC-36 已并入本项） |
| **选项** | A. 校验映射 + 意向终态 + 商品状态｜B. 仅校验映射是否存在 |
| **▶ 开发方决定** | 根据 DEC-02，口令码与意向状态绑定，**进入终态即失效**。关键在于**区分「已失效」和「错误口令」**，买家端返回**三种**状况：<br>① **错误口令**——数据库中无此口令<br>② **失效口令**——存在，但意向为终态，**不返回用户信息**<br>③ **有效口令**——返回用户信息<br>虽然这可能有安全风险，但能够做到一部分「口令码防误输」机制。 |

**决策解读（分析方）**

1. **采纳了原 DEC-16 的选项 A**（区分两种提示），并进一步细化为三类响应。
2. **技术细节明确化**：因 DEC-02 已定「口令码与商品状态无关」，校验**不再单独检查商品是否下架**，只检查意向是否终态。三态响应的判定条件为：

   | 返回 | 判定条件 | 是否返回买家信息 |
   | --- | --- | --- |
   | 错误口令 | 口令码在数据库中不存在 | 否 |
   | 失效口令 | 口令码存在，但对应意向已处于终态 | **否** |
   | 有效口令 | 口令码存在，且对应意向为「排队中」或「交易中」 | 是 |

3. **安全权衡已登记**：「错误口令」与「失效口令」的区分会让攻击者得以判断某个码是否**曾经存在**，构成轻量枚举探测面。因 12 位码（DEC-07）空间足够大，风险可接受。
4. **与业务方 Q19 的关系**：业务方只要求「提示已失效」，未要求区分。本决定是**在不透露交易结果的前提下**改善提示体验——注意「失效口令」的文案**不得说明失效原因**（如「商品已售出」），否则即突破 Q19「买家查不到任何结果」的边界。原 DEC-36 的裁定即为此点。

### DEC-38　买家端是否提供「商品列表」，以及空态/冻结/下架时的页面表现　✅ 已定

| 项目 | 内容 |
| --- | --- |
| **优先级** | P0（决定买家端页面结构与 URL 设计） |
| **状态** | 已定（本决策替代原业务侧 `Q-01`） |
| **来源** | 开发方判断：「一次只卖一个商品，买家侧没有『商品列表』这一说」——该问题无需向业务方提问，属开发方页面结构设计 |
| **▶ 开发方决定** | **① 买家侧不设「商品列表」页**，页面上只显示**当前在售商品**；<br>**② 无商品时不显示**（空态）；<br>**③ 商品已冻结时显示「已冻结」**；<br>**④ 商品已下架时不显示**；<br>**⑤ 买家端为服务端渲染，不存在 REST 风格的 `:id` 路径参数，因此没有「旧链接」问题。** |

**分析方核对结论**

**✅ 采纳，与既有需求一致的部分**

| 项 | 核对结果 |
| --- | --- |
| 不设商品列表 | **与业务逻辑自洽**：`BR-11` 规定同一时间至多 1 个商品处于在售或已冻结，列表最多也只有 1 条，确实不构成「列表」 |
| 只显示当前在售商品 | 与 `FR-19` 一致（原表述为「只展示当前在售（含已冻结）的商品」） |
| 已下架不显示 | 与澄清 Q19「已售/已下架商品本来就不对买家展示」一致 |
| 无空态占位 | 属开发方页面设计，业务方未规定 |

**⚠️ 需澄清一处推理（结论正确，但理由需修正）**

开发方的理由是「服务端渲染 → 不存在 REST 的 `:id` 路径参数 → 没有旧链接」。**这个推理链条不成立**：JSP 服务端渲染同样可以有 `product.jsp?id=123` 这样的查询参数，SSR 与「有无 id 参数」无关。

**真正的原因是「单一商品槽位」**：买家端页面只需查出「当前商品」这一条记录，天然不需要在 URL 中携带商品 ID，因此也就没有可被收藏、可在下架后复访的旧链接。

> 结论不变（**确实没有旧链接问题**），但规格说明书中应表述为「因买家端采用单一商品槽位设计，不设商品 ID 路径参数」，而非「因服务端渲染」。

## 附一：决策内部矛盾登记（已闭合）

> 以下两处曾是**开发方决策之间的内部矛盾**，分析方登记而未擅自改写；现已经开发方裁定闭合，结论如下。

### 冲突 1：DEC-02 与 DEC-04 对「重新排队」口令码的处理矛盾　✅ 已闭合

**矛盾点**

| 决策 | 表述 | 推论 |
| --- | --- | --- |
| DEC-02 | 口令码「失效以**意向终态**作为标准」 | 交易失败 ⇒ 意向进入「交易失败」终态 ⇒ **口令码失效** |
| DEC-04 | 复用原意向，改变状态到「排队中」，**使得口令码仍有效** | 交易失败 + 重新排队 ⇒ **口令码仍有效** |

**为什么这是冲突**：按业务方 Q11 的定义，卖家必须先「标记交易失败」，再选择该买家的意向是「作废」还是「重新排队」。若严格按 DEC-02，意向在「标记失败」的瞬间即进入终态，口令码随之失效；DEC-04 却要求重新排队后口令码仍有效。

**影响**：这条直接决定 GAP-01（静默买家漏洞）**是否存在**——
- 若口令码仍有效（DEC-04 口径）⇒ 买家可用原码继续查询，**GAP-01 自然消解**；
- 若口令码失效（DEC-02 严格口径）⇒ GAP-01 存在，需依赖 DEC-03 的后台可见能力兜底。

**建议裁定**：以 **DEC-04 的意图为准**，将 DEC-02 的表述精确化为：

> 口令码在意向进入**终态**时失效。「重新排队」**不产生终态**——卖家选择「重新排队」时，意向直接从「交易中」回到「排队中」，口令码**保持有效**；只有卖家选择「作废」、或交易成功、或买家自行撤销时，意向才进入终态，口令码随之失效。

**若采纳该裁定**：`GAP-01` 状态由「已确认漏洞」改为「**已消解**」；DEC-03 的后台口令码展示能力**降级为兜底功能**（用于买家丢失口令码的情形），仍建议保留。

**▶ 开发方裁定**：**采纳。重新排队不产生终态。** 口令码在意向进入终态时失效；卖家选择「重新排队」时，意向直接从「交易中」回到「排队中」，口令码保持有效；只有选择「作废」、交易成功、或买家自行撤销时，意向才进入终态，口令码随之失效。

**裁定结论**：✅ **已闭合**。DEC-02 的表述以本裁定为准（DEC-02 原文中「失效以意向终态作为标准」的落点即「重新排队不产生终态」）。`GAP-01` **正式关闭**，状态为「已消解」。

---

### 冲突 2：DEC-24 未区分「系统原因」与「卖家备注」　✅ 已闭合

**矛盾点**：DEC-24 决定失败原因用**纯自由文本**，理由是「能够确定的交易失败原因只有『主动取消 / 重新排队』两种，其他均不确定」——但这两个原因恰恰**不是**卖家手填的，而是**系统自动产生**的（业务方 Q6、Q11 明确「其余意向置为失败，原因为已卖出」）。

**影响**：若只有一个自由文本字段，则系统自动写入的原因与卖家手填的备注会混在一起，导致：
- 历史名单中无法区分「系统判定失败」与「卖家判定失败」；
- 业务方 Q15 要求「每次失败记录都可查」，若原因是自由文本，无法按结果类型聚合或校验。

**建议裁定**：字段拆为两个——

| 字段 | 性质 | 取值 | 买家可见 |
| --- | --- | --- | --- |
| **失败类型** | 系统自动产生，**枚举** | 商品已售出 ｜ 买家撤销 ｜ 卖家作废 ｜ 重新排队 | 否 |
| **失败备注** | 卖家手填，**纯自由文本、可空** | 任意文本 | 否 |

这样既保留了 DEC-24「卖家备注用自由文本」的原意，又让系统自动原因保持可判定。

**▶ 开发方裁定**：**采纳。失败原因分成两个字段。** ① **失败类型**（系统自动产生，枚举：商品已售出 / 买家撤销 / 卖家作废 / 重新排队）；② **失败备注**（卖家手填，纯自由文本，可空）。两者均**买家不可见**。

**裁定结论**：✅ **已闭合**。DEC-24 的原始决定（卖家备注用自由文本）由「失败备注」字段落实；系统自动原因由「失败类型」字段承载。

## 2.1 系统定位

simple-shop 是一个**极简单商品**的在线购物系统，其形态由三条硬约束共同定义：

| 约束 | 内容 | 来源 |
| --- | --- | --- |
| 单商品 | 同一时间只经营**一件**商品；卖掉一件，再发布下一件 | 基线需求 1 |
| 单卖家 | 系统**只有一个卖家账号**，不做多账号与权限分级 | 基线需求 2 |
| 线下交易 | 线上只负责**撮合与排队**，钱货两清在线下当面完成，系统不承载支付与物流 | 基线需求 4 |

**一句话定位**：卖家在线发布商品，买家在线留下联系方式排队，卖家在线下完成交易后回到系统登记结果。

**系统解决的唯一问题**：让「一件商品被多个买家想要」这件事有**明确的先后秩序**，并让买卖双方在系统外联系时都有可靠的依据。

### 2.1.1 系统的核心复杂度

本系统的实现难度**不在交易本身**（交易在系统外发生），而在于：

1. **商品状态与意向状态的联动一致性**——冻结、恢复在售、下架三个动作必须与队列状态严格同步，否则会出现「商品在售却有人正在交易」这类不一致状态（该风险已在澄清 Q16/Q17 中被发现并修正）。
2. **队列的先到先得判定与位次维护**——「重新排队」要求把意向排至队尾，而「先到先得」要求按提交先后排序，二者存在实现张力（见 `DEC-15`：须用独立自增序号）。
3. **无账号体系下买家的凭证（口令码）及其生命周期**——买家不注册、不登录，口令码是其唯一的身份与操作凭证，其生成、展示、校验、失效四个环节都必须明确定义。

## 2.2 设计意图

| 编号 | 设计意图 | 具体体现 |
| --- | --- | --- |
| D-01 | **不让买家承担注册成本** | 买家不注册、不登录；仅在提交意向时填姓名与电话 |
| D-02 | **用一次性凭证替代账号体系** | 提交成功后系统当场发放口令码，买家凭码查询、改信息、撤销意向 |
| D-03 | **先到先得，秩序可查** | 按提交先后排队；买家可凭口令码查到自己的位次 |
| D-04 | **卖家对结果有完整裁决权** | 进入交易、标记成功/失败、作废/重新排队、冻结/解冻/下架，均由卖家在后台操作 |
| D-05 | **过程可追溯** | 历史商品保留每一次交易的结果（含多次失败），不只留最终结果 |
| D-06 | **成交即可换货** | 商品下架后即可发布下一件，支撑「卖掉一个，再做一个，再卖」的经营节奏 |
| D-07 | **不做多余的事** | 系统不涉及支付、物流、评价、通知；业务方明确「没有主动通知买家这一说」 |

> **D-07 的边界**：因系统不做通知，买家只能**主动**凭口令码查询状态。这一点已确认为**业务约束**，不作为缺陷处理。

## 2.3 用户角色

### 2.3.1 角色定义

| 角色 | 是否需要账号 | 凭证 | 说明 |
| --- | --- | --- | --- |
| **卖家** | 是（唯一账号） | 账号 + 密码 | 商品的发布者与所有状态的裁决者 |
| **买家** | 否 | 口令码 | 无需注册的访客；提交意向后成为「意向购买人」 |

### 2.3.2 角色能力对照

| 能力 | 卖家 | 买家 |
| --- | --- | --- |
| 需要登录 | 是 | 否 |
| 需要凭证 | 账号密码（密码长度 ≥8 位） | 口令码（12 位大写字母 + 数字） |
| 可发布商品 | ✅ | ❌ |
| 可修改已发布商品 | ❌（`BR-15`） | ❌ |
| 可操作商品状态（冻结/解冻/下架/进入交易） | ✅ | ❌ |
| 可查看意向购买人名单 | ✅（含在售阶段，见 `FR-08`） | ❌ |
| 可查看**他人**意向 | ✅（后台名单） | ❌ |
| 可操作**自己**的意向 | ❌（只能标记交易结果） | ✅（改姓名电话、撤销） |
| 可查看队列位次 | ✅（完整名单） | ✅（仅自己的位次） |
| 可查看历史商品 | ✅ | ❌（`FR-19`） |
| 会收到系统通知 | ❌ | ❌（`FR-21`，业务方明确不做通知） |

## 2.4 范围边界

### 2.4.1 范围内（本期实现）

**卖家侧**

- 登录、修改密码；
- 发布商品（名称、描述、图片、价格）；
- 查看当前商品；
- 冻结商品 / 解冻商品；
- **手动下架商品**【开发方新增】；
- 进入交易（选定队首买家）；
- 查看意向购买人名单（**含在售阶段**【开发方新增】，及历史商品的名单）；
- **查看非终态意向的口令码**【开发方新增】；
- 标记交易成功 / 交易失败，及失败后对买家意向的处置（作废 / 重新排队）；
- 查看历史商品列表与历史详情。

**买家侧**

- 浏览当前商品（**不设商品列表**，首页即当前商品）；
- 提交购买意向，获取口令码；
- 凭口令码查询位次与交易状态；
- 凭口令码修改姓名、电话；
- 凭口令码撤销意向；
- 在商品冻结期间看到「商品交易中」提示。

**系统侧**

- 口令码的生成、展示、校验（三态）、失效；
- 队列排序与位次维护；
- 商品与意向的状态联动；
- 关键操作日志（保留 3 个月）。

### 2.4.3 三个需要特别说明的边界

| 编号 | 边界说明 |
| --- | --- |
| B-01 | **买家端不设「商品列表」页**。因 `BR-11` 规定同一时间至多 1 个商品处于在售或已冻结，列表最多只有 1 条，不构成列表。买家端首页直接展示**当前商品**；无商品时不显示，商品冻结时显示并标注「已冻结」，商品下架时不显示。（`DEC-38`） |
| B-02 | **买家端 URL 不含商品 ID**。因买家端采用**单一商品槽位**设计，页面只需查出「当前商品」这一条记录，无需在 URL 中携带商品 ID——因此**不存在**「旧链接访问已下架商品」的问题。<br>（注意：**这与「买家端使用服务端渲染」无关**——JSP 同样可以携带查询参数。真正的原因是单一商品槽位。） |
| B-03 | **口令码失效与商品状态无关**。口令码的有效性**只取决于所属意向是否处于终态**；商品是否下架不参与判定。（`BR-26`） |

## 2.5 术语

术语与缩写见《需求规格说明书》第 1 章「术语与缩写」。本章新增以下与边界相关的表述：

| 术语 | 定义 |
| --- | --- |
| 当前商品 | 处于「在售」或「已冻结」状态的那一件商品。全局至多 1 件（`BR-11`） |
| 单一商品槽位 | 买家端的设计前提：系统任一时刻只对外呈现「当前商品」，因此买家端无需商品 ID 参数 |

## 6.1 本章说明

| 项 | 内容 |
| --- | --- |
| **目的** | 定义卖家端（**唯一账号持有者**）的全部功能需求、各操作的前置条件与结果 |
| **角色前提** | 卖家是系统**唯一**账号持有者（基线需求 2、`O-10`）；商品的发布者与**所有状态的裁决者** |
| **与其他章的关系** | ① 本章**每个操作都对应第 4 章的具体状态迁移**（`PS-xx`、`IS-xx`），映射表见 §6.4；② 口令码的查看能力（`FR-24`）在行为上属卖家端、在规则上归第 7 章；③ 卖家端为**前后端分离（Vue）**，须有完整接口契约，见第 11 章；④ 页面字段、按钮可用条件见第 10 章 |
| **服务端形态** | Vue 客户端渲染 + REST 接口（`C-06`、`A-01`）；**卖家端必须产出接口契约**（第 11 章） |
| **【开发方新增】条目** | `FR-08`（在售阶段查看名单）、`FR-23`（手动下架）、`FR-24`（查看口令码）——**共 3 条**，详见 §6.6 |
| **辅助编号** | 本章自定的辅助编号——通用要求 `G6-xx`——**以章号限定作用域**，与全局编号（`FR` / `BR` / `PS` / `IS` / `UX` / `C` / `O` / `DEC` / `Q`）互不冲突 |

## 6.3 逐条展开

### FR-01　卖家登录

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家访问后台任意页面，尚未建立有效会话 |
| **输入** | 账号、密码 |
| **前置条件** | — |
| **处理规则** | ① 账号为**单一账号**，但**必须持久化在数据库**中（不可仅放环境变量或服务器缓存）（`DEC-06`）；② 校验账号密码；③ 建立会话（**session + token**），**30 分钟**无操作自动退出（`DEC-13`、`C-07`）；④ **不做**登录失败次数限制（`DEC-25`）；⑤ **不做**图形验证码（`DEC-26`）；⑥ **不做**找回 / 重置密码（`DEC-06`、`O-12`） |
| **输出** | 进入后台首页（当前商品页） |
| **异常** | 账号或密码错误 → 提示登录失败，可无限次重试；会话超时 → 跳回登录页 |
| **关联** | `C-07`、`NFR-04`、`DEC-06`、`DEC-13`、`DEC-25`、`DEC-26`、`DEC-32` |

> **账号初始化**：由**初始化脚本**创建（`DEC-32`）；首次登录**不强制改密**，交付文档须说明交付后应修改初始密码。
> **已接受的风险**：登录接口无频率防护（`DEC-25`），登记入第 12 章已接受风险清单。

### FR-02　修改密码

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家在后台选择「修改密码」 |
| **输入** | 原密码、新密码（长度 **≥8 位**，澄清 Q20、`C-17`） |
| **前置条件** | 已登录 |
| **处理规则** | 校验原密码 → 校验新密码格式 → 更新密码 → **使全部会话立即失效** |
| **输出** | 提示修改成功，并**要求重新登录** |
| **异常** | 原密码错误 → 拒绝；新密码长度不足 → 提示 |
| **关联** | `DEC-17`、`NFR-04`、`C-17`、澄清 Q12 |

> **关键口径**：改密后**全部会话失效**（不只是当前会话）——`DEC-17`。

### FR-03　发布商品

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家在后台选择「发布商品」 |
| **输入** | **名称**（必填）、**描述**（选填）、**图片**（选填，单张）、**价格**（必填） |
| **前置条件** | **当前不存在处于「在售」或「已冻结」的商品**（`BR-11` 同一时间至多一件）。【推断】 |
| **处理规则** | 按《字段校验规则》（§6.5）校验全部字段；通过后创建商品，商品状态置「**在售**」，记录**发布时间** |
| **输出** | 提示发布成功；商品出现在「当前商品」页 |
| **异常** | ① 已存在在售 / 冻结商品 → **拒绝**创建（不可创建第二个在售商品）；② 名称超长 / 价格越界 / 图片超限 → 提示具体错误 |
| **关联** | `BR-11`、`C-12`、`C-13`、`C-14`、`C-15`、`DEC-21`、`DEC-22`、`DEC-34` |

> **发布后不可编辑**：名称、描述、图片、价格一经发布**固定不变**，后台**无编辑入口**（`BR-15`、澄清 Q2 / Q7、`O-02`）。这是买家端展示与历史记录一致性的前提。

### FR-04　查看当前商品

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家进入后台首页 |
| **输入** | 无 |
| **前置条件** | 已登录 |
| **处理规则** | 查询当前处于「在售」或「已冻结」的商品 |
| **输出** | 商品的名称、描述、图片、价格、**当前状态**、**冻结来源**（若已冻结）、发布时间 |
| **异常** | 无当前商品 → 显示空态并引导「发布商品」 |
| **关联** | `BR-11`、`FR-19`、【推断】 |

> 卖家需要看到「冻结来源」才能判断「解冻」按钮是否可用（`FR-06` 的前置条件依赖该字段，见 `PS-05` / `PS-06`）。

### FR-05　冻结商品

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家在「当前商品」页对**在售**商品点击「冻结」 |
| **输入** | 无 |
| **前置条件** | 商品处于「**在售**」。**不要求队列清空**（澄清 Q18） |
| **处理规则** | 商品状态 → 「已冻结」，**冻结来源记为「手动冻结」** |
| **输出** | 提示冻结成功；状态与来源刷新 |
| **异常** | 商品非「在售」→ 入口不可用 |
| **关联** | `PS-02`、`BR-11`、`DEC-14`（记入操作日志） |

> **易错点**：早期版本曾把「队列为空」当作手动冻结的前置条件——这是**自行添加的限制，澄清记录中无依据**，已由澄清 Q18 更正为「**在售即可冻结**」。

### FR-06　解冻商品

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家在「当前商品」页对**已冻结**商品点击「解冻」 |
| **输入** | 无 |
| **前置条件** | 商品处于「已冻结」**且冻结来源为「手动冻结」** |
| **处理规则** | 商品状态 → 「在售」，**清空冻结来源** |
| **输出** | 提示解冻成功 |
| **异常** | ① 冻结来源为「**交易冻结**」→ **解冻入口禁用**（`PS-06`）：此类商品结束与买家交易的**唯一路径是「标记交易结果」**；② 若通过接口绕过前端直接调用 → **服务端拒绝** |
| **关联** | `PS-05`、`PS-06`、`BR-07`、`BR-08`、澄清 Q17、`DEC-14` |

> **本条来自一次已修正的设计缺陷**：原设计「已冻结」不区分来源，交易中的商品可被手动解冻，产生「**商品在售 + 有人仍在交易中**」的不一致状态（`FIX-01`，澄清 Q16 确认漏洞、Q17 确认修正）。因此**冻结来源是必需字段**，而非可选信息。

### FR-07　进入交易

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家在「当前商品」页的意向名单中选定**队首**买家，点击「进入交易」 |
| **输入** | 目标意向（队首） |
| **前置条件** | ① 商品处于「**在售**」；② 队列中存在**排队中**的意向（即存在队首） |
| **处理规则** | ① 商品状态 → 「已冻结」，**冻结来源记为「交易冻结」**（`PS-01`）；② 该意向状态 → 「**交易中**」（`IS-02`）；③ 记录**交易开始时间**（= 冻结时间戳，澄清 Q22）；④ 队列中**其余意向保持「排队中」**（`BR-01`）；⑤ 此后**不接受任何新意向** |
| **输出** | 提示已进入交易；商品状态刷新为「已冻结」 |
| **异常** | ① 队列为空 → 无队首，入口不可用；② 商品非「在售」→ 入口不可用 |
| **关联** | `PS-01`、`IS-02`、`BR-01`、`BR-02`、`FR-18`、`INV-02`、`INV-04`、`DEC-14` |

> **关键口径**：卖家**只能**对**队首**发起交易（`BR-12` 先到先得）。进入交易是**唯一**使商品由「在售」变「已冻结（交易冻结）」的动作，也是买家侧 `FR-18` 提示的触发点。

### FR-08　查看意向购买人名单　【开发方新增】

> **来源标注**：本条中「**在售阶段即可查看名单**」的部分**不在业务方的原始需求与澄清答复中**，由开发方按业务合理性补充（`Q-02` 裁定）。业务方在澄清 Q12 只提到「**对交易中的商品**，能看到所有想买的人的姓名、联系电话和提交意向的时间」。
>
> **新增理由**：卖家必须**先看到队列才能选人进入交易**，否则 `FR-07` 无从操作；且名单属卖家自身的经营数据，不存在隐私越界。

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家在当前商品页 / 历史商品详情页查看意向名单 |
| **输入** | 无（按商品过滤） |
| **前置条件** | 已登录 |
| **处理规则** | 列出该商品下的意向名单，**含所有结果类型**（交易成功 / 交易失败 / 已撤销 / 商品已售出） |
| **输出** | 每行：**姓名**、**联系电话**、**意向提交时间**（= 原始提交时间，澄清 Q22）、**位次**、**对应交易结果** |
| **可见范围** | ① **在售阶段即可查看**（【开发方新增】）；② 交易冻结期间可查看；③ 历史商品可点进详情查看 |
| **异常** | 无任何意向 → 空态 |
| **关联** | 澄清 Q12、**Q22**；`Q-02` 裁定；`BR-12`、`NFR-05`、`DEC-35` |

> **隐私边界**：名单**只对已登录的卖家开放**；买家侧无任何途径获取他人信息（`NFR-05`、`FR-20`）。

### FR-09　标记交易成功

| 项 | 内容 |
| --- | --- |
| **触发条件** | 线下成交后，卖家在后台对处于「交易中」的意向标记「交易成功」 |
| **输入** | 目标意向（处于「交易中」的那一条） |
| **前置条件** | 商品处于「已冻结」（来源：交易冻结）；目标意向处于「交易中」 |
| **处理规则** | **按固定顺序执行**（`BR-03`，顺序保证结果一致）：<br>① **先**将该商品名下**其余排队意向**全部置「**交易失败**」，**失败类型 = 商品已售出**（`IS-04`）；<br>② **再**把本次意向置「**交易成功**」（终态，`IS-05`）；<br>③ **最后**商品状态 → 「**已下架**」并**归档入历史**（`PS-03`）；④ 口令码随各意向进入终态而失效 |
| **输出** | 提示标记成功；商品转入历史记录 |
| **异常** | 商品非「已冻结」或意向非「交易中」→ 入口不可用 |
| **关联** | `PS-03`、`IS-04`、`IS-05`、`BR-03`、`BR-10`、`INV-05`、`INV-06`、`FR-21`、`DEC-02`、`DEC-14` |

> **关键口径**：处理顺序**不可调换**。先处理其余意向、再置本次成功、最后下架——该顺序保证「下架时其名下所有意向均已终态」（`INV-05`）这一不变量在所有执行路径上成立。
>
> **口令码的连带效果**：所有口令码随各自意向进入终态而**失效**，买家侧**查不到任何结果**（含「未成交」），但卖家后台历史记录**完整保留**名单（`BR-21`、`BR-31`）。

### FR-10　标记交易失败

| 项 | 内容 |
| --- | --- |
| **触发条件** | 线下未成交（含买家反悔）后，卖家在后台标记「交易失败」 |
| **输入** | 目标意向；**裁决**该意向的处理方式（作废 / 重新排队）；可选的**失败备注** |
| **前置条件** | 商品处于「已冻结」；目标意向处于「交易中」 |
| **处理规则** | ① 商品状态 → 「**在售**」（`PS-04`）；<br>② 由卖家**裁决**该买家意向：<br>　· **作废** → 意向置「**交易失败**」（终态，**失败类型 = 卖家作废**）（`IS-06`）；<br>　· **重新排队** → 意向**复用原记录**从「交易中」直接回到「**排队中**」，**排序序号刷新至队尾**，**原始提交时间保留不变**，**口令码保持有效**（`IS-07`）；<br>③ 队列中**其余意向状态不变**，位次**依次前移**（`BR-04`）；<br>④ 可选填写**失败备注**（自由文本，可空，**买家不可见**） |
| **输出** | 提示标记成功；商品恢复在售、队列位次刷新 |
| **异常** | 商品非「已冻结」或意向非「交易中」→ 入口不可用 |
| **关联** | `PS-04`、`IS-06`、`IS-07`、`BR-04`、`BR-05`、`BR-17`、`BR-18`、`BR-20`、`DEC-04`、`DEC-15`、`DEC-24`（已裁定）、`DEC-14` |

> **本条是本章最需要注意的一条，三个易错点**：
> 1. **「重新排队」不产生终态**（`BR-27`）。这是 GAP-01（静默买家漏洞）得以消解的原因所在。
> 2. **排序序号必须刷新，原始提交时间必须保留**——两个字段各司其职（`DEC-15`）。若只按提交时间排序，「重新排队排到队尾」无法实现。
> 3. **作废与重新排队都是卖家的裁决权**，买家侧只有「撤销」（`BR-06`、`BR-18`、澄清 Q9）。

### FR-11　查看历史商品

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家在后台进入「历史商品」 |
| **输入** | 页码（分页）；**不做结果筛选** |
| **前置条件** | 已登录 |
| **处理规则** | **两级结构**（`DEC-35`）：① 历史商品列表；② 商品详情内的意向购买人名单 |
| **输出** | **列表**：按时间**倒序**、**每页 10 条**；每行展示**发布时间 + 交易结束时间**（**不展示交易开始时间**，澄清 Q22）、商品名称、交易结果。<br>**详情**：名称、描述、图片、价格、交易结果，以及**意向购买人列表**（姓名、电话、**意向提交时间**、对应交易结果） |
| **异常** | 无历史商品 → 空态 |
| **关联** | 澄清 Q12、**Q15**、**Q22**；`DEC-29`、`DEC-35`、`BR-21`、`BR-22`、`O-16` |

> **历史列表的范围**：**只含已下架商品**（交易成功下架 / 手动下架）。交易失败后恢复在售的商品**仍在「当前商品」**，不算历史（《粗略分析》§10.1 对 `Q-06` 的处置）。
>
> **必须能看到每一次失败**：业务方明确要求「一个商品前两次交易失败、第三次才卖掉，这一路的过程在历史里都查得到」（澄清 Q15）。因「重新排队」复用原意向记录，该要求由「**一条意向记录 + 一条完整交易流水**」的口径落实（见第 9 章）。
>
> **时间字段口径**：历史商品展示的是「**发布时间 + 交易结束时间**」；**交易开始时间只记录、不展示**（澄清 Q22）。

### FR-23　手动下架商品　【开发方新增】

> **来源标注**：本条**不在业务方的原始需求与澄清答复中**。业务方在澄清 Q18 表示「这个我其实没细想……我也没有明确的想法」，由开发方决定实现（`DEC-01`）。
>
> **新增理由**：「冻结 → 标记交易结果 → 下架」这条路径上**只有交易成功才能下架**——标记交易失败只会让商品回到在售（`PS-04`）。因此需要一条**不依赖成交**的撤下通道。

| 项 | 内容 |
| --- | --- |
| **触发条件** | 卖家在「当前商品」页对**在售**商品点击「手动下架」 |
| **输入** | 无 |
| **前置条件** | 商品处于「**在售**」，**且队列为空**（即该商品下无任何处于「排队中」的意向） |
| **处理规则** | 商品状态 → 「**已下架**」（终态）并**归档入历史** |
| **输出** | 提示下架成功；商品转入历史记录 |
| **异常** | **队列非空** → 入口**禁用**（或隐藏），并提示卖家**需先处理完队列中的意向** |
| **关联** | `PS-08`、`BR-09`、`BR-10`、`DEC-01`、`DEC-02`、`DEC-14` |

> **为什么要求队列为空**：避免「队列中的买家被无理由作废」，从而不破坏系统最核心的**先到先得**承诺。
>
> **与 `DEC-02` 的互相印证**：`DEC-02` 要求「商品下架前所有意向均须处于终态」，`PS-08` 要求队列为空——两条规则互相印证，因此**下架时不需要批量处理队列**（批量转失败只是防御性逻辑）。

### FR-24　查看意向口令码　【开发方新增】

> **来源标注**：本条**不在业务方的原始需求中**，由开发方决定实现（`DEC-03`、`DEC-05`）。
>
> **新增理由**：业务方在澄清 Q20 追问中确认这是漏洞——系统无通知机制，买家丢失口令码后**在系统内无从获知**。因此需要卖家后台可查、在线下转告。`DEC-04` 决定「复用原意向、口令码保持有效」后，**本能力的必要性大幅下降**，**降级为兜底功能**（用于买家丢失口令码的情形），**仍予保留**。

| 项 | 内容 |
| --- | --- |
| **触发条件** | 买家丢失口令码，向卖家求助；卖家在后台意向名单中查看该买家的口令码 |
| **输入** | 无（按意向行查看） |
| **前置条件** | 目标意向处于**非终态**（「排队中」或「交易中」） |
| **处理规则** | 在名单中展示该意向**当前口令码的原文**（须**可反查原文**，不可只存哈希） |
| **输出** | 口令码原文；卖家据此在**系统外**（电话 / 当面）转告买家 |
| **异常** | 意向已处于终态 → 口令码已失效，**无需展示**（展示亦无意义） |
| **关联** | `BR-30`、`NFR-16`、`DEC-03`、`DEC-05`、`X-03` |

> **安全权衡（须在安全章节登记）**：口令码可反查原文意味着**数据库泄露即凭证泄露**。本系统为单卖家小规模场景，该风险**已接受**（`DEC-05`、`NFR-16`）。详见第 7 章 §7.10。

## 6.4 卖家操作与状态迁移的对应关系

> 本表是本章的**验收核对基准**：卖家的每个操作都必须能落到至少一个状态迁移编号上。

| 卖家操作 | 功能编号 | 商品状态迁移 | 意向状态迁移 | 前置条件 |
| --- | --- | --- | --- | --- |
| 发布商品 | `FR-03` | — → 在售 | — | 当前无在售 / 冻结商品 |
| 手动冻结 | `FR-05` | `PS-02` 在售 → 已冻结（手动） | 不变 | 在售（**不要求队列清空**） |
| 手动解冻 | `FR-06` | `PS-05` 已冻结（手动）→ 在售 | 不变 | **仅**来源为「手动冻结」 |
| （对交易冻结解冻） | `FR-06` | `PS-06` **不迁移，按钮禁用** | — | **不允许** |
| 进入交易 | `FR-07` | `PS-01` 在售 → 已冻结（交易） | `IS-02` 排队中 → 交易中 | 在售 + 存在队首 |
| 标记交易成功 | `FR-09` | `PS-03` 已冻结 → 已下架（终态） | `IS-05` 交易中 → 交易成功；`IS-04` 其余排队中 → 交易失败（商品已售出） | 已冻结 + 目标意向交易中 |
| 标记交易失败 | `FR-10` | `PS-04` 已冻结 → 在售 | `IS-06` 交易中 → 交易失败（卖家作废）／`IS-07` 交易中 → 排队中（复用原记录、序号刷新） | 已冻结 + 目标意向交易中 |
| 手动下架 | `FR-23` | `PS-08` 在售 → 已下架（终态） | — | 在售 + **队列为空** |
| 查看名单 | `FR-08` | 不变（只读） | 不变（只读） | — |
| 查看历史 | `FR-11` | 不变（只读） | 不变（只读） | — |
| 查看口令码 | `FR-24` | 不变（只读） | 不变（只读） | 意向处于**非终态** |
| 修改密码 | `FR-02` | 不变 | 不变 | — |

> **三条「不是解冻」的区分**（易混）：① **手动解冻**（`PS-05`）只改商品状态，**不碰任何意向**；② **标记交易失败**（`PS-04`）才是正式结束与某位买家的交易，同时裁决该意向；③ **买家撤销**（`IS-03`）是买家侧操作，卖家无法触发（澄清 Q14、`BR-06`）。

## 6.5 字段校验规则（发布商品）

| 字段 | 必填 | 校验规则 | 依据 |
| --- | --- | --- | --- |
| **名称** | **是** | ≤ **50 字符** | `C-13`、`DEC-22`、澄清 Q21 |
| **描述** | 否 | 纯文本，≤ **500 字符**，**须做 XSS 防护**（输入校验 + 输出转义） | `C-13`、`C-15`、`DEC-22`、`NFR-20` |
| **图片** | 否 | 最多 **1 张**主图；JPG 或 PNG；单张 **≤5MB**（超出给提示）；不传则显示**占位图**；存**服务器文件系统**、数据库存**路径**；**不生成缩略图** | `C-08`、`C-14`、`DEC-09`、`DEC-34`、`NFR-11`、澄清 Q13、Q21 |
| **价格** | **是** | 人民币（元）；**两位小数**；**> 0 且 ≤ 999,999.99** | `C-12`、`DEC-21`、澄清 Q21 |

> **图片 5MB 限制须做前后端双重校验**（`NFR-11`）。
> **发布后以上四项均不可修改**（`BR-15`）。

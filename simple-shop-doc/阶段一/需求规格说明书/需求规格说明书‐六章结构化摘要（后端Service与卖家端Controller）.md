# 第 7 章　口令码专题（v1.1）

## 7.1 定位与生命周期（§7.2）
- 口令码 = 买家提交意向成功后**当场生成并展示的唯一凭证**；买家不注册/不登录/不设账号（基线需求 3、`O-01`），口令码是**无账号体系下买家唯一的身份凭证**。
- 与意向 **一一对应、全局唯一**（`BR-25`）。
- 只能做三件事：**查状态、改姓名电话、撤销意向**（`BR-32`）。
- 一句话口径：**口令码的有效性只取决于「所属意向是否处于终态」，与商品状态完全无关。**

**状态绑定核心表（§7.2.3）**

| 意向状态 | 是否终态 | 口令码是否有效 | 买家可执行操作 |
| --- | --- | --- | --- |
| 排队中 `queued` | 否 | ✅ 有效 | 查位次 / 改姓名电话 / 撤销 |
| 交易中 `trading` | 否 | ✅ 有效 | 查「是否已进入交易」/ 改姓名电话（**不可撤销**） |
| 交易成功 `succeeded` | 是 | ❌ 失效 | 无 |
| 交易失败 `failed` | 是 | ❌ 失效 | 无 |
| 已撤销 `revoked` | 是 | ❌ 失效 | 无 |

> `BR-27`：**「重新排队」不是终态**，是「交易中」→「排队中」，口令码**保持有效**，买家可继续用**原口令码**查询。

## 7.2 生成规则（§7.3）
| 编号 | 规则 |
| --- | --- |
| `BR-25` | 与购买意向**一一对应、全局唯一** |
| `BR-25` | 格式 **12 位大写字母 + 数字**（字符集 36：A–Z 与 0–9）；**不排除易混字符 `0/O/1/I`**（`DEC-07`、`C-16`） |
| — | **生成时机**：`FR-13` 提交意向的**同一事务内**生成，与排序序号一并分配 |
| `BR-24` | 生成后**立即**在提交成功页展示 |
- 不排除易混字符是**开发方接受的已知体验代价**（`DEC-07`），不视为缺陷。
- 业务方 Q20 **未提任何格式/长度要求**（仅要求唯一）；**12 位是开发方决定**。Q20 提到的「≥8 位」是**卖家后台登录密码**要求（`C-17`），**不适用于口令码**。
- **生成算法无具体规定**（原文只规定字符集与长度，未写算法）；§7.11 明确「把口令码写成服务端对意向的数字签名」是常见错误写法——那是实现方案而非需求，需求口径是「**唯一、即显即存**」。

## 7.3 展示规则（§7.4）
- `BR-24`：提交成功后**当场展示在成功页，且仅展示这一次**。
- `UX-04`：成功页**必须提醒买家保存**（业务方明确要求，强制项，澄清 Q23）。
- 系统**不重发**、页面**不可回看**、买家侧**无任何找回入口**（`BR-24`、`BR-30`）。
- `FR-21`：**不向买家发送任何通知**（无短信/邮件/站内信/推送）。

## 7.4 校验与三态响应（§7.6）
**校验维度**：`DEC-11` —— 只校验「**码 → 意向**」映射是否存在 + 该意向**是否终态**；**不再单独校验商品是否下架**。`BR-28` 返回三种结果。`NFR-13` 须可理解且**区分「错误口令」与「失效口令」**。

**三态判定式（§7.6.2）**

| 返回结果 | 判定条件 | 是否返回买家信息 | 提示口径 |
| --- | --- | --- | --- |
| **错误口令** | 口令码在数据库中**不存在** | 否 | 提示口令不正确，可重试 |
| **失效口令** | 口令码存在，但对应意向**已处于终态**（`succeeded`/`failed`/`revoked`） | 否 | 只说**已失效**，**不说明原因** |
| **有效口令** | 口令码存在，且意向为「**排队中**」或「**交易中**」 | 是 | 返回位次与交易状态 |

**两条不得越界约束**：`BR-29` 失效提示只说已失效、不说明原因，**不得透露**「商品已售出」「交易失败」等结果（合并原 `DEC-36`）；`BR-32` 校验通过也只能执行三件操作，无其他数据出口。

**错误次数策略**：`BR-33` / `NFR-15` —— 口令码查询接口**不做错误次数限制**（`DEC-12`）。
> 与 `NFR-17`（`DEC-26`，提交意向接口的「基础限流 + 前端防抖」）**分列，不矛盾**。

## 7.5 失效规则（§7.5）
- **判定标准**：`BR-26` / `INV-07` —— 只看所属意向是否终态，**与商品状态无关**；`INV-08` —— 「排队中」意向的口令码**必然有效**。
- **失效的四条触发路径**：
  1. 卖家标记**交易成功**（`IS-05` 交易中 → 交易成功）
  2. 他人成交导致**商品已售出**（`IS-04` 排队中 → 交易失败，由 `FR-09` 自动批量处理）
  3. 卖家裁决**作废**（`IS-06` 交易中 → 交易失败）
  4. 买家自行**撤销**（`IS-03` 排队中 → 已撤销；仅「排队中」可撤销）
- **注意**：卖家标记**交易失败本身并不必然**使口令码失效——若同时选择「**重新排队**」，意向回到「排队中」，口令码**保持有效**（`BR-27`、`IS-07`）。
- **三条边界**：`B7-01` 商品下架**不直接导致**失效（下架前提是名下所有意向已终态 `INV-05`，两规则是「必然同时成立」而非因果）；`B7-02` 商品在售/已冻结时只要意向非终态，口令码**有效**；`B7-03` 意向终态时商品**不一定**下架（作废后商品恢复在售 `PS-04`）。
- **失效后买家侧**：`BR-31` 无法查询/修改、**无法获知任何结果**（含「未成交」「已成交」）；但**卖家后台历史记录完整保留**。

## 7.6 丢失、找回与后台代查（§7.8）
| 编号 | 规则 |
| --- | --- |
| `BR-30` | **无买家自助找回渠道**；**卖家后台可查看非终态意向的口令码**并线下转告 ⇒ 口令码须**可反查原文**（明文或可逆存储） |
| `NFR-16` | 同上，登记为**已接受的安全权衡** |
| `FR-24` | 功能入口：卖家后台在意向名单中查看**非终态意向**（排队中/交易中）的当前口令码（**开发方新增**） |
| `X-03` | 口令码**线下转告属系统外业务**，系统只提供查询手段 |

## 7.7 §7.9 存储要求（全部条目，`S7-01` ~ `S7-04`）
| 编号 | 要求 | 依据 |
| --- | --- | --- |
| **`S7-01`** | 口令码须**可反查原文**——允许**明文存储**或**可逆加密**。**不可只存单向哈希** | `BR-30`、`DEC-03`、`DEC-05` |
| **`S7-02`** | 口令码字段**非空、全局唯一**（**唯一索引**） | `BR-25` |
| **`S7-03`** | 口令码与意向**一一对应**，**不作为独立实体的主键** | `BR-25` |
| **`S7-04`** | 口令码**不因商品下架而被删除**——**在购买意向表中**须完整保留；但**归档时口令码不复制到历史意向表**，即**历史记录中不含口令码字段**（v1.1 修订，依据已决 `9-S`） | `BR-21`、`DEC-19`、`9-S` |

`S7-04` v1.1 修订理由（4 条）：① 归档前口令码必已失效；② 口令码查看能力只对非终态意向开放（`FR-24`/`NFR-16` 对终态不返回可用值）；③ 历史查询 `I11-16` 只展示姓名、电话、意向提交时间与交易结果，**不消费口令码**；④ 附带收益——`token` 的「全局唯一」只需在**购买意向表**内成立，**跨表唯一性缺口消除**。

## 7.8 唯一性如何保证（小结，供 Service 实现）
- 业务规则：`BR-25` 一一对应 + 全局唯一。
- 存储要求：`S7-02` **非空 + 唯一索引**（库级唯一约束）；`S7-03` 不作独立实体主键（属于意向表的一个字段）。
- 校验层级：**值校验不下沉数据库**（已决 `9-T`）——`NFR-02` v1.1 明确格式校验在**应用层**（生成时断言格式 `^[A-Z0-9]{12}$` + 查询参数归一化），唯一性用独立校验脚本读**购买意向表**全量比对；**不得声称「由数据库约束保证格式」**。唯一索引仍存在（`S7-02`）。
- v1.1 后唯一性**只需在单表（购买意向表）内成立**（因历史意向表已不含 `token`）。

## 7.9 口令码专题中与 Seller/Service 实现相关的硬性要求（汇总）
1. **生成**：提交意向的**同一事务内**生成 12 位 `[A-Z0-9]{12}`，与 `queue_order` 一并分配（§7.3）。
2. **存储**：明文或可逆；非空 + 唯一索引；不建独立实体（`S7-01`~`S7-03`）。
3. **归档**：口令码**不进历史意向表**（`S7-04`，v1.1）。
4. **卖家端新增能力**：`FR-24` —— 后台名单可查**非终态**意向的口令码原文；对应接口 `I11-14`（§13.4.2）。终态**不返回可用值**（`NFR-16` 可测指标②）。
5. **三态校验服务**：只查「码→意向」+ 是否终态，**不查商品状态**（`DEC-11`）。
6. **失效提示**：不得说明原因、不得返回买家信息（`BR-29`）。
7. **不做限流**：口令码查询接口不限错误次数（`BR-33`/`NFR-15`）。
8. **不做通知**：不重发、不通知（`BR-24`、`FR-21`）。
9. **不发送**：页面不可回看；无买家侧找回入口（`BR-30`）。
10. **禁止项**：不得让买家「作废/重新排队」、不得「确认进入交易」、不得查看他人意向/名单（`NFR7-05`）、不得修改姓名电话以外的内容、不得再次获取口令码。
11. **风险登记义务**：`R7-01`~`R7-06` 与第 12 章 `R12-xx` 口径必须一致，不得两处不同表述（§12.5.2）。

## 7.10 安全权衡 `R7-01` ~ `R7-06`（§7.10）
| 编号 | 取舍 | 代价 | 依据 |
| --- | --- | --- | --- |
| `R7-01` | 明文可反查（不存哈希） | 库泄露 ⇒ 全部凭证泄露 | `DEC-05`、`NFR-16` |
| `R7-02` | 查询不做错误次数限流 | 可无限次尝试 | `DEC-12`、`NFR-15`（前提：码长 12 位） |
| `R7-03` | 不排除易混字符 | 更易输错 | `DEC-07` |
| `R7-04` | 区分「错误口令」与「失效口令」 | 可判断某码是否曾存在（轻量枚举面） | `DEC-11` |
| `R7-05` | 失效后查不到任何结果 | 未成交买家无反馈 | 澄清 Q19、`BR-31` |
| `R7-06` | 不发送任何通知 | 买家可能长期不知情 | `DEC-08` |

## 10.3 `P10-05` 登录页（§10.4.1）
- 入口：未建立有效会话时访问后台任意页自动跳转；**会话超时 30 分钟**亦回本页（`DEC-13`）。承接 `FR-01`。
- 字段：`account` 账号（单行文本，必填，非空）；`password` 密码（密码框，必填，非空——**≥8 位是修改密码时的规则**，登录侧不另设长度限制）。
- 按钮：登录（账号、密码均非空 → 校验并建立会话 **session + token**）。
- 状态表现：登录失败 → `M10-23`（**统一提示，不区分「账号不存在」与「密码错误」**）；**不限失败次数**（`DEC-25`）、**无图形验证码**（`DEC-26`）；会话超时返回本页 → `M10-22`；**不含**「找回密码/重置密码」入口（`DEC-06`、`O-12`）。
- 空态：本页无列表、无数据展示。

## 10.4 `P10-06` 发布商品页（§10.4.2）
- 入口：`P10-07` 点「发布商品」；**前置：当前不存在在售/冻结商品（`BR-11`）**。
- 字段与校验：
  | 字段 | 控件 | 必填 | 校验与提示 |
  | --- | --- | --- | --- |
  | `name` 名称 | 单行文本 | 是 | ≤50 字符；统一文本规则（§9.2.5）：拒绝 `<` `>`、禁止首尾空格、**不允许换行** |
  | `description` 描述 | 多行文本 | 否 | 纯文本 ≤500 字符；**允许换行**；输入拒绝 `<` `>`；**输出须转义**（`C-15`、`NFR-20`） |
  | `pic_url` 图片 | 文件选择（单张） | 否 | **JPG/PNG、≤5MB**；**前端 + 后端双重校验**（`C-14`、`NFR-11`）；不传则买家端显示占位图 |
  | `price` 价格 | 数字输入 | 是 | 人民币元、两位小数、**>0 且 ≤999,999.99**（`C-12`） |
- 按钮：发布（名称、价格已填且全部校验通过 → **二次确认** → 创建商品 `status = on_sale`，写 `create_at`；`M10-25`，因发布后不可修改）；取消（始终可用）。
- 状态表现：已存在在售/冻结商品仍尝试提交 → **拒绝创建**并提示 `M10-24`（`INV-01`、`BR-11`）；字段超限 → 就地提示 `M10-29`~`M10-32`；**本页无「编辑」入口**。
- 空态：无列表；图片可提供本地预览（可选）。

## 10.5 `P10-07` 当前商品与意向名单页（后台首页，§10.4.3）——**卖家端核心页**
- 承接 **9 个 FR**：`FR-04`~`FR-10`、`FR-23`、`FR-24`。
- 区域构成：商品信息区｜商品操作区｜**意向名单区（表格）**｜交易操作区｜导航区。
- 字段：`fail_reason` 失败备注（「标记交易失败」弹窗内多行文本，**否**必填，**≤300 字符**，**允许换行**，**买家不可见**）。其余为只读展示。

**按钮及可用条件（原表）**
| 按钮 | 可用条件 | 对应迁移 | 点击动作 | 二次确认 |
| --- | --- | --- | --- | --- |
| 发布商品 | 当前**无**在售/冻结商品（`BR-11`） | — | 跳转 `P10-06` | 否 |
| 手动冻结 | 商品 `status = on_sale`；**不要求队列为空** | `PS-02` | `status → frozen`，`freeze_by → manual` | 是（`M10-33`） |
| 手动解冻 | 商品 `status = frozen` **且** `freeze_by = manual` | `PS-05` | `status → on_sale`，`freeze_by` 清空 | 否 |
| 手动解冻（**禁用态**） | `freeze_by = trade` → **按钮禁用**，提示 `M10-15` | `PS-06`（不迁移） | — | — |
| 手动下架 | 商品 `status = on_sale` **且队列为空**（无 `queued` 意向） | `PS-08` | `status → off_sale` 并**归档入历史** | 是（`M10-17`） |
| 手动下架（**禁用态**） | **队列非空** → 按钮禁用，提示 `M10-16` | — | — | — |
| 进入交易 | 商品 `status = on_sale` **且存在队首**；**仅名单第 1 行可用** | `PS-01`、`IS-02` | 商品 → `frozen`/`freeze_by → trade`；该意向 → `trading`；写 `trade_start` | 是（`M10-18`） |

| 标记交易失败 | 商品 `freeze_by = trade` **且**存在 `trading` 意向 | `PS-04`、`IS-06`/`IS-07` | 商品 → `on_sale`；弹窗**裁决**：**作废**→`failed`（`fail_type = voided`）/ **重新排队**→`queued`（`queue_order` 刷新至队尾，`create_at` 不变，**口令码保持有效**）；可填 `fail_reason` | 是（`M10-20`） |
| 查看口令码 | 该意向状态 ∈ {`queued`, `trading`}（**非终态**）；**终态不展示** | — | 展示口令码原文（`FR-24`） | 否（兜底查询，`10-F` 决定不做确认） |

**五条易错口径（原文）**
1. 「进入交易」**只能对队首（名单第 1 行）可用**，其余行置灰（`BR-12` 先到先得）。
2. 「手动冻结」**不要求队列为空**；「手动下架」**要求队列为空**——前置条件不同，不可混用。
3. 交易冻结的商品，「解冻」按钮**必须禁用**（`PS-06`，`FIX-01` 落点）。
4. 「标记交易成功」是全系统风险最高的操作；二次确认文案**必须说明连带后果**（`M10-19`）。
5. 「重新排队」不产生终态、口令码保持有效；弹窗选项文案不得写成「作废」。

**数据展示**
- 商品信息区：`name`/`description`/`pic_url`/`price`（输出转义）；`status` 在售/已冻结；**`freeze_by` 冻结来源必须展示**（卖家据此判断解冻按钮是否可用）；`create_at` 发布时间（UTC 存储、东八区展示）。
- 意向名单列定义：**位次**（按 `queue_order` 升序的秩；`trading` 意向**不占位次**）｜`name`｜`tel`｜**意向提交时间 = `create_at`（原始提交时间，不是刷新后的序号时间）**｜`status`｜**交易结果/失败类型**（`fail_type` 与 `fail_reason` 可查看，**均买家不可见**）｜**口令码**（仅非终态可查看原文）｜**操作**（「进入交易」——仅第 1 行）。
- 枚举对照：`queued` 排队中｜`trading` 交易中｜`succeeded` 交易成功｜`failed` 交易失败｜`revoked` 已撤销；失败类型 `sold_out` 商品已售出｜`revoked` 买家撤销｜`voided` 卖家作废｜`requeued` 重新排队。
- 排序口径：名单按 `queue_order` 升序。**不加「交易开始时间」列**（`trade_start` 只记录、不展示）。分页每页 10 条（`10-E`）。
- 状态表现：无当前商品 → 空态 + 引导「发布商品」；无任何意向 → 名单区空态 `M10-26`；队列达 1000 条上限 → 名单区**顶部显示计数提示**（`10-D`：显示）；加载失败 → 错误态 + 重试。

## 12.2 与后端实现直接相关的可测口径（§12.3）
### 12.2.1 会话与超时（`NFR-04`）
- `session + token`；**30 分钟**无操作自动退出；**修改密码后全部会话立即失效**（含**其他**会话，不只当前会话）。
- 验证：闲置 30 分钟（**宽容 ±1 分钟**，`12-P7`）后原凭证请求被拒并跳转登录页；改密后旧凭证 **≤5s** 内失效。双会话对照测试（A、B 登录 → A 改密 → B 下一次请求应被拒）。

### 12.2.2 日志（`NFR-08`、`NFR-12`）
- **业务数据（商品、意向、历史、流水、账号）永久保留**；**操作日志保留 3 个月**（两者分列，**不得互相套用**）。
- 关键操作日志 **8 类**：冻结、解冻、手动下架、进入交易、标记交易结果、作废／重新排队、查看意向口令码、修改密码。
- 每条含**操作时间（UTC 存储）**、**操作类型**、**目标对象**。
- **日志不纳入业务表结构**（已决 `9-B`，由**应用日志实现**；文件轮转，保留 3 个月，`12-P7`）。
- **日志不记录口令码明文**（【推断】，供开发确认，`12-H`）——只记「谁在何时查看了哪条意向的口令码」，不落码值。

### 12.2.3 图片大小与格式（`NFR-06`、`NFR-11`；`C-08`、`C-14`）
- 最多 **1 张**主图；**JPG 或 PNG**；单张 **≤5MB**；**不生成缩略图**。
- 存**服务器文件系统**，数据库**仅存路径**（不存二进制）。
- **前端预校验 + 后端独立校验**：绕过前端直传 >5MB 或非 JPG/PNG **仍被拒绝**；提示 `M10-31`。
- 无图显示**占位图**（不出现破图）。
- 性能：单页图片数 ≤1；首屏可交互 ≤2s、含单张 5MB 原图完整加载 ≤8s（移动端 4G 限速：下行 ≥10Mbps、RTT≈100ms）。

### 12.2.4 限流（`NFR-17`）
- 唯一的匿名写入口 = **提交购买意向**接口，须做**基础限流 + 前端防抖**；**不做图形验证码**。
- 阈值：**同一 IP ≤10 次/分钟**（`12-P6`）；超出返回「请稍后重试」/被拒并给出可重试提示；**前端防抖 2s**（连续点击仅产生 1 次请求）。
- **两个入口策略分列，不矛盾**：`NFR-03`（登录不限失败次数）≠ `NFR-17`（提交限流）；`NFR-15`（口令码查询不限次）≠ `NFR-17`（提交限流）。
- 登录：连续 100 次错误密码后第 101 次仍可正常尝试；登录页与登录接口**均无验证码字段与校验分支**；密码长度校验 ≥8 位仍生效。
- 口令码查询：连续 1000 次错误查询后仍返回「错误口令」，**不锁定、不延迟、不要求验证码、不要求人工介入**。

### 12.2.6 并发要求（`NFR-01`、`NFR-07`）

### 12.2.7 安全要求（`NFR-02`、`NFR-03`、`NFR-15`、`NFR-16`、`NFR-17`、`NFR-20`）
- `NFR-02` ① 全部口令码匹配 `^[A-Z0-9]{12}$`；② 任意两条意向的口令码互不相等。验证 = **写入与查询路径的程序化校验**（生成时断言格式 + 查询参数归一化）+ **唯一性断言**（独立校验脚本读**购买意向表**全量比对）。**⚠️ v1.1：不再采用「库内全量正则校验」，不得声称「由数据库约束保证」**。
- `NFR-16` ① `I11-14` 对 `queued`/`trading` 返回原文且与库内值一致；② 对 `succeeded`/`failed`/`revoked` **不返回可用口令码**；③ 库内口令码字段为明文或可逆形式。
- `NFR-20` ① 输入含 `<` 或 `>` 时被拒绝并提示（`M10-29`/`M10-30`/`M10-36`）；② 即便绕过输入校验写入，页面渲染时输出被转义。涉及字段：商品名称、描述、买家姓名、失败备注。

### 12.2.8 其他实现相关（`NFR-05`、`NFR-08`、`NFR-09`、`NFR-13`、`NFR-14`、`NFR-18`）
- `NFR-05`：买家端**无以姓名/电话/商品 ID 查意向的端点**；**名单接口未登录调用被拒**。
- `NFR-09`：界面全部文案（含错误提示、状态提示、按钮禁用提示）均可在 §10.5 找到 `M10-xx`，**抽查命中率 100%**。
- `NFR-13`：三种输入分别返回 `M10-05`/`M10-06`/`M10-07` 或 `M10-08`，**互斥且必居其一**；失效响应体与页面文案**不含**「已售出」「交易失败」「已撤销」，**不含**姓名、电话、商品信息。
- `NFR-14`：三项必须项逐条可核 = `M10-04`（含口令码原文与保存提醒）、`M10-01`、`M10-07`/`M10-08`；全站**不存在**交易流程说明页与说明文字。**验收红线：§10.5.3 标注 `【必须】` 的 5 条文案遗漏任一即验收不通过**。
- `NFR-18`：库内 `datetime` 均为 UTC 时点（不含本地偏移）；所有页面与接口输出为 UTC+8；同一记录在列表与详情中展示一致。

## 5.2 `FR-12` ~ `FR-22` 逐条要点（§5.3）
- **`FR-12` 浏览当前商品**：触发 = 访问买家端首页（无需登录/凭证）；输入 = 无，**URL 不含商品 ID**；处理 = 查询**当前商品**（在售或已冻结那一件，由 `BR-11` 保证至多一件）；输出 = 名称、描述、图片（无图占位图）、价格、当前状态；异常 = 无当前商品 → **不显示商品**（空态，无占位商品）。**已冻结时详情仍可浏览**（`BR-14`），只是不能提交意向。
- **`FR-13` 提交购买意向**：触发 = 商品处于「**在售**」时从首页进表单并提交；输入 = **姓名（必填）+ 联系电话（必填）**，除此不采集任何信息（Q5）。
  处理规则 7 步：① 校验姓名、电话非空且长度合法；② 校验商品当前为「在售」，否则拒绝；③ **校验队列未达上限（1000 条）**；④ **同一事务内**分配排序序号（独立自增）；⑤ 生成 12 位口令码；⑥ 意向状态置「排队中」；⑦ **商品状态不变**（`BR-13`）。
  输出 = 跳转提交成功页展示口令码。关联 `NFR-01`、`NFR-07`、`NFR-17`、`DEC-10`、`DEC-15`、`DEC-23`、`DEC-26`、`DEC-37`。
- **`FR-14` 获取口令码**：提交成功时**自动触发**；当场展示原文，**仅展示这一次**，系统不重发、无通知；页面**须提醒保存**；异常 = 未保存即离开 → **无自助找回渠道**（唯一补救是卖家后台查看后系统外转告）。
- **`FR-15` 凭口令码查询意向**：输入 = 口令码（12 位）；按第 7 章三态校验；有效时返回 ① 当前位次「当前排第 N 位」②「是否已进入交易」标识（排队中返回位次；交易中返回「已进入交易」）；异常 = 错误口令→提示不正确；失效口令→提示已失效、**不返回任何买家信息、不说明原因**；空值/格式不符→**前端提示，不发起校验**。
- **`FR-16` 凭口令码修改信息**：输入 = 新姓名和/或新电话（**两项均可独立修改**，可只改其中一项）；校验后更新；**不影响排队位次**（不改排序序号、不重新排队）；异常 = 口令码已失效→不可修改，只提示已失效；字段校验失败→提示。**改信息只能走口令码通道**，不能靠再次提交同名联系方式覆盖（`DEC-37`、`BR-23`）。
- **`FR-17` 凭口令码撤销意向**：**仅当意向处于「排队中」时**允许撤销；撤销后置「已撤销」（终态 `IS-03`）、**退出队列**；异常 = 意向「交易中」→**不允许撤销**（`BR-19`、Q10、`O-09`）；口令码失效→只提示已失效。买家的「撤销」与卖家的「作废/重新排队」是**两回事**，互不触发（`BR-06`、Q9）。
- **`FR-18` 交易中状态提示**：触发 = 商品「已冻结」（交易冻结）期间；① 提示「商品交易中，暂停接收新意向」；② 提交入口**不可用**（隐藏或禁用）；③ 详情**仍可浏览**；异常 = **绕过前端直接发起提交 → 服务端一律拒绝**（`INV-03`）。
- **`FR-19` 当前商品展示规则**：**不设商品列表页**，首页直接展示当前商品；四态（无商品→不显示空态；在售→正常展示、入口可用；已冻结→仍展示详情 + 「已冻结」+ 交易中提示、入口不可用；已下架→不显示、无历史浏览入口）；结构约定 `S5-01`（不设列表页）、`S5-02`（URL 不含商品 ID，正确理由是「单一商品槽位设计」而非服务端渲染）、`S5-03`（无历史浏览入口、无「我的意向」列表页）。
- **`FR-20` 意向查询入口**：**不提供**「我的意向/我的订单」列表页，**也不提供**凭姓名或电话反查意向的入口；唯一途径是输入口令码；异常 = 遗失口令码 → 走 `FR-24` 线下兜底。不做反查的原因：无身份验证手段，凭电话反查等于任何人可查他人信息（`NFR-05`）。
- **`FR-21` 无主动通知**：系统**不向买家发送任何通知**——无短信、无邮件、无站内信、无推送（`DEC-08`、`O-14`）；买家只能**主动**凭口令码查询。**须作为业务约束理解，不得视为缺陷**。
- **`FR-22` 口令码输入反馈**：按第 7 章三态给出**明确且可区分**的反馈；任何情况下「失效口令」**不得**透露交易结果、**不得**返回买家信息（`BR-29`、`NFR-13`）。

## 5.4 异常与边界汇总 `E5-01` ~ `E5-12`（§5.3.1）
| 编号 | 场景 | 系统行为 |
| --- | --- | --- |
| `E5-01` | 商品**已冻结**期间提交意向 | **拒绝**，提示「商品交易中，暂停接收新意向」 |
| `E5-02` | 商品**已下架** | 买家端**不显示**该商品，无任何查询入口 |
| `E5-03` | 提交时**姓名或电话为空** | 拒绝提交并提示必填项 |
| `E5-04` | 意向队列已达 **1000 条**上限 | 拒绝新提交并提示（防御性上限） |
| `E5-05` | **同一电话**对同一商品重复提交 | **允许**，每次提交独立成条，不合并、不覆盖 |

| `E5-11` | 买家丢失口令码 | 无自助找回；由卖家后台查看后线下转告 |
| `E5-12` | 网络中断导致重复提交 | 每次提交独立成条；前端防抖降低重复概率 |

## 5.5 三态响应与展示约束（§5.5、§5.6）
- **三态判定与返回**（与第 7 章一致）：错误口令=库中不存在、不返回买家信息、可重试；失效口令=存在但意向已终态、**不返回买家信息、不说明原因**（不得出现「商品已售出」「交易失败」等字样）；有效口令=存在且排队中或交易中、返回位次与交易状态。
- **边界 `B5-01`**：失效提示**不能带原因**；**`B5-02`**：失效**与商品下架无关**，只看意向是否终态（把「商品下架」写进失效条件即为错误）。
- **有效口令下的输出**：排队中 → 「当前排第 **N** 位」（N 由排序序号决定）；交易中 → 「**已进入交易**」标识（此时该意向已不在队列中）。
- **口令码展示三条硬约束**：`K5-01` 时机 = 提交成功页、当场展示；`K5-02` **仅展示这一次**，不重发、不可回看；`K5-03` 必须**提醒买家保存**（强制项）。

## 5.6 买家侧交互要求（§5.7，`UX-01` ~ `UX-07`）
- 效力分级：① 必须满足 = `UX-04`、`UX-06`（部分）；② 明确不做 = `UX-05`（**已取消**）；③ 开发方自定 = `UX-01`、`UX-02`、`UX-03`、`UX-06`（部分）。
- **业务方硬性要求清单（3 项）**：① 提交成功后**口令码直接展示**并**提醒保存**；② 页面提示「**商品交易中，暂停接收新意向**」；③ 凭口令码**可查「当前排第 N 位」**与**「是否已进入交易」**。
- **明确不要求**：不需要交易流程说明页、不需要任何流程说明文字、二次确认机制不强制。
- 买家流程完整表述（业务方原话）：**看商品 → 提交意向（拿口令码）→ 凭码查状态**。

# 第 13 章　验收标准与附录（v1.1）

## 13.1 验收总则（§13.2）
- **级别（沿用第 8 章 `P0`/`P1`/`P2`）**：`P0` = 违反后必然导致 `INV-01`~`INV-08` 至少一条不成立 → **验收不通过且阻断发布**；`P1` = 业务方明确要求或已裁定确认的规则 → **功能不通过验收**；`P2` = 纯开发方落实取径 → 记录变更即可，不阻断验收。混级按**最高级别**验收。
- **验收方式 5 种**：`V-01` 数据库断言；`V-02` **接口调用（卖家端 REST）——必须包含绕过前端的负向调用**；`V-03` 页面走查；`V-04` 端到端流程演练；`V-05` 交付文档检查。
- **不纳入验收**：视觉设计、`【建议】` 项（含二次确认）、`OPEN-01`~`OPEN-03`、`9-O`。
- **验收通过判定**：全部 `P0`（`AC-01`~`AC-08` 及标注 `P0` 的拦截项）+ 全部 `P1`（`AC-09`~`AC-16`、`AC-24`~`AC-29`）通过；`P2` 调整须有变更记录；`12-P1`~`12-P7` 按定稿目标值验收。

## 13.2 `AC-01` ~ `AC-29` 中与后端 Service/Controller 相关的验收标准
**不变量验收（`AC-01`~`AC-08`，全 `P0`，全部 `V-01` 可执行）**
| 编号 | 对应不变量 | 通过判据要点 |
| --- | --- | --- |
| `AC-01` | `INV-01` 全局至多 1 个商品处于在售/已冻结 | 再次发布商品 B **被拒绝**并展示 `M10-24`；任意时点行数 **≤1** |
| `AC-02` | `INV-02` 同一商品任一时刻至多 1 条意向「交易中」 | 对第二条调用 `I11-11` **被拒绝**；任意时点 `trading` 条数 **≤1** |
| `AC-03` | `INV-03` 冻结期不接受任何新意向提交 | 手动冻结/交易冻结两场景下（页面 + 直接 POST）提交**一律被拒、不新增意向行**、展示 `M10-01` |
| `AC-04` | `INV-04` 有「交易中」意向时商品必为「已冻结」 | 进入交易后商品必为 `frozen`；对交易冻结商品调用 `I11-08`（解冻）**被拒绝**（`M10-15`）。⚠️ 单向约束，**手动冻结期间无 `trading` 意向是合法状态** |
| `AC-05` | `INV-05` 下架时名下所有意向均已终态 | 两条路径下历史意向表中**不存在** `queued`/`trading` 记录；**如有则归档事务回滚、商品不得进入已下架** |
| `AC-06` | `INV-06` 「交易成功」意向有且仅有 0 或 1 条 | 计数 **∈{0,1}**；`result = sold` 时为 1、`offline` 时为 0 |
| `AC-07` | `INV-07` 口令码有效性只与意向终态相关 | 商品状态变化前后 K 的返回**完全一致**（均为有效口令） |

## 13.5 §13.6 已知限制（8 项，供方案与验收参照）
1. 买家**不会收到任何通知**，只能主动凭口令码查询（不可规避，业务约束）。
2. 口令码**丢失后无自助找回**，须由卖家后台查看后线下转告（部分规避：卖家可代查，须意向仍处**非终态**）。
3. 买家端**看不到已下架商品，也无历史查询**（不可规避，有意不做）。
4. 口令码**失效后买家查不到任何结果**（含「未成交」）（不可规避，业务约束）。
5. **已发布商品名称/描述/图片/价格不可修改**（不可规避，有意不做；错误只能下架后重新发布修正）。
6. **卖家无自助找回密码**，忘记密码只能在**数据库层面重置**（需运维介入；交付文档须含重置步骤）。
7. **系统不做超时自动恢复在售**；冻结后必须由卖家动手结束（仅「标记交易结果」或「手动解冻（限手动解冻）」两条出口）。
8. **无数据导出能力**（暂缓，二期可补）。

## 14.2 架构形态 `A-01` ~ `A-06`（§3.2.2）

## 14.3 §3.4 开放项（`OPEN-01` ~ `OPEN-03`，与第 12/13 章同口径）
| 编号 | 开放项 | 当前状态 | 建议决断时间 | 影响面 |
| --- | --- | --- | --- | --- |
| `OPEN-01` | 系统部署形态（单机 vs 容器化） | 开发方明确「有同时考虑单机部署和容器化的需求，现阶段暂缓」 | **详细设计阶段前，越早越好** | ① 容器化图片目录需挂载**持久卷**（`C-08`）；② 容器化**多实例**时 session + token 需共享存储，而 `C-04` 已排除缓存组件，**二者存在潜在张力**，届时需复核 `C-07` 与 `C-04` |
| `OPEN-02` | 数据备份与恢复策略 | 开发方暂缓 | 交付前 | 备份须**同时覆盖数据库与图片目录**（`C-02`、`C-08`、`C-18`）；**数据库侧须包含队列序号辅助表** `simpleshop_queue_sequence`（第 9 章 §9.3.1/§9.11，已决 `9-S`）——否则恢复后 `current_value` 归零，会与库内既有 `queue_order` 冲突（唯一索引直接报错，属**可发现**的失败，不会静默产生重复值） |

## 14.4 明确与本轮「Service 层 + 卖家端 Controller」相关的约束
1. **`C-01`/`C-02`/`C-03`**：SpringBoot + MySQL（≥8.0.16）+ 单体应用——Service/Controller 的组织形态。
2. **`C-04`/`A-04`**：**无缓存、无消息队列** ⇒ 并发排序**只能用数据库独立自增序号**，**必须在提交事务内分配**；不得用内存计数器/加锁队列替代（`NFR-01` 验证点）。
3. **`C-06`/`A-01`**：卖家端前后端分离 ⇒ 卖家端 Controller 须提供**完整 REST 接口契约**（入参、出参、错误码；第 11 章 `I11-01`~`I11-16`、`B11-xx`）。
4. **`C-07`**：Controller 层会话 = **session + token**，**30 分钟**无操作自动退出；改密后**全部会话立即失效**（`NFR-04`）。
5. **`C-08`/`A-06`/`C-14`**：图片走文件系统、库只存路径；上传须**服务端独立校验** JPG/PNG 且 ≤5MB（绕过前端直传仍被拒）；须定义访问路径与目录结构。
6. **`C-10`/`C-11`**：Service 内时间统一 **UTC 存储**，对外输出 **UTC+8**。
7. **`C-12`/`C-13`**：价格 0<x≤999,999.99（两位小数）、名称 ≤50、描述 ≤500 —— 属**功能校验**（第 6 章 §6.5、第 9 章 §9.10 为准），Service 须实现。
8. **`C-15`/`NFR-20`**：输入校验（拒绝 `<` `>`）+ **输出转义**，两处都要做。
9. **`C-16`**：口令码 12 位 `[A-Z0-9]`；**格式校验在应用层**（已决 `9-T`，库内不设格式约束）。
10. **`C-17`**：卖家密码 ≥8 位（**仅改密时**校验；登录侧不另设长度限制，见 `P10-05`）。
11. **`C-18`**：业务数据永久保留；**操作日志 3 个月**且**不纳入业务表结构**（已决 `9-B`，应用日志文件轮转），**日志不记录口令码明文**（【推断】，`12-H`）。
12. **`S10-07`（第 10 章）**：会改变状态的操作**前端禁用只是一层，服务端必须独立校验**——`AC-17`/`AC-20`/`AC-21`/`AC-23` 均要求**绕过前端的直接调用也被拒绝**（`V-02` 验收方式）。

# 附：给 Service/Controller 方案的关键交叉结论（逐条有据）
1. **口令码失效判定 = 仅看意向是否终态**（`BR-26`、`INV-07`、`DEC-02`）；商品状态**不参与**（`AC-07`/`AC-19` 明示「不校验商品是否下架」）。
2. **重新排队不产生终态、复用原记录、`queue_order` 刷新至队尾、`create_at` 不变、口令码保持有效**（`BR-27`、`IS-07`、`BR-20`、`AC-16`、`AC-08`）。
3. **标记交易成功的事务顺序不可颠倒**：其余 `queued` → `failed`(`sold_out`) → 本次 → `succeeded` → 商品 `off_sale` 并归档（`BR-03`、`PS-03`、`IS-04`/`IS-05`；`AC-05`/`AC-06` 判据）。
4. **归档事务须保证历史意向表无非终态记录，否则回滚、商品不得进入已下架**（`AC-05`）。
5. **队列上限计数口径 = 当前商品名下非终态意向数**，=1000 拒绝且不新增、返回 `B11-02`（`NFR-07`、`AC-18`）。
6. **会话：30 分钟 ±1 分钟超时、改密后全部会话 ≤5s 失效**（`NFR-04`、`12-P7`）。
7. **限流只作用于提交意向接口（同一 IP ≤10 次/分钟 + 前端防抖 2s）**；登录不限次、口令码查询不限次（`NFR-03`/`NFR-15`/`NFR-17`，三处策略分列）。
8. **日志 8 类关键操作**（冻结、解冻、手动下架、进入交易、标记交易结果、作废／重新排队、查看意向口令码、修改密码），含 UTC 时间、类型、目标对象，保留 3 个月（`NFR-12`、`12-P7`）。
9. **`FR-24`/`I11-14` 只对非终态意向返回口令码原文**；历史详情 `I11-16` **不返回 `queue_order` 与 `token`**（`11-I`），历史意向名单排序键为 `create_at`（`11-H`）。
10. **文案即可判定为需求**：`M10-01`、`M10-04`、`M10-06`、`M10-07`、`M10-08` 5 条 `【必须】`文案与后端返回的错误提示必须一致（`NFR-09` 要求界面文案 100% 可映射到 `M10-xx`；`AC-28` 逐条核对；`M10-06` 的信息边界不可放宽）。

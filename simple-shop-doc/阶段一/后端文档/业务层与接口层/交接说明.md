## 1. 环境与构建

### 1.1 怎么跑

> ⚠️ **必须在工程根目录（`simple-shop/simple-shop-backend/`）执行 `mvn`**——原因见《数据层 · 交接说明》§2.1
> （`.mvn/maven.config` 把本地仓库重定向到**项目内** `.m2/repository`，该路径**相对当前工作目录**解析）。

```bash
mvn clean verify                 # 编译 + 全部 462 个测试
mvn test                         # 仅跑测试
mvn spring-boot:run              # 开发期启动（默认 8080 端口）
mvn clean package                # 产出 target/simple-shop.war
java -jar target/simple-shop.war # 以 war 方式启动（本轮所有真实端口验证都用这条）
```

### 1.2 环境变量（容器化部署时全部用它覆盖）

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DB_URL` | `jdbc:mysql://localhost:3306/simple_shop?…` | 连接串**必须**保留 `connectionTimeZone=UTC` 与 `characterEncoding=UTF-8` |
| `DB_USERNAME` / `DB_PASSWORD` | `root` / `123456` | 正式环境请注入，不要沿用默认值 |
| `IMAGE_DIR` | `./data/images` | 商品图片目录。⚠️ **容器化时必须挂持久卷**（见 §10） |
| `TEST_DB_URL` | `…/simple_shop_test` | 仅测试用（`application-test.yml`） |

**日志目录**用 **JVM 系统属性**而非环境变量：`-DAUDIT_LOG_PATH=/var/log/simple-shop`。
> ⚠️ 这是**有意的**：logback 的 `${ENV:-default}` 语法对「未定义的环境变量」不可靠，只对系统属性可靠。
> 实测 `-DAUDIT_LOG_PATH=target/smoke-logs` 确实改变了审计日志目录。

### 1.3 启动时会自我校验的两件事

1. **Flyway** 校验 2 个迁移脚本的校验和（**改已发布脚本 → 启动直接报错**）；
2. **Hibernate `ddl-auto=validate`**：实体与库结构不一致（列宽/列名/可空性）会启动失败。
   > 所以「应用起得来」本身就等于一条「实体 ↔ 库结构一致」的断言。

## 4. 接口层的 6 条硬口径（每条都对应一个真实的坑）

### 4.1 **业务规则拒绝返回 HTTP 200 + 业务码**（不要"顺手"改成 4xx）

「队列非空」「商品非在售」「非队首」这类结果是**业务语义的正常分支**（§11.3.4）。
只有 4 个例外：`10002`→401、`20011`→404、`50000`→500、`50002`→400。
**默认 200 在 `ErrorCode` 里是默认值**，不是逐个枚举出来的。

### 4.2 **`message` 是 ASCII 英文，且前端不得展示**（已定 Q-13）

前端按 `code` 映射第 10 章《提示文案表》的 `M10-xx`（`UX-07`）。故 `message` 只用于 grep 与日志。

### 4.3 ⚠️ **DTO 注解只判「有没有」，取值规则一律归 Service**

这是 S3 发现、**影响 S4/S6 的硬规则**：若在 DTO 上写 `@Size(max=50)`，请求会在**进 Controller 之前**
被拦成 `50002` + HTTP 400，而契约给该字段的专属码（`20007`）是 **HTTP 200** → **专属码永不可达**（死码），
前端还会拿到错误的文案。**判据**：先查 §4.3 错误码表里该字段有没有专属码——有就只留 `@NotBlank`。
（`page`/`page_size` 没有专属码，故注解可以留。）

### 4.4 ⚠️ **三处契约未规定的分支，实现时按这口径收敛**（`§4.2`）

| 情形 | 处理 |
| --- | --- |
| 媒体类型协商失败（`Content-Type` 不对） | 400 + `50002`（**不加处理会变成 500**） |
| HTTP 方法不支持 | 405（保留 REST 惯例） |
| **Controller 方法参数**上的约束不通过 | 400 + `50002`（Spring 6.1 抛 `HandlerMethodValidationException`，**不加处理会变成 500**） |

> 后两条都是「客户端写错请求却被报成服务端内部错误」——同一类缺陷，**两处都实测到过**。

### 4.5 **`price` 全程是字符串**（`11-F`）

入参 `String` → `BigDecimal` 校验 → 出参 `toPlainString()`。**不要**改成 `double`/JSON 数字。

### 4.6 **`snake_case` 靠逐个 `@JsonProperty`**

**不配**全局命名策略（会连带影响实体）。新增字段时请显式写注解——它是契约的一部分。

## 5. Service 层的 7 条口径

### 5.1 ⚠️ 加锁顺序（防死锁，**本层最容易写错的一处**）

**① 序号表行 → ② 商品行 → ③ 意向行**。所有 `...ForUpdate` **必须在事务内**调用。
`markTradeFailure` 的「重新排队」分支需要序号表行锁，故它被**提到商品行锁之前**——
因为买家 `submitIntention` 是「先序号表、不锁商品」，反过来就会**反向取锁**。

### 5.2 **一个业务动作 = 一个事务**；卖家写操作 `@Transactional(timeout = 5)`

`I11-12`（标记成功）是影响面最大的写：它同时改「其余全部意向」「本次意向」「商品状态」并归档，
**顺序不可调换**（先他人失败 → 再本人成功 → **追加流水** → 最后归档），否则 `INV-05`/`INV-06` 会破。

### 5.3 **时间只有一个来源**：`DatabaseTimeProvider`

**禁止** `LocalDateTime.now()` / `new Date()` / `System.currentTimeMillis()` 写业务时间。
（`SessionStore` 用 `Instant.now()` 是**会话挂钟**，会话不是业务数据。）
静态检查命令见 §8.3。

### 5.4 ⚠️ **口令码：三态 + 唯一判定式**

`isTokenValid() = !isTerminal()`，**不得**掺入商品状态（`BR-26`、`INV-07`）。
终态（`succeeded`/`failed`/`revoked`）→ `40002` 且**不展示**；`queued`/`trading` → 返回原文。
**日志绝不记录码值**（`12-H`）：`OperationLogService.log` 的签名里只放意向 ID，**没有放码值的位置**。

### 5.5 **排序口径两处相反，别互相抄**

| 接口 | 排序 | 怎么给 |
| --- | --- | --- |
| `I11-10` 意向名单 | `queue_order` 升序 | 仓储**不内建** → 调用方**必须**显式传 `Sort` |
| `I11-15` 历史列表 | `trade_end` 倒序 | 排序**写在方法名里** → 调用方**不得**再传 `Sort`（会覆盖） |

### 5.6 **会话在进程内**（已定 Q-3）

后端是**单容器**，故 `SessionStore` 用 `ConcurrentHashMap`，**不引入缓存组件、不建会话表**。
⚠️ **改多副本/负载均衡时必须回头改共享存储并复核 `C-04`**。容器重启会丢会话——这是**已接受的**。

### 5.7 **买家端与卖家端的失败表达刻意不同**

卖家端抛 `BusinessException`（有全局处理器翻译成 HTTP）；买家端返回**密封的 `BuyerResult`**（服务端渲染、不走业务码）。
⚠️ 由此有一条硬规则：**买家端返回「被拒」是正常返回，事务会提交**——
所以 `BuyerIntentionService` 的所有拒绝分支**必须早于任何写操作**。

## 6. ⚠️ 三个「秒精度」排序键（本项目最隐蔽的一类问题）

`trade_start`／`create_at`／`trade_end` 都是 `datetime`（**秒**精度，V1 脚本未带 `(3)`）。
**同一秒内**产生的多行，其排序键**完全相同** ⇒ 按它排序的结果**不确定**（InnoDB 上通常表现为插入顺序，
但那只是实现细节）。受影响的三处：

| 位置 | 排序键 | 后果 |
| --- | --- | --- |
| `I11-16` 的 `trades[]` | `trade_start` | 同一秒内的多次交易分不出先后 |
| `I11-16` 的 `intentions[]` | `create_at`（`11-H`） | 同一秒提交的意向分不出先后 |
| `I11-15` 的历史列表 | `trade_end` | 同一秒归档的商品分不出先后 |

**本项目的口径**：契约要的是「**都在**」（`BR-22`「每一次失败都能查到」、`FR-11`「历史可查」），
**不是**「严格时序」。故：
- **界面上不得声称**「按时间严格排序」；
- **写用例时不要断言顺序**——要么先让排序键互不相同再断言（见 `SellerHistoryApiTest` 的两条用例），
  要么只断言「内容都在、集合相等」。
> ⚠️ 这个坑**已经咬过两次**（S7 一条用例单跑绿、全量红；S8 一处不查就撞上）。
> 若确实需要严格时序：把三列改成 `datetime(3)` 并**新增迁移脚本**（改 V1/V2 会导致 Flyway 校验和失配），
> 属数据层变更，须单独评审。

## 7. ⚠️ 已知限制与开放项（交付文档须含开放项说明，`AC-29`）

### 7.1 性能：`12-P1`／`AC-27` **已达标**（含一处口径裁定）

| 对象 | 规模 | P95 实测 | 预算 | 结论 |
| --- | --- | --- | --- | --- |
| 查询（`I11-10`/`I11-15`/`I11-16`） | 1000 意向 + 100 历史 | **10~110ms** | 500ms | ✅ 余量 5~50 倍 |
| 典型写（冻结/解冻、进入交易/标记失败） | 同上 | **36~61ms** | 1s | ✅ 余量 16~28 倍 |
| 归档整队列（`I11-09`/`I11-12`，1000 条） | **1000 条意向** | **1.9~2.8s** | 1s | ✅ **不计入该指标**（见下） |

> **⚠️ 口径裁定（业务方，2026-10-10）**：`§8.4` 的「写操作 P95 ≤ 1s」原文**没有说清单个端点还是整个写请求集**。
> 实测两条「一次点击搬走整队列」的归档写要 1.9~2.8s，而其余写只有 36~61ms。
> **裁定：按「写请求整体的 P95」判定** ⇒ 达标；归档整队列的绝对耗时**不计入该指标**，且经确认**可接受**
> （它是「一个商品生命周期一次」的操作），**不做**批量删除优化。

**成因（实测锁定，便于将来判断是否要改）**：代价全在删除阶段，**Hibernate 6.6 不批处理这批 DELETE**——
归档 1000 条时 `Com_insert` 增量 = **21**（插入已批处理），`Com_delete` 增量 = **1001**（逐行删除）；
试过 `hibernate.order_updates: true`，无效。

**备查：万一将来口径改成「每个写端点各自 ≤1s」**，修法与代价（**本次未实施**）：
把归档末尾的删除改成批量 SQL（`delete … where fk_good_id = ?` + 删商品），预期降到 **0.3~0.5s**；
代价是 ① 绕开持久化上下文（`ArchiveService` 的类注释专门警告过这条路上的坑——`deleteAllInBatch`
→ `TransientObjectException`，S7 实测过）；② 需在数据层**新增**批量删除入口（附录 B 要求「单独提出并评审」）；
③ 会**作废 S7 对归档顺序的验证**，必须重新验证。

用例仍守两条与机器无关的判据（**语句计数** + **5s 数量级护栏**），而不是拿绝对时间当断言
（同配置在单跑与全量跑之间会差 50%+）。详见
[实现过程记录/09-S10…](实现过程记录/09-S10-测试补全与性能实测.md) 的 D-1／O-1。

### 8.2 用例组织的两条约定（写新用例前先看）

1. **字段校验与状态迁移用 CSV 用例表驱动**（`src/test/resources/csv/`）：
   一行一个组合，边界值写成 `REPEAT(商:50)` 而不是手敲 50 个字符。
   ⚠️ 三条踩过的坑：`REPEAT` 里不能用逗号（用**冒号**）；涉及空格的用例用 `@CsvFileSource`（内联的 `@CsvSource` 会静默 trim）；
   「未被拒」不要用 `NULL` 表示（`NULL` 已被 `nullValues` 占用）。
2. **用例表里的「前置状态」用词表描述**（如 `goodsSetup=trade`），由测试代码去造；

## 10. 部署要点（容器化三容器）

| # | 要点 | 不做的后果 |
| --- | --- | --- |
| 1 | **`IMAGE_DIR` 必须挂持久卷** | 归档**不搬迁图片文件**（`DEC-09`），历史商品的图片也依赖这批文件 ⇒ 丢失即永久性数据丢失 |
| 2 | **容器时区设为 UTC**（`ENV TZ=UTC` / `-Duser.timezone=UTC`） | 多一道确定性，防住将来有人误用系统时区（数据层 §4.1 那个缺陷的成因） |
| 3 | **构建须在工程根目录** | 本地仓库路径相对 CWD，否则依赖下错位置 |
| 4 | **数据库容器就绪顺序** | 应用启动即连库并跑 Flyway |
| 5 | **不用 `HttpSession`/`JSESSIONID`** | 契约要求 `Authorization: Bearer`；用容器会话会引入 cookie 语义与 CSRF 面 |
| 6 | **审计日志目录**（`-DAUDIT_LOG_PATH`）也应持久化 | 日志保留 3 个月（`C-18`、`12-P7`），落在容器可写层会随容器销毁 |

## 11. 下一轮（买家端 JSP）必须做的 5 件事

1. ⚠️ **口令码的格式判定必须先做**：`B11-09`／`M10-28`（「请输入 12 位口令码」）**不在** Service 的查询方法里
   （§3.3.5 明确「由调用方先调 `PasscodeService.isWellFormed`」）。**不先判格式，格式错的输入会退化成
   「口令不正确」（`B11-04`）**——安全但不精确。
2. **成功页用服务端转发（forward），不要重定向**：口令码只展示一次，重定向会让它出现在 URL 里（`K5-02`）。
3. **输出侧必须转义**：输入拒绝（拒 `<>`）是**第一层**，输出转义是**第二层**，两层**不可互补**
   （例如 `&lt;script&gt;` 里没有裸尖括号，输入层会放行）。
4. **时间要本地化**：服务端一律下发 UTC 带 `Z`，**UTC+8 由展示层转换**（`C-10`、`C-11`、已定 Q-11）。
5. **买家端失败用穷尽 `switch` 处理 `BuyerResult`**（`Ok`/`Rejected`）与 `PasscodeQueryResult`（三态）——
   它们是密封类型，**漏一个分支编译不过**，这正是当初把它们做成密封类型的原因。

> 另外：买家端**不需要鉴权拦截器**（凭证是口令码，`O-01`、`BR-32`）；`WebMvcConfig` 只对 `/api/seller/**` 注册了拦截器。

## B. 关键实现决策

1. **直接调 Service，不走 HTTP**。本阶段验证的是「归档后**每一列**是什么」，不是传输契约；
   直接调 `takeGoodsOffline()`／`markTradeSuccess()` 少一层噪声，而且能让「归档被拒 → 整体回滚」
   的断言直接落在**事务边界**上（走 HTTP 也能测，但那是在测别的东西）。
   ⚠️ 两条都仍是**真实业务入口**，没有绕过任何业务规则、也没有直接调 `archive()`。

2. **列集先断言「不多不少」，再逐列断言值**。
   两条路径都先 `assertThat(history.keySet()).containsExactlyInAnyOrderElementsOf(列集常量)`：
   这半句防的是「归档时多带/少带了一列」——而**只比对已知的几列是发现不了这种问题的**
   （§11.1 要求接口层不得引入未登记字段，历史表同理）。
   历史意向那 8 列的列集本身就是 `DEC-DB-05`／`9-S` 的断言（**没有** `queue_order` 与 `token`）。

3. **「1:1 继承」的 7 列用一个循环比对，5 个例外列逐条显式断言**。
   例外是：`status` 恒 `off_sale`、`freeze_by` 恒清空、`update_at` = 归档时间、
   `trade_end` = 调用方传入、`result` = `sold`/`offline`。
   这样注释与代码一一对应，且新增列时会立刻在「列集」那半句上失败。

4. **`update_at` 的核对必须先把原值推远**（否则测不出）。
   夹具造的商品 `create_at = update_at = now`，而归档发生在同一秒内——
   「`update_at` 是否复制了原值」根本不可判别。故用例先把商品的 `create_at`/`update_at`
   改成**一天前**，再断言「历史 `update_at` = `trade_end` **且 ≠ 一天前**」。

5. **「当前表 `result`/`trade_end` 恒 NULL」只有一个可观测窗口**：
   `markTradeFailure`（作废／重排队）——它是唯一一个「商品留在原表」的交易结果操作。
   `markTradeSuccess` 与 `takeGoodsOffline` 都会把当前行删掉，那时「有没有写过当前表的 `result`」
   已经无法观测（行没了）。故该断言只可能写在 `markTradeFailure` 之后，
   并同时断言 `trade_start` **有值**（说明「不是所有交易时间列都不写」，而是只有它写）。

6. **`INV-05` 的「整体回滚」用一条构造出来的脏状态来触发**（本阶段最强的一条用例）。
   正常流程下 `markTradeSuccess` 走到归档时已无活动意向——所以它的回滚分支**结构上不可达**。
   用例于是**故意违反 `INV-04`**：进交易后，再手工把第二条意向也置为 `trading`。
   此时归档会被 `INV-05` 拒绝，而**流水已经插入、状态已经改过**，于是这条用例成为
   「`I11-12` 必须整体一个事务」这句话唯一能被**观测**的证据：
   ```text
   归档被拒后必须成立的五件事（全部断言）：
     ① 已追加的那条流水 = 0 条      ← 核心
     ② 本次意向仍 trading（succeeded 未提交）
     ③ 连带失败也未提交
     ④ 商品仍 frozen + trade
     ⑤ 当前表未清空、历史表零行
   ```

## D. S7 期间发现并处理的问题

1. **⚠️ 口径事实（写给 S8）：同一秒内的多次交易，`trade_start` 相同 ⇒ 按它排序的结果不确定**。
   本用例第一版把两次失败流水按 `order by trade_start asc` 断言成「第 1 条是 `requeued`、第 2 条是 `voided`」，
   **单独跑这个类时通过，全量跑时失败**（`fail_type` 期望 `requeued` 实得 `voided`）——一个典型的偶发绿/偶发红。

   **机制**：`simpleshop_trade_history.trade_start` 是 `datetime`（**秒**精度，V1 脚本，未带 `(3)`）。
   两次 `enterTrade` 相隔毫秒 ⇒ 两行的 `trade_start` **完全相同** ⇒ `order by trade_start asc`
   对这些行**没有确定的顺序**（InnoDB 小表上通常返回插入顺序，所以第一次跑看起来是对的）。

   **影响面**（都不在本阶段，但都会真的遇到）：
   - `TradeHistoryRepository.findByIntentionIdOrderByTradeStartAsc` 的注释写「按 `trade_start` 升序**即等于**交易发生顺序」——
     **只在两次交易落在不同秒时成立**；
   - `findFirstByIntentionIdOrderByTradeStartDesc`（「最后一条流水」）同理，同一秒内可能取错；
   - **S8 的 `I11-16` `trades[]`**：契约要求「N 次失败**逐条可见**」——**内容是确定的**，
     但「严格按时间先后排列」在同一秒内**给不出保证**。

   **处置**：① 本用例改为「断言两条都在、内容正确」（**不断言顺序**），并把这个事实写进用例注释；
   ② 在 §3.3.4（`getHistoryDetail` 的取数口径）加了风险提示，供 S8 实现时看到；
   ③ 登记为 **O-1**，并列进顶层 README 的 S8 待办。

   **若要严格时序**（本阶段**不做**，因为要动数据层）：把两列改成 `datetime(3)` 需要**新增迁移脚本**
   （改 V1/V2 会致 Flyway 校验和失配——附录 B），属数据层变更，须单独走评审。
   **代价评估**：真实场景下「同一秒内对同一意向做两次交易结果」需要一个卖家在同一秒里点两次
   （每次都要经过「进入交易 → 标记失败」两个动作），概率极低；而需求（`§10.4.5 P10-09`）要的是
   **「每一次失败都能查到」**，不是「严格时序」。故**接受现状 + 登记**，不改。

2. **两处注释「过度声称」的校正（代码注释与文档）**：
   - `ArchiveService` 原写「只 `save` 不 flush 也不行——Hibernate 会自行重排 INSERT 顺序，照样撞外键」。
     **实测不成立**（变异 #3：换成 `save`、顺序不变 → 10/10 通过）。
     已在代码与 §3.3.6 改成准确说法：`saveAndFlush` 的价值是**不依赖** Hibernate 的内部 INSERT 排序，
     是**显式保证**，而不是它能修掉某个已观测到的失败。
   - 同处的「`deleteAllInBatch` 会在提交时把旧行重新 INSERT 回去」也只是**预判**：
     实测（变异 #2）的实际症状是**更早**的 `TransientObjectException`（发生在随后删除商品的那次刷新）。
     根因相同、症状不同，已按实测改写。
   > 这两条都属于同一类**诚实性修正**：注释里的因果若没被验证过，就不该写得像已验证过。

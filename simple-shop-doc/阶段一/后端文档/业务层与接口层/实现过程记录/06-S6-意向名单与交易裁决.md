## B. 关键实现决策

1. **`markTradeFailure` 在「重新排队」分支把序号表行锁提到商品行锁【之前】**（风险 R3）。
   买家 `submitIntention` 的取锁顺序是「① 序号表、不锁商品」；若本方法先取商品行、再取序号表行，
   两条路径就构成**反向取锁**。因为 `disposal` **进入方法时即已知**，这把锁可以安全地提前——
   不需要先做任何查询来判断「要不要排队」。
   > **⚠️ 一处与方案步骤编号的偏差（已在 §3.3.3 就地注明）**：§3.3.3 的编号把「取当前商品」列为第 1 步、
      「校验 `disposal`」列在第 2 步。实现按此顺序（**先 20002，再 30006/30007**），
      并把两步都放在**第一次取锁之前**——方案那句「必须在第一次触碰仓储之前完成」的**目的**
      （非法值不能走错分支）因此完全满足，而错误码的出现顺序与方案一致。
   > **真实端口实测印证了这一点**：无商品 + `disposal=bogus` → `20002`；有商品但商品手动冻结 + `disposal=bogus` → `30006`。

2. **`markTradeSuccess` 的四步顺序**（`BR-03`）：其余 `queued` → `failed`+`sold_out` → 本次 → `succeeded` →
   **追加流水** → **最后归档**。
   - 先他人失败、再本人成功，保证归档时「名下所有意向均已终态」（`INV-05` 成立、`INV-06` 同时成立）。
   - **流水必须在 `archive` 之前追加**：归档会 `deleteAll` 掉当前意向行，之后才追加则事务内持久化上下文已混乱，
     且「流水归属的意向已不在当前表」难以自证。
   - **其余 `queued` 意向不追加流水**：`IS-04` 是「他人成交」的连带效果，不是「对该意向登记交易结果」；
     §9.7.2 明确流水写入时机只有「标记成功」「标记失败」两处。**全系统的流水写入点只有本类的这两个方法**
     （`ArchiveService` 一条都不追加，`enterTrade` 也不能追加——`trade_end` 尚无值，而它是 `NOT NULL`）。

3. **`freezeBy` 必须严格等于 `trade`（已定 Q-1）**，两个 `markTrade*` 共用一处校验。
   手动冻结的商品**必须先解冻**才能标记交易结果。该分支实际不可达
   （`trading` 意向只可能由 `enterTrade` 产生，而它要求 `on_sale` 并把 `freezeBy` 置为 `trade`），
   故它是**防御性断言**：真被触发说明存在另一条产生该组合的路径，属数据不一致，应拒绝而非继续。
   用 `20004` 而非新错误码（契约表里没有更贴切的编号，`§11.6.1` 又禁止擅自加码）。
   > **⚠️ 副作用（口径观察项 O-2）**：因此 `20004` 的 `message` 是 `product is not frozen`，
   > 而实际成因可能是「商品在售」或「商品被手动冻结」——文案只描述了前者。`message` 不构成契约（仅供 grep），
   > 故按方案原定的码执行、不改码；已登记供评审。

4. **`disposal` 按 `String` 收、在 Service 里判（Q-14）**，且**归一化为 `FailType`**、不另造 `TradeDisposal` 枚举。
   `FailType` 已有 `voided`／`requeued`，且它们**正是**要写进 `intentions.fail_type` 的值；
   再造一个平行枚举等于多维护一张「两个枚举一一对应」的映射表。`sold_out`／`revoked` 不在白名单内。

5. **`fail_reason` 允许换行、拒绝 `<>`**（与商品名／买家姓名相反，那两个不允许换行）。
   「允许换行」只意味着**不因换行而拒绝**；XSS 第一层照旧拒绝尖括号（`NFR-20`）。
   长度按**码点**计、超 300 → `30007`；空值收敛为 `null`（与商品描述同一口径，避免库里同时有 `''` 与 `NULL`）。

6. **没有抽公共的 `PageData<T>` 基类**（方案 §4.6.2 的草图里有）。
   响应 DTO 一律是 `record`，而 **record 不能被继承**——想复用四个分页字段就只剩
   「嵌套对象」（JSON 多一层，契约不符）或 `@JsonUnwrapped` 反射展开（正是 §4.6.4 反对的隐式拷贝）。
   代价只是**四行字段声明**，收益是每份响应 DTO 都能被一眼核对完。若日后出现第三个分页接口再抽不迟。

7. **`enterTrade` 里 `30003`／`30004` 的「可测性」**：`30004` 看似不可达，实为**可用违反 `INV-04` 的夹具真测**
   ——构造「在售却有 `trading` 意向」（`ShopFixtures` 的正当用途），此时队首校验通过、`INV-02` 计数命中 → `30004`，已写进用例表。
   而 `30003` 在 `enterTrade` 中**确实不可达**：队首是按 `queued` 查出来的，`findByIdForUpdate(队首 id)` 必然拿回同一条 `queued` 意向；
   且「不属于当前商品」在单商品模型下也不可能出现。故它是**纯防御**，本阶段**不伪造用例**去覆盖它（诚实登记，见 E-4）。

8. **用例表的 `goodsSetup=trade` 通过真实 `I11-11` 造状态，而不是直接插库**。
   「交易冻结」只能由 `enterTrade` 产生，且它会**同时**写入 `goods.trade_start`——
   而 `trade_start` 是追加流水时 `NOT NULL` 的必填列。用 JDBC 伪造 `frozen+trade` 会让后续断言
   以一条与业务无关的 `NOT NULL` 约束错误失败。（需要 `frozen+manual` 的用例仍直接插库，那是「卖家手动冻结」的真实产物，
   且这些用例都在触碰流水之前就被 `20004` 拒绝。）

## D. S6 期间发现并处理的问题

1. **⚠️ 缺陷：Controller <u>方法参数</u>上的约束注解不通过时会返回 `500`**（新增处理器）。
   Spring Framework 6.1 起，`@RequestParam` 上的 `jakarta.validation` 约束由**内建的方法校验**执行
   （**不需要**在类上加 `@Validated`），失败时抛 `HandlerMethodValidationException`。
   而本类还有一个**兜底的** `@ExceptionHandler(Exception.class)`（契约要求未预料异常一律 `50000`+500），
   于是它落到兜底分支，被翻译成 **500 + `50000`**。

   ```
   实测（真实端口，未加处理器时）：
     GET /api/seller/product/intentions?page=0            → 500  （应为 400 + 50002）
     GET /api/seller/product/intentions?page_size=101     → 500
     GET /api/seller/intention/passcode?intention_id=     → 500
   服务端日志：org.springframework.web.method.annotation.HandlerMethodValidationException:
               400 BAD_REQUEST "Validation failure"
   ```

   这与 S3 发现的「媒体类型协商失败」是**同一类缺陷**：异常**自己就带着 400 的语义**
   （Spring 默认会渲染成 400），却被我们的兜底分支改写成 500——
   **客户端把请求写错，却被报成服务端内部错误**，既误导排查方向，又污染 500 的监控告警。
   **修复**：新增处理器 → `400` + `50002`（`11.3.4` 对 400 的定义正是「参数格式错误」，
   而前端必须拿到它已持有文案映射的码）。
   > **二次修正**：首个版本的处理器用 `MethodParameter#getParameterName()`，报出的是 **Java 形参名**
   > （`pageSize`），而 Spring 自己的处理器用的是**线上名**（`invalid parameter: page_size`）——
   > 同一个类里两种叫法。已改为优先读 `@RequestParam(name = ...)`，与
   > `missing parameter: intention_id` / `invalid parameter: page_size` 统一。
   > （`message` 不构成契约，但它是给人 grep 的，用客户端看得见的名字才有用。）

2. **⚠️ 测试夹具破坏了 `QueueSequence` 的不变量，会让「重新排队」撞唯一索引**（修复夹具）。
   `QueueSequence` 的口径是「`currentValue` = **已分配的最大** `queue_order`，只增不减」。
   而 `ShopFixtures` 直接写库造数时，序号表仍是 0——于是被测代码一旦走「重新排队」分支
   （`current_value + 1` 当新序号），分到的就是 `1`，与夹具已造出的 `queue_order = 1` **撞唯一索引**，
   用例会以一个与被测逻辑无关的 `Duplicate entry` 失败。
   **修复**：`insertIntention`／`insertIntentions` 造数后同步 `current_value`。
   这不是「顺手加保险」——夹具原本就在制造一个**真实流程不可能出现的状态**，
   而 S6 恰好是第一个依赖该不变量的阶段。

3. **断言用例自己写错过一次：标记成功会把当前表清空**。
   `markSuccessCases` 起初只用 `intentionRow(id)`（查当前表）断言目标意向的最终状态，
   而 `I11-12` 在**同一事务内归档**——行已搬到历史表，于是报
   `Incorrect result size: expected 1, actual 0`。已改为「先查当前表、再查历史表」的 `intentionRowAnywhere`。
   > 这条值得记：**「标记成功」是唯一会把自己断言的对象搬走的接口**，
   > 写它的用例时必须意识到「读哪张表」随成功/失败而不同。

4. **过度设计清理（用户指定）**：删除 `BuyerPromptTest`，并同步收缩它赖以为生的枚举元数据。
   - **删测试的理由（用户的判据，已写进 `BuyerPrompt` 的类注释）**：文案的唯一权威是第 10 章 §10.5
     《提示文案表》。把它的原文**再抄一份**进测试，等于制造**第二个权威**——改文案要同时改两处，
     而测试里的那一份**不会**因此更可靠；「哪几条是【必须】」属**验收口径**（`AC-28`），
     对着 §10.5 走查即可判定，编码成枚举字段 + 断言只会让需求改一个字就误报红灯。
   - **连带清理的**：`docs()`／`upstream()`／`mandatory()` 三个访问器**只被那个测试使用**，
     删测试后它们就是**没有读取方的生产代码**。溯源信息（`M10-xx`／`B11-xx`／`【必须】`）
     改以**注释**形式写在每个常量上——给人看，不给构建看。类注释里关于「买家端不用 `ErrorCode`」、
     「`B11-xx` 编号撞车」的说明**全部保留**（那是评审会用到的信息）。
   - **同类清理**：`PasscodeQueryResultTest.expiredTextRevealsNothing` 去掉
     `isEqualTo("该口令码已失效")` 的等值断言，保留 `doesNotContain("售出","成功","失败","撤销",...)` 的**否定**断言
     ——后者守的是 `BR-29`（失效不泄漏结果），不是「文案必须是什么」。
   - **⚠️ 刻意保留的**：`PasscodeQueryResultTest` 里三条**检查 record 组件清单**的用例（反射）。
     它们不是「规定文案」，而是 `BR-29`（失效不返回买家信息）在**类型层**的唯一防线——
     若有人给 `Expired` 加一个 `status` 字段，没有任何**行为**用例会失败。判据是
     「它守的是不是一条**无法用行为断言表达**的约束」，而不是「它看起来像不像设计测试」。

5. **真实端口冒烟污染了共享测试库，打挂了数据层用例**（已记录，未改代码）。
   冒烟在 `simple_shop_test` 上发布了一件商品且未清理，随后 `mvn clean verify` 中
   `InvariantAndConcurrencyTest.inv01_atMostOneActiveGoods` 失败：
   `existsByStatusIn({on_sale, frozen})` 断言「测试开始时表内无在售/冻结商品」，而该行还在。
   （`DataLayerTestBase` 会清业务表，但这条断言**依赖**清理确实发生过——它测的正是「此刻没有」。
   最终仍是通过后续 `Seller*ApiTest` 的 `@BeforeEach` 清理恢复的。）
   > **处置**：本阶段不改测试（那是数据层交付物，附录 B），但把结论写在这里：
   > **对 `simple_shop_test` 的真实端口冒烟必须在结束时清理数据**，否则会以「与 S6 无关的失败」
   > 打挂整轮构建。下一次冒烟建议指向**独立库**（如 `simple_shop_smoke`，`createDatabaseIfNotExist=true` + Flyway 可自建）。

## B. 关键实现决策

1. **性能用例直接调 Service，不测 HTTP；查询用 P95，不可重复的写只报单次样本。**
   - 直接调 Service：MockMvc／容器的开销与本阶段要测的「SQL 规模」无关，混进来只会掩盖信号。
   - 查询可重复（同一份数据反复读）→ 预热 10 次后取 **30 个样本的 P95**。
   - **写大多不可重复**（状态机单向），故只挑两对天然可循环的（冻结⇄解冻、进入交易→标记失败重排队）测 P95；
     归档整队列这种「一次点击把商品搬走」的写**只能取一次样本**——与其用几个样本假装成 P95，
     不如**只报实测值并说清波动范围**（实测同配置在不同运行间可从 1.7s 漂到 2.8s）。

2. **新增 `hibernate.jdbc.batch_size: 50`——本阶段唯一的生产改动，且它是被实测逼出来的。**
   - 不设时 Hibernate 的批处理大小默认为 **0（关闭）**，归档 1000 条意向会发 1000 条 INSERT。
   - 设置后**用 MySQL 自己的语句计数器验证**（`SHOW GLOBAL STATUS LIKE 'Com_insert'`）：
     归档 1000 条 → **`Com_insert` 增量 = 21**（≈ 1000/50 + 1），即确实被改写成多值语句；
     未设时同样的归档接近 1000。
   - ⚠️ 本项**只影响性能、不影响语义**：单行写入（发布、提交意向）本就无批可批；
     归档的插入顺序由 `saveAndFlush(历史商品)` 单独落定，与历史意向不在同一次 flush 中。

3. **⚠️ 性能判据优先用「结构性事实」，而不是绝对时间。**
   本阶段的教训是：绝对时间在**同一台机器**上都会漂（单跑 vs 全量跑差 50% 以上）。
   故最终保留两条**不随机器漂**的判据：
   - **结构性**：归档 1000 条的 `Com_insert` 增量必须 ≤ 25（关掉 `batch_size` 会涨到 ~1000）；
   - **数量级**：归档整队列 ≤ 5000ms（只拦灾难性退化，例如把取数写成 O(N²)）。
   <p>而 §8.4 的 **1s 指标**在「归档整队列」这一项上**达不到**——它没有被放宽成一条看不出问题的断言，
   而是**登记为偏差**（§D-1／O-1）。

4. **§8.3 的覆盖矩阵（§C）是「逐条对账」的产物，不是「罗列测试类」。**
   对照时按 §8.3 的四个小节（不变量／状态机、校验与错误码、会话与鉴权、归档与时间、口令码、历史接口、JSON 契约、归档流水并发）
   逐条找「哪个用例断言了它」；找不到的才补。**结果是只有 2 处真缺口**（C-2）——
   这说明前九个阶段的用例是围绕 §8.3 长出来的，而不是随手写的。

## D. S10 期间发现并处理的问题

1. **⚠️⚠️ 最重要的一条：`12-P1` 的写在「归档整队列」上的口径与裁定（结论：按「整体 P95」判定 ⇒ 达标）。**
   - **实测**：把满队列（1000 条）整批归档时，`I11-09`（手动下架）约 **1.7~2.2s**、
     `I11-12`（标记成功）约 **1.9~2.8s**，而 `§8.4`／`12-P1`（由 **`AC-27`** 验收）要求写操作 **P95 ≤ 1s**。
   - **成因（实测锁定，非猜测）**：整个代价集中在**删除阶段**，而 **Hibernate 6.6 不批处理这批 DELETE**。
     证据是 MySQL 自己的计数器：归档 1000 条时 `Com_insert` 增量 = **21**（≈1000/50+1，插入**已**批处理），
     而 `Com_delete` 增量 = **1001**（= 行数 + 1，删除**逐行**执行）。
     规模曲线也吻合：10→67ms、100→286ms、300→659ms、1000→1561ms，**线性、约 1.5ms/条**。
     ⚠️ 试过 `hibernate.order_updates: true`——**无效**（`Com_delete` 仍是 1001），故已回退不加该配置。
   - **影响面**：只有**这两条**路径（都在同一个事务里搬走整队列）。
     其余写的 P95 是 32~59ms（余量 17~31 倍）；查询类 P95 ≤ 150ms（余量 3~45 倍）。
     而且「1000 条」是**队列上限**（`NFR-07`）——最坏情况，不是典型值（典型归档是几条到几十条）。
   - **可选的修法（本阶段【未】实施，属评审决策）**：把归档末尾的删除改成**批量 SQL**
     （一条 `delete from simpleshop_intentions where fk_good_id = ?` + 一条删商品），
     预期可把两条路径拉到 **0.3~0.5s**（删除从 1000 条语句变成 2 条）。
     **代价**：① 要绕开持久化上下文，而 `ArchiveService` 的类注释专门警告过这条路上的坑
     （`deleteAllInBatch` → `TransientObjectException`，S7 已实测）；② 需要在数据层**新增**批量删除入口
     或在 Service 里直接用 `EntityManager`，属附录 B 要求「单独提出并评审」的改动；
     ③ 会**作废 S7 对归档顺序的验证**（那套保证正是建立在「逐实体删除」上的），必须重新验证。
   - **本阶段的处置**：**把实测数字与成因原样摆出来**，而不是把断言放宽成一条看不出问题的阈值；
     在此基础上由**业务方裁定口径**（本记录开头）：
     - **按「写请求整体的 P95」判定 ⇒ 达标**（归档是「一个商品生命周期一次」的操作，其绝对耗时经确认可接受）；
     - **不做**上面的批量删除优化——代价（绕开持久化上下文 + 动数据层入口 + 作废 S7 的顺序验证）大于收益；
     - 用例仍守两条与机器无关的判据（结构性 `Com_insert ≤ 25`、数量级 ≤ 5s）——
       **裁定的是指标口径，不是放弃护栏**。
     > 这与 §9 对 S10 的措辞一致：**「性能达标【或】记录偏差与优化结论」**；
     > ⚠️ 关键是**先把事实测准**（否则连"是否达标"都无从判定），再让**口径**由业务方定。

2. **自己写错了一次断言：用全表计数去核验「归档搬了多少」**。
   性能用例里我先写的是 `select count(*) from simpleshop_intentions_history` = 1000，
   但该用例的数据集**本来就含 100 条历史商品（545 条历史意向）**，实际得到 1545。
   已改成**限定本商品**（`where fk_goods_history_id = ?`）。
   > 这已经是同一个坑的第三次（S7 归档 → S6 冒烟残留 → 本次）：**全表计数只在「表里只有我的数据」时才对**。
   > 写这类断言时的一秒钟自问「现在表里还有别人的东西吗」值得养成习惯。

3. **一次「以为是批处理没生效、其实是断言错了」的排查（过程值得记）**。
   首次实测时我用「SQL 日志里 `insert into …` 出现 1000 次」判断批处理没生效——
   这个判据本身是错的：**Hibernate 在批处理模式下也会逐行记录语句**，
   日志条数根本分辨不出批处理。改用 MySQL 的 `Com_insert`／`Com_delete` 计数后才看清真相：
   **插入批了、删除没批**。教训：**日志条数不是并发/批量行为的判据，计数器才是。**

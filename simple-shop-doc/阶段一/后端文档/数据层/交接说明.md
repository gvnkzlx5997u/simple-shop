### 2.1 ⚠️ 关于「必须在工程根目录执行 mvn」（实测确认）

`.mvn/maven.config` 里的 `-Dmaven.repo.local=.m2/repository` 是**相对路径**，Maven 按**当前工作目录**解析它。实测：

| 调用方式 | 实际使用的本地仓库 |
| --- | --- |
| `cd simple-shop-backend && mvn ...` | ✅ `simple-shop-backend/.m2/repository`（正确） |
| 在别处 `mvn -f simple-shop-backend/pom.xml ...` | ❌ `<当前目录>/.m2/repository`（**会另外下载一份**） |

因此：**统一在工程根目录执行 mvn**；若确实需要在别处调用，请显式指定 `-Dmaven.repo.local=<绝对路径>`。

### 2.2 项目内已核对的「非环境相关」配置（属正常设计，不要误删）

| 项 | 说明 |

## 4. 实体层的实现要点（代码里看不出「为什么」的部分）

### 4.1 ⚠️ 最重要的一条：时间字段必须标注 `@JdbcTypeCode(LOCAL_DATE_TIME)`

**不标会静默把时间写错 8 小时。** 这是本项目在自测阶段实测发现并修复的真实缺陷。

| 项 | 说明 |
| --- | --- |
| **问题** | Hibernate 6 对 `LocalDateTime` 的**默认**绑定走 `PreparedStatement.setTimestamp`，而 Connector/J 的 `setTimestamp` 会按**会话时区**把值解释并转换一次。开发机（JVM 时区 `Asia/Shanghai`、`connectionTimeZone=UTC`）上实测：应用写入 `11:33:19`（UTC），**库中落成 `03:33:19`** |
| **为什么配置救不了** | `hibernate.jdbc.time_zone=UTC` 只决定「传哪个时区给它」，**改变不了「会被解释一次」** |
| **正确做法** | 每个 `LocalDateTime` 字段标注 `@JdbcTypeCode(SqlTypes.LOCAL_DATE_TIME)`，强制走 `setObject`/`getObject`（不做时区转换）。**当前 15 个时间字段全部已标注** |
| **注解位置** | 该注解 `@Target({FIELD, METHOD})`，**不能标在 `package-info.java` 上**（实测无法编译），只能逐字段标 |
| **维护要求** | **新增时间字段时必须一并标注**，否则该字段会静默偏 8 小时，且 `validate` 查不出来 |
| **为什么 validate 查不出来** | `ddl-auto=validate` 只校验「表/列/类型/可空性」，**不校验数据值**。这类问题只能靠「写入后直接查库比对」的集成测试发现 |

### 4.2 主键

- 形态：`<前缀> + 标准 UUID`，列宽 `varchar(50)`。前缀：商品 `G`｜意向 `I`｜历史商品 `GH`｜历史意向 `IH`｜流水 `TH`｜账号 `U`。
- 赋值：各实体在 `@PrePersist` 中 **`if (id == null)`** 才生成。
- **⚠️ 这个 `if` 是硬约束**：归档时历史行要**沿用原 ID**、由调用方显式赋原值。写成无条件赋值会让归档产生新 ID，直接违反 `9-G`。
- 时间列一律 `datetime`（不是 `timestamp`），值由应用层按 UTC 写入。

### 4.3 枚举

- 6 个枚举，取值即库中代码（`on_sale`、`queued`、`sold_out`…），配合 `@Enumerated(EnumType.STRING)` 使落库值与字典**逐字一致**。
- **⚠️ 不要改成驼峰**（如 `onSale`）：命名策略只作用于表名/列名，**不影响枚举值**，改成驼峰会存错。
- 携带只读元数据：`label`（中文名，仅界面/文档用）、`terminal`、`tokenValid`、`revocable`、`auto`、`buyerVisible`。
- **`tokenValid` 严格等于 `!isTerminal()`**——这是口令码有效性的**唯一**判定式，**不得**把「商品是否下架」混进去。

### 4.4 关联与等价性

- 关联一律 `FetchType.LAZY`，**不级联**（`CascadeType = {}`），**不建 `@OneToMany` 反向集合**。
- 外键列名不规则（`fk_good_id` 是**单数** `good`），必须用 `@JoinColumn(name = "...")` 显式声明，不能靠推断。
- `TradeHistory.intentionId` 映射为**普通 `String` 列**，**不映射 `@ManyToOne`**：该列刻意无物理外键，且目标可能是当前意向表或历史意向表，映射成关联会在归档瞬间产生「悬空引用」。
- `equals`/`hashCode` 按 `id`；`id == null` 时退化为对象同一性。
- **`toString` 不得输出口令码与密码**：`Intention`、`IntentionHistory`、`TradeHistory`、`ShopUser` 均已遵守（日志泄漏防护）。
- `QueueSequence.id` 是 `Integer` 但列类型是 `tinyint`，故显式标注 `@JdbcTypeCode(SqlTypes.TINYINT)`，否则 `validate` 会报 `wrong column type ... found [tinyint], but expecting [integer]`。

### 4.5 时间回调的分工（易错）

| 实体 | 回调 | 原因 |
| --- | --- | --- |
| `Goods`、`ShopUser` | `@PrePersist` + `@PreUpdate` | `createAt` 一次性写，`updateAt` 每次更新刷新 |
| `Intention` | **只有 `@PrePersist`，无 `@PreUpdate`** | `createAt` 是「原始提交时间」，重排队与改姓名电话**都不得变更** |
| `TradeHistory` | 只有 `@PrePersist`（写 `id` 与 `createAt`） | `tradeStart`/`tradeEnd` 由业务显式赋值 |
| `GoodsHistory`、`IntentionHistory` | **一条回调都没有** | 归档是**数据搬迁**，时间列必须**继承原值**；挂了 `@PreUpdate` 会让二次保存覆盖归档时间 |
| `QueueSequence` | 无 | 无时间字段，ID 是固定常量 1 |

> `ShopUser.updateAt` 语义是「密码最后修改时间」，当前实体只有 `password` 一个可变字段，用 `@PreUpdate` 与「仅改密时更新」等价（`DEC-DB-10`）。**若将来新增可变字段，必须改为显式赋值**，否则无关字段的更新会带动该列。

## 5. 仓储层与加锁契约（Service 层必读）

### 5.1 仓储清单要点

| 仓储 | 要点 |
| --- | --- |
| `GoodsRepository` | **不提供**任何改商品名称/描述/图片/价格的方法。这是「发布后不可修改」（`BR-15`）的第二道防线——实体保留 setter（JPA 与归档复制需要），但仓储不开任何入口 |
| `IntentionRepository` | 位次 = `countQueuedAhead` + 1；撤销后位次自动前移（位次是**计数派生**，不需要额外的「前移」SQL） |
| `GoodsHistoryRepository` | **只提供**按 `trade_end` 倒序一种排序，不提供按 `createAt`/`id` 排序的重载，避免调用处选错 |
| `IntentionHistoryRepository` | 历史名单按 **`create_at`** 升序（该表已无 `queue_order` 列） |
| `TradeHistoryRepository` | **不提供任何 delete/update**（流水只追加）；单条计数 `countByIntentionId` 与批量分组 `countGroupedByIntentionIdIn` **两种都提供，由 Service 按数据量选择** |
| `ShopUserRepository` | 不提供按账号+密码查询（库中是不可逆哈希，比对在 Service 做）；无删除入口（账号永久保留） |
| `QueueSequenceRepository` | 主键是 `Integer`（单行辅助表，唯一不是 `JpaRepository<T, String>` 的仓储） |

### 5.2 ⚠️ 加锁契约（§8）

| 锁 | 方法 | 什么场景用 |
| --- | --- | --- |
| 序号表行锁 | `QueueSequenceRepository.findByIdForUpdate(1)` | 提交意向时分配序号 |
| 商品行锁 | `GoodsRepository.findByIdForUpdate(id)` | 进入交易、标记交易结果、手动冻结/解冻、手动下架 |
| 意向行锁 | `IntentionRepository.findByIdForUpdate(id)`<br>`IntentionRepository.findByTokenForUpdate(token)` | 卖家登记交易结果；买家凭口令码撤销/改信息 |

**三条硬性约定：**

1. **统一加锁顺序：① 序号表行 → ② 商品行 → ③ 意向行**（防死锁）。不同事务以不同顺序取同一批锁会死锁。
2. 凡**改变商品状态**或**改变「是否有意向处于 `trading`」**的事务，**必须首先**锁商品行。
   （提交意向 `IS-01` 与买家撤销 `IS-03` **不需要**锁商品行。）
3. **所有 `...ForUpdate` 必须在事务内调用**。脱离事务时 `SELECT ... FOR UPDATE` 的行锁会立即释放，保护形同虚设——Service 方法必须带 `@Transactional`。

> **为什么必须用行锁而不是「条件 UPDATE 抢占」**：`INV-02` 要求「同一商品至多 1 条 `trading`」。
> 用 `UPDATE ... WHERE id=? AND status='queued'` 抢占只能防「同一条意向被进入交易两次」，
> **防不住「两条不同意向同时进入交易」**（两条 UPDATE 都会成功）。必须用商品行锁把二者串行化。
>
> **为什么不用乐观锁 `@Version`**：状态迁移的前置校验依赖「读到的当前状态」，
> 乐观锁冲突后要重试整个业务判断；商品表全局仅 1 行，行锁串行化代价可忽略。字典也没有 `version` 列。

### 5.3 序号分配契约

```
事务内:
  1. seq = queueSequenceRepository.findByIdForUpdate(1)   // 行锁：并发事务在此排队
  2. next = seq.getCurrentValue() + 1
  3. seq.setCurrentValue(next)
  4. save(seq)
  5. intention.setQueueOrder(next)
  → 提交：行锁释放，下一个事务拿到 next+1
```

保证：序号单调递增、互不重复（`uk_intention_queue_order` 是第二道防线）、**不丢单**（后到者排队等待而非失败）、不依赖意向表范围锁。

## 6. 归档（Service 层要实现的事务）

归档是**跨表业务事务**，属 Service；数据层只提供实体与仓储。口径如下：

1. **同一事务内**「写历史表 → 删当前表」。
2. **归档前必须校验 `INV-05`**：调用 `countActiveByGoodsId(goodsId, {queued, trading})`，返回值 **> 0 即拒绝归档**。
3. 归档时的列对应关系：
   - 历史商品：与商品表字段 **1:1 同名同类型**；差异是 `status` 恒写 `off_sale`、`freeze_by` 恒清空、`trade_end`/`result` 变必填。
   - 历史意向：`id`、`create_at`、`name`、`tel`、`status`、`fail_type`、`fail_reason` **逐列复制**；`fk_good_id` → `fk_goods_history_id`（**值不变**）；**`queue_order` 与 `token` 不复制**（该表根本没有这两列）。
   - 历史实体的 **ID 沿用原值**（前缀仍为 `G`/`I`，前缀表示「实体来源类型」，不表示当前所在表）。
   - 历史实体的时间列**必须继承原值**，不要依赖回调（历史实体没有回调，见 §4.5）。

> **`INV-05` 没有数据库级兜底**：原本的 `ck_intention_history_status_terminal` 已按 `DEC-DB-14` 删除，
> 因此它**完全依赖应用层归档前置校验 + 集成测试断言**
> （`IntentionHistoryRepository.countActive({queued, trading})` 应恒为 0，这就是那唯一的事后观测手段）。

## 7. 校验责任边界（重要，避免重复实现）

| 层 | 负责什么 |
| --- | --- |
| **数据库** | 只管「结构对不对」：`NOT NULL`、`UNIQUE`、`FOREIGN KEY`、以及**纯物理性**的时间先后 CHECK（共 4 条） |
| **JPA `@Column`** | 列名、长度、精度、可空性（用于 Hibernate 校验与结构对照） |
| **应用层（Service）** | 「值对不对」**全部**归这里：枚举取值、数值区间（价格）、格式（口令码 `[A-Z0-9]{12}`、电话）、文本规则（拒绝 `<`/`>`、禁止首尾空格、换行）、长度上限、跨表不变量（`INV-01/02/05/06`）、队列上限 1000、状态迁移合法性 |

一句话：**数据库只管结构，不管值。** 客户端的非法值不要指望数据库兜底——它不会拦。

**Service 层不得依赖的项：**

| 项 | 原因 |
| --- | --- |
| `Goods.result` | 该列在本表**恒为 NULL**（值只在归档时写到历史商品表）。任何界面/接口都不得读它 |

## 8. 时间口径（强约束）

- 库内所有 `datetime` 一律为 **UTC**。
- **全项目禁止**直接使用 `LocalDateTime.now()`／`new Date()`／`System.currentTimeMillis()` 入库——它们取本机时区。
- 唯一时间来源：`com.simpleshop.persistence.time.DatabaseTimeProvider`
  - 业务代码（Service）：注入后调用 `nowUtc()`
  - JPA 生命周期回调：`DatabaseTimeProvider.utcNow()`（静态，回调里无法依赖注入）
- **UTC+8 的展示转换不在数据层**，由应用层/前端完成。
- 另见 §4.1：时间字段必须标注 `@JdbcTypeCode(SqlTypes.LOCAL_DATE_TIME)`。

## 9. 初始化数据与账号口令

`V2__seed_initial_data.sql` 幂等写入两项（重复执行不产生第 2 行）：

| 数据 | 内容 |
| --- | --- |

时间列用 `UTC_TIMESTAMP()` 写入（**不用** `NOW()`，后者取会话时区会写成 UTC+8）。

### 9.1 初始账号

| 项 | 值 |
| --- | --- |
| 登录账号 | `seller` |
| 初始口令 | `Abcd@1234` |
| 库中存储 | BCrypt 哈希（强度 10，60 字符），**脚本中无任何明文** |

> **⚠️ 已知取舍（需让评审看到）**：初始口令是**约定的固定值**——否则交付后无人能登录。
> 因此「库里只存哈希」满足的是「**不存明文**」，**不能**提供保密性：能读到本仓库/本文档的人都知道它。
> 缓解措施：① 首次登录后**立即改密**；② 上线前换成只有运维知道的口令。

### 9.2 改密方式

口令不以明文入库，所以**不能**直接 `UPDATE ... SET password = '新口令'`，必须先转成 BCrypt 哈希。
工具：[`PasswordHasher`](simple-shop-backend/src/main/java/com/simpleshop/security/PasswordHasher.java)（应用层用）与
[`PasswordHashTool`](simple-shop-backend/src/main/java/com/simpleshop/security/PasswordHashTool.java)（命令行用）。

**方式 A：运维直接改库（立即生效，推荐）**

```bash
cd simple-shop
mvn -q compile
mvn -q dependency:build-classpath -Dmdep.outputFile=target/cp.txt
# Windows（classpath 分隔符为 ';'）：
java -cp "target/classes;$(cat target/cp.txt)" src/main/java/com/simpleshop/security/PasswordHashTool.java gen
# Linux/macOS（分隔符为 ':'）：
java -cp "target/classes:$(cat target/cp.txt)" src/main/java/com/simpleshop/security/PasswordHashTool.java gen
```

不带参数时**交互式输入且不回显**（需输两次），工具会直接打印可执行的 `UPDATE` 语句：

```sql
UPDATE simpleshop_users
   SET password  = '<工具输出的 BCrypt 哈希>',
       update_at = UTC_TIMESTAMP()      -- ⚠️ 必须用 UTC，不能用 NOW()
 WHERE account = 'seller';
```

**方式 B：改种子脚本（重建库时生效）**

把 `V2__seed_initial_data.sql` 里的 `password` 字面量换成新哈希。
⚠️ 已发布的迁移脚本**不应修改**；库已上线时请**新增** `V3__update_seller_password.sql`，
不要改 V2（改了会导致 Flyway 校验和失配、启动直接报错）。

**校验口令与库中哈希是否匹配**（排查登录失败）：

```bash
java -cp "target/classes:$(cat target/cp.txt)" src/main/java/com/simpleshop/security/PasswordHashTool.java verify '<库中的哈希>'
```

**Service 层怎么用**：登录调用 `PasswordHasher.matches(明文, 库中哈希)`；
改密调用 `PasswordHasher.hash(新明文)`。都是静态方法，无需注入。

> `PasswordHashTool gen` 若在命令行直接传明文（`gen 明文`），该明文会进入 shell 历史与进程列表；
> 不带参数时走交互式不回显输入，推荐后者。

### 10.1 怎么跑


### 10.2 测试跑在独立库，不碰开发数据

### 10.3 用例构成（24 个）

| 测试类 | 用例数 | 覆盖 |
| --- | --- | --- |
| `StructureAndUniqueConstraintTest` | 12 | 表/列/索引/约束结构核对；`token`、`queue_order`、`account`、主键重复插入被拒；空密码被 CHECK 拒绝 |
| `InvariantAndConcurrencyTest` | 6 | `INV-01`、`INV-02`（含行锁契约路径）、`INV-05`、`INV-06`、`INV-08`；**并发提交 10 条序号不重复** |
| `ArchiveAndUtcTest` | 6 | 归档字段逐列核对、历史表无 `queue_order`/`token`、历史时间列不被回调覆盖、**UTC 写入校验**、口令码哈希回归 |

### 10.4 写测试时要注意的几件事

1. **数据清理的陷阱**：`simpleshop_trade_history.fk_intention_id` **刻意没有物理外键**（`9-N`），
   所以**删除意向不会连带删除流水**。清理时必须显式删「FK 指向本测试意向的流水」，
   且不能用 `like 'DLT-%'` 去匹配流水 id——流水 id 由 Hibernate 生成、前缀是 `TH`，不带测试标记。
   （基类 `DataLayerTestBase.cleanTestData()` 已处理，并有实测：连续跑多次 `mvn verify`，测试库零残留。）
2. **并发用例不能加类级 `@Transactional`**：每个线程必须持有各自**独立**的真实事务，
   否则 `SELECT ... FOR UPDATE` 无法真正并发（同事务内重入不阻塞），测试就失去意义。
   该用例用线程池 + `CountDownLatch` 同时放行 10 个线程，各自在 `TransactionTemplate` 内按 §5.2 的加锁顺序分配序号。
3. **不要用 `rs.getTimestamp().toLocalDateTime()` 校验 UTC**：`getTimestamp` 会按驱动/JVM 时区再解释一次，
   在 UTC+8 机器上读出来会差 8 小时，让人误判。应按字面值读：`rs.getObject(col, LocalDateTime.class)`。
4. **断言「被数据库拒绝」时不要写死异常类型**：约束失败向上冒泡可能是
   `DataIntegrityViolationException`，也可能是 `JpaSystemException`，取决于失败发生在 persist 还是 flush 阶段。
   基类提供了 `assertRejectedByDatabase(action, 约束名)`，它同时校验「确实被拒」**和**「是哪条约束拒的」。
5. **JPA `save()` 对已存在主键会退化为 `merge`（upsert）**：想验「数据库主键冲突」必须用原生 `INSERT`，
   用 `saveAndFlush` 是验不出来的。
6. **`information_schema` 的返回顺序在平台间不稳定**：断言索引/约束集合时用顺序无关的比较（`containsExactlyInAnyOrder`），
   别把 Windows/MySQL 的排序行为写成断言。

### 10.5 自测阶段实测发现的问题（供参考，避免重复踩）

| # | 问题 | 定位与结论 |
| --- | --- | --- |
| 1 | **UTC 偏移 8 小时**（最严重） | 见 §4.1。`setTimestamp` 会按会话时区解释，Hibernate 默认就用它；已用 `@JdbcTypeCode(LOCAL_DATE_TIME)` 修复。`validate` 查不出这类**值**错误，只能靠「写入后查库比对」的测试发现 |
| 2 | `QueueSequence.id` 校验失败 | `tinyint` 列 vs Java `Integer` 默认映射为 `integer`；已加 `@JdbcTypeCode(SqlTypes.TINYINT)` |
| 3 | Mockito 无法初始化 | 本机禁用 JVM agent 自附加；已在 pom 中显式注入 `byte-buddy-agent` |
| 4 | 连接串 `characterEncoding=utf8mb4` 被驱动拒绝 | 该参数取的是 **Java 字符集名**，`utf8mb4` 是 MySQL 字符集名；已改为 `UTF-8`（并加 `connectionCollation=utf8mb4_unicode_ci` 落实排序规则） |
| 5 | 主键冲突用例验不到数据库 | JPA `save()` 对已存在主键走 `merge`；改用原生 `INSERT` |
| 6 | 测试库残留流水行 | 见 §10.4 第 1 条 |
| 7 | 构建 JDK 限制过严（交接前核对时发现） | 原 enforcer 规则要求 JDK 必须**恰好为 21**。这会把「开发机恰好装了 21」这一环境特征写进构建契约，妨碍换机与 CI。已放宽为**「≥ 21」**，并实测 JDK 24 也能构建、字节码仍为 Java 21、24 个测试全通过 |

# 需求澄清记录
针对挑战需求C，对用户进行提问，得到了以下需求澄清记录

## 问题1

### 问：
1. 订单创建后即进入"待支付"，是否设置支付时限？超时后由谁、以什么方式关闭订单？
2. 未支付期间是否占用库存？超时关闭订单时是否自动回补库存？
3. 银行卡、信用卡、支付宝、微信四种支付方式，系统是否需要分别记录支付渠道，还是 MVP 阶段统一走 Mock 接口、不区分渠道？
4. 已支付订单能否取消？取消后款项是原路退回还是线下处理，由谁触发退款？
5. 支付失败是否需要记录失败状态，还是仅提示用户、订单仍停留在"待支付"？
6. 订单进入"已支付"后，原有的"商家确认"环节是否仍然保留（即已支付 → 商家确认是否还要人工点击）？
7. "待支付"状态下客户和商家是否都能取消？原有取消规则（客户在开始发货前、商家在交易完成前）是否需要随之调整？
### 答：
1. 设了，24 小时。超时没付，系统自动把订单取消掉，库存也加回去。
2. 占用。下单的时候就把库存占住了，不够还不让下；超时取消就自动回补。
3. 四种支付方式都要支持，客户付款时自己选渠道；退款要原路退回，所以系统得记清楚客户当时用的哪个渠道。至于「统一走 Mock 接口」——那是怎么实现的事，超出需求范围，我不聊。
4. 能取消。已支付的订单取消，钱原路退回客户原来的支付渠道；谁取消就触发退款。商家在交易完成前也都能取消，已支付的同样退。
5. 不单独记「失败」状态。支付失败，订单就还停在「待支付」；超时了才自动取消。
6. 保留。已支付之后还是「商家确认」这一步，要卖家在后台手动点确认。
7. 待支付时，客户可以直接取消（没付款，不用退款）；商家在交易完成前都能取消，待支付也算在内。原规则要跟着调：客户这边现在要分两种——待支付直接取消不退款，已支付再取消就得走退款。

## 问题2
### 问：

2. 售后申请的粒度是"某件商品"还是"整张订单"？同一件商品能否重复申请？
3. 售后图片是否必填？最多几张、单张大小上限、支持哪些格式？
4. 售后状态包含哪几个（待处理、同意退货、已退货、已退款、已拒绝、已关闭）？
5. "商家线下与客户协商"是否需要在系统中留痕（例如拒绝理由、协商备注）？
6. "退货"与"退款"是二选一还是可以组合？只退款不退货是否允许？
7. 退款金额按商品单价计算，还是按实付金额（含运费、优惠）计算？
8. 退货入库后库存如何回补？售后期间订单状态保持不变，还是新增"售后中"状态？
9. 卖家能否拒绝售后？若允许，拒绝后客户能否再次申请售后？

### 答：
1. 哪些状态能申请售后、同一订单最多申请几次，我都没细定。
2. 粒度是「某件商品」，不是整张订单。同一件商品能不能重复申请，我没规定。
3. 图片是「可上传」的，不强制。几张、单张多大、支持什么格式，我没细规定。
4. 售后具体有哪些状态我没列那么细，结果就是退货、退款这些。
5. 不用留痕。协商是「线下」的，系统外面谈，拒绝理由、协商备注这些不进系统。
6. 不是二选一绑死。退款能单独发生——只退款、货不退。退货的话，货退回来商家确认后，再退款或者换货。
7. 我这个系统里本来就没有运费、优惠这些东西，订单总金额就是商品的钱。退款就按商品金额退（原路退回）。
8. 退货入库后库存加回来，每件 +1。订单状态不新增「售后中」，还是原来那几个状态。
9. 「拒绝」这个结果我都没明确列，拒绝之后客户能不能再申请，我也没规定。

## 问题4
### 问：
1. 退款由谁触发？
2. 待支付订单是否占用库存？
3. 下单时能否当场新建/编辑收货地址？
4. 物流状态来源？是否可以由商家手动更新，还是实时对接API？
5. 售后申请图片的限制？是否可以沿用商品图片规则（最多 9 张 / JPG·PNG / 单张 ≤5MB） ？
6. 申请售后时需要填写哪些字段？申请时是否允许选择类型（退货/退款/换货等）
7. 售后退款与取消订单退款是同一通道吗？
### 答：
1. 已支付订单取消即触发退款，售后退款单独走售后流程。
2. 下单即占用库存，取消才回补，不是支付成功才占用。
3. 下单时可以「选择」收货地址（默认自动带入、可切换），地址的维护（增删改、设默认）是单独的。下单只能选已有，新建/编辑去地址管理。
4. 功能上要求「客户可查发货后物流状态（物流单号 + 跟踪信息）」，但状态是手动维护还是对接物流商实时跟踪，需求没写。商家手动更新可以接受；对接顺丰等物流 API 实时跟踪属于技术实现，我不强求。
5. 需求里只说「可上传问题图片」，没写数量/格式/大小。你沿用商品图片规则（9 张 / JPG·PNG / 单张 ≤5MB）合理，接受。
6. 售后申请单就三样：标题、描述、图片，没有「类型」这个字段。退货、退款（甚至换货）是商家线下协商后定的结果，不是申请时先选类型。
7. 取消退款和售后退款都是原路退回，走同一退款通道；售后退款由商家处理售后时触发。

## 问题5
### 问：
1. 买家付款成功后，订单显示什么状态？挑战需求B中的订单有“待确认/已确认”状态，现在这两个状态怎么处置？
默认：待支付 → 已支付 / 待确认 → 已确认 → 备货完成 → 已发货 → 已完成；合并为 7 个状态，商家仍需手动点「确认」。
2. 是否所有订单都必须先线上付款？有没有货到付款的需求？
默认：是，没有货到付款的需求
3. 待支付期间，卖家能做什么？
默认：不能确认、不能备货、不能发货（即订单状态不能跳跃推进），必须等付款。
4. 支付超时怎么算、怎么显示，需要在已取消状态中区分原因吗？
默认：从下单时刻起 24 小时未付，系统自动取消并回补库存；订单统一显示「已取消」，不区分原因。
5. 库存占用怎么记？卖家后台的「库存」是什么数？
A：下单即从「可售库存」扣掉；取消、超时、退货再加回；成交时不再扣。卖家看到的就是可售数。
B：库存分「在库 / 已占用 / 可售」三个数，卖家改的是在库数，下单只增加占用。
C：不改数字，只在下单时校验并标记占用（即不预占）。
6. 下单把最后一件占完时，商品立即下架吗？
默认：立即下架，下架原因沿用「已售」；取消 / 超时回补后自动重新上架。
7. 交易完成时扣库存吗？
A：不扣、也不校验，下单时已经扣过。
B：下单只占用不扣，完成时扣（此选项与5.A选项冲突，即类似5.B选项，有多种库存）。
8. 我在挑战需求B中设计了有未完成订单时禁止手动下架 / 把库存改成 0，这条规则还应该保留吗？
默认：取消该限制——库存已占用，卖家随时可以下架或改库存。
### 答：
1. 付款成功 →「已支付」。挑战 B 的「商家确认」其实是 1 个状态（不是「待确认/已确认」两个），挑战 C 保留它，商家仍需手动确认。7 个状态：客户下单 → 待支付 → 已支付 → 商家确认 → 备货完成 → 开始发货 → 交易完成。
2. 确认。所有订单先线上付款，没有货到付款。
3. 确认。待支付期间卖家不能推进状态（不能确认/备货/发货），必须等付款。
4. 确认。从下单时刻起 24 小时未付，系统自动取消并回补库存；统一显示「已取消」，不区分原因。
5. 最接近 C（不预占）。交易成功减 1，不是「下单即扣」。库存就是一个数（可售数）：下单只校验、成交减 1、取消/退货回补。注意这里「取消回补」和「成交减 1」有张力——取消发生在成交前，库存还没减，回补就没货可回。你挑战 B 就抓过这个矛盾，挑战 C 里同样存在，就是成交减 1。
6. 纠正：不是「下单占完立即下架」。库存是成交才减 1，所以是「成交减到 0 才自动下架」，取消/退货回补后重新上架。
7. 交易完成（成交）时扣库存（减 1）——就是「下单不预占、成交减 1」，既不是 A（下单已扣）也不是 B（占用模型）。
8. 确认。没这条限制，取消掉——卖家随时可以手动下架或改库存。

## 问题6
### 问：
若库存不预占，那么“备货完成”状态不就失去语义了吗？我还有个折中方案，1. 卖家推进到备货完成时校验库存，若库存不足不允许推进，推进后库存扣减。2. 库存回补全部由商家手动登记（包括退货/换货产生的库存变化）。
### 答：
「备货完成」就是工作流标记——卖家备好货了打个标记，但库存扣减发生在交易成功那一刻，不是备货完成。它不「失去语义」，只是它标记的是「货已备好」，不是「库存已扣」。
你的两个折中方案：
1. 备货完成时校验 + 扣减：明确为「交易成功减 1」，减 1 在成交，不在备货完成。这个方案等于改了减 1 时机，不符合需求。
2. 回补商家手动登记：只定了「取消/退货回补 +1」，没规定自动还是手动。待支付超时是系统自动回补；取消、退货的回补方式没细说，手动登记不冲突。

## 问题7
### 问：
1. 退款在系统里是「即时完成」还是「要走流程」？
A：即时完成——取消已支付订单后订单直接「已取消」；售后处理完成即「已完成」；系统只记录退款结果。
B：需要「退款中 → 已退款」，由卖家或系统确认。
C：还需要「退款失败 / 重试」
2. 支付与退款要记录并展示哪些信息？
A：支付渠道、支付时间、退款金额、退款时间；订单详情显示「已退款 ¥X」
B：只记录渠道与金额，不记时间。
C：不记录，退款线下处理（退款由系统完成，但退款结果线下通知）。
3. 售后只退了一部分钱，订单怎么显示？
A：订单仍是「交易完成」，另外显示「已退款 ¥X（售后）」和售后单入口。
B：订单状态改成「已退款」（需要新增状态，与「交易完成」并存）。
C：订单仍是「交易完成」，不显示退款金额，订单页面不提供售后单入口。
4. 订单里的收货地址，是下单时的快照，还是引用地址簿？
A：快照——下单时把收货人、电话、完整地址写进订单；之后改 / 删地址不影响订单，地址也可以随便删。
B：引用——订单详情实时读地址簿；改地址会影响未发货订单，被引用的地址也不能删。
5. 地址数量上限？
默认：地址上限最多n个，n由我们定。我暂定n=10。
6. 默认地址细则？
A：第一个自动设为默认；删掉默认地址后，把最近新建的设为默认。
B：删掉默认后没有默认，下单时必须手动选，即默认地址允许为空。
7. 地址字段？
A：收货人、手机号、省 / 市 / 区、详细地址、是否默认。
B：再加邮编。
C：只保留收货人、手机号、一行详细地址。
8. 下单时必须选地址吗？
默认：必须选；默认地址自动带入、可切换；没有地址时提示「先去地址管理新建」，不支持下单页新建。
9. 无物流时，买家注册有“默认交易地点”。现在是否转变为“默认地址”？
默认：该注册信息转变为“默认地址”并加入该买家的地址中，设为默认。
### 答：
1. A（即时完成）。没有「退款中 / 已退款」状态，退款就是「原路退回」：取消已支付订单后订单直接「已取消」，售后处理完成即结束。也没定义「退款失败 / 重试」。
2. 支付渠道隐含要记（要对账），但支付时间、退款金额、退款时间这些字段没明确要求。
3. 订单状态不变（仍是「交易完成」），不新增「已退款」订单状态（B 排除）。是否在订单上显示退款金额、放售后单入口（A vs C），没明确，但售后单本身是有的。
4. 没规定是快照还是引用。只说了下单选地址、地址簿可维护，订单存快照还是引用地址簿这块没说。
5. 没规定上限，只说「多个」地址。
6. 只说「设默认地址」，第一个是否自动默认、删默认后怎么办这些细则都没写。
7. 没明确列地址字段（收货人、手机号、省市区、详细地址、邮编这些都没逐项列）。
8. 确认：下单要选地址、默认地址自动带入可切换。没有地址时怎么办，还没有细想。
9. 你的理解合理，线上支付后线下交易已废弃，这个字段是没清理干净的遗留，实际就该转成「默认地址」并进地址簿、设为默认。

## 问题8
### 问：
1. 快递公司怎么选？
默认：提供预设选项（顺丰、京东、中通、圆通、申通......），选「其他」时填名称。
2. 发货后物流单号 / 快递公司还能改吗？
默认：卖家可以改，订单状态不变，买家看到最新值。
3. 买家看到的「物流跟踪信息」是什么形态？
A：卖家手动录入物流节点（时间 + 描述），买家在订单详情看时间线。
B：卖家只维护一个物流状态（已揽收 / 运输中 / 派送中 / 已签收）+ 单号 + 备注。
C：系统只存快递公司 + 单号，买家点链接去快递官网查，卖家不维护并更新状态。
D：有明确要求对接物流API
4. 要不要增加「买家确认收货」，即“已完成”状态由谁推进？
A：不增加，仍由卖家标记「交易完成」。
B：增加买家确认收货，买家确认后订单才完成。
5. 哪些状态的订单可以申请售后？
A：已发货 + 交易完成。
B：仅交易完成。
C：已支付起（含未发货）。
6. 一张售后单对应多少商品 / 数量？
A：严格一对一，对应的是一个订单项，具体退多少数量由线下决定，系统不记录。
B：一张单可以勾选多个订单项合并申请。
7. 同一商品/订单能多次申请售后吗？
默认：能，不限制售后次数
8. 售后单需要哪些状态？
A：两个，待处理 → 已完成，不能撤销。
B：三个，新增已拒绝状态。
C：更多状态，把退/换货状态也写进去。
9. 商家处理完成时，「结果」怎么选？
A：三选一——仅退款、退货退款、换货。
B：两选一——仅退款、退货退款（不做换货）。
C：只写一段文字结论，不结构化。
10. 选「换货」时，系统要管到哪一步？

## 0. 一页结论

1. **库存**：不预占；下单只校验；买家确认收货（成交）时扣减。**已下架商品成交不扣库存、允许完成**；支付、取消、超时都不改变库存。系统内所有库存“增加 / 回补”操作**全部手动**。
2. **售后**：仅交易完成订单可申请；一张售后单对应一个订单项，整行全退；状态只有 **待处理 / 已完成 / 已取消**；已完成必须带 result（退货并退款、仅退款、换货）。售后退款由系统按整行金额自动写，退款字段只放售后单。
3. **确认收货**：只由买家确认；卖家不能完成、不能代确认；不做超时自动确认（订单可能长期停在已发货，卖家可在完成前取消作为出口）。
4. **地址 / 物流**：地址为“收货人 + 手机号 + 一行详细地址”，默认地址在地址列表点“设为默认”；物流存承运商、单号（多行文本，可多个）、备注，不做状态枚举或节点表。
5. **支付**：按独立支付包设计，不假设只有一个端点；Mock / 短路开关先行，支付宝沙箱作为可选实现，其他渠道待定。

共 **35 项**：§1 四项口径、§2 十七项产品与交互、§3 七项数据与契约、§4 七项工程与测试。§7 列已知取舍与风险。

## 1. 订单、库存与售后口径

### A1 库存模型：不预占、成交扣减、下架例外

**决定**

1. 下单只校验：商品在售、数量不超过当前可售库存；**不锁定、不扣减、不占用**。
2. 支付成功、买家 / 卖家取消、24 小时超时取消，都**不改变库存**。
3. 成交 = 买家确认收货：
   - **在售（ON_SALE）商品**：按明细数量扣减；不足按 A4 拒绝。
   - **已下架（OFF_SHELF）商品**：**不扣库存，允许完成**（Q10-4）。
4. 在售商品扣到 0：自动下架，原因 SOLD_OUT；补货 / 手动改库存 > 0 时，按阶段三规则仅对 SOLD_OUT / STOCK_ZERO 自动上架。
5. **系统内所有库存“增加 / 回补”操作全部手动**：取消、超时、售后退货都不自动 +1。
6. 手动下架是终态：手动下架后不接受库存改动；该商品发生售后退货时也不回补，作为可接受风险。
7. 删除“有未完成订单禁止手动下架 / 改 0”规则；UnfinishedOrderPort / UnfinishedOrderAdapter / OrderStatus.unfinished() 下线，取消守卫按 7 态重算。

**边界**

- Q5-4 / Q6 字面“超时自动回补”按本模型解释为“无库存变化”，不实现自动 +1；该解释需要在澄清记录中标注。
- 已下架商品完成不扣库存，是“成交减 1”的唯一例外。

**影响**：StockPort 不新增预占字段；删除未完成订单阻断及相关错误码；完成动作迁移到买家确认，并按商品状态分支（ON_SALE 扣、OFF_SHELF 不扣）；超时任务不做库存操作；售后不加库存；E2E 库存用例基本保留。

---

### A2 售后：仅已完成、整行全退、三态、result 字段

**决定**

1. **受理范围**：仅 COMPLETED（交易完成）订单；一张售后单对应一个订单项；整行全退，系统不记录具体退货数量。
2. **状态**：待处理 → 已完成 / 已取消。**取消与拒绝同义**，由卖家操作；买家只能发起和查看，没有改状态的权限。
3. **已完成必须带 result**：退货并退款、仅退款、换货；已取消不带 result。
4. **退款**：卖家把售后单标记为完成（退货并退款 / 仅退款）时，系统自动写 refund_amount = 订单项单价 × 数量、refunded_at = 当前时间；退款渠道 = 订单 payment_channel；不手填金额 / 时间。
5. **每个订单项最多一条“已产生退款”的售后单**；服务层在“完成并退款”时强校验；已取消、未退款的售后单不占额度，可再次申请。
6. **库存**：系统不自动加回；退货入库由卖家手动改库存；手动下架商品终态，退货不回补（风险接受）。
7. **售后退款字段只放售后单**；订单表不存退款字段；取消退款流水归支付包；订单详情聚合两者显示“已退款 ¥X”。

**边界**

- 取消已支付订单的退款不是售后，没有售后单；按 D2 归支付包的退款流水记录，订单详情聚合展示。C3 不冻结该流水表结构。
- 换货不产生退款、不占退款额度；之后同一订单项仍可再申请退款，是否允许由卖家线下判断。

**影响**：售后表需 result、refund_amount、refunded_at；订单项累计退款校验；退款展示走聚合；库存回补无系统动作。

---

### A3 确认收货：仅买家

**决定**

- 交易完成只由买家在 SHIPPED 状态手动确认；**卖家不能确认、不能代确认**；删除卖家“交易完成”端点。
- **不做超时自动确认**。买家长期不确认时，订单停在已发货；卖家仍可在完成前取消订单，作为出口。

**取舍**：可能出现长期停在已发货的订单；不接受自动确认，避免系统替买家做完成决定。

---

### A4 成交缺货

**决定**

- **在售商品**：成交时库存不足 → 拒绝确认，订单停在 SHIPPED，提示卖家补货；卖家手动补货后买家重试。不扣负、不部分完成、不自动取消。
- **已下架商品**：成交不扣库存、不校验缺货，直接允许完成。
- 补货 / 库存增加一律手动。

## 7. 已知取舍与风险

1. **买家一直不确认收货**：订单停在已发货；卖家可在完成前取消作为出口；不做自动确认。接受。
2. **已下架商品成交不扣库存**：库存账可能不反映该笔成交；同一商品多笔已发货订单可能都完成，形成超卖 / 账实不符；按 Q10-4 接受。
3. **手动下架商品售后退货不回补**：商品终态、库存只读；接受这部分库存损失。
4. **所有库存增加 / 回补手动**：系统不记录回补原因，由卖家负责；可能出现漏记、重复记。
5. **售后仅对交易完成订单**：已发货但未完成时不能申请售后；买家需先确认收货，或由卖家取消。
6. **取消已支付订单的退款**：没有售后单，退款流水归支付包；订单详情的“已退款”需要聚合两个来源。
7. **售后单只有三态、卖家单方操作**：买家不能撤销；取消与拒绝同义，线下协商结果由卖家登记。
8. **地址只有一行详细地址**：不做省市区结构化；承运商枚举只在前端；多个单号存一个多行文本字段。按当前范围接受。
9. **支付范围**：支付宝沙箱可选，其他渠道可能只做 Mock；真实支付 / 退款接口开发时再定，部署文档需写明局限。
10. **换货不产生退款、不占退款额度**：同一订单项换货后仍可再申请退款，是否允许由卖家线下判断。

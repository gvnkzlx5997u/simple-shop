# 挑战需求C 需求总结

> **适用范围**：本阶段在线支付、配送与售后升级的交付与验收。
> **阅读说明**：正文按“需求新增、需求变更、需求删减”组织。状态模型只用于解释规则，不是独立交付物；阅读时以各节的能力与约束为准。

本阶段在现有单卖家购物系统上补齐三件事：**订单先支付、商品有配送、成交后可售后**。系统仍然不承载运费、优惠、发票和真实物流对接；支付以可替换的支付端口为主，真实渠道按开发情况接入。

## 0. 三类改动一览

| 类别 | 一句话 | 主要内容 |
| --- | --- | --- |
| 需求新增 | 订单能收钱、商品能送到、成交后能售后 | 线上支付、收货地址、配送与物流信息、买家确认收货、按订单项售后 |
| 需求变更 | 完成人从卖家改为买家，支付和配送进入订单 | 订单 7 态、成交扣库存与下架例外、取消退款、商品下架规则、订单字段与页面 |
| 需求删减 | 删除不再成立的旧规则和入口 | 未完成订单阻断、卖家交易完成、注册默认交易地点；另有明确不做的范围 |

## 1. 业务目标与范围

### 1.1 一句话目标

把订单从“下单后等商家确认”升级为“**先支付、再履约、买家确认完成、完成后按商品售后**”，并让收货地址、配送信息和售后退款成为订单的正式组成部分。

### 1.2 业务闭环

浏览在售商品 → 加入购物车 → 下单并选择收货地址 → 待支付 → 支付 → 已支付 → 商家确认 → 备货完成 → 发货（承运商、单号、备注）→ 买家确认收货 → 交易完成 → 按订单项申请售后 → 卖家线下协商 → 登记结果（退货并退款、仅退款、换货）。

### 1.3 角色与权限

| 角色 | 主要职责 | 明确不能做 |
| --- | --- | --- |
| 买家 | 浏览、加购、下单、选地址、支付、取消（发货前）、确认收货、维护地址、申请和查看售后、上传售后图片 | 不能确认、备货、发货；发货后不能取消；不能改售后状态；不能操作卖家后台 |
| 卖家 | 维护商品与库存、确认订单、备货、发货、修改物流信息、取消（交易完成前）、处理或取消售后、筛选订单 | 不能确认收货；不能在待支付阶段推进订单；不能修改手动下架商品的库存 |
| 系统 | 24 小时未支付自动取消；按取消或售后操作自动记退款 | 不自动确认收货，不自动增加或回补库存 |

### 1.4 术语

| 术语 | 含义 |
| --- | --- |
| 成交 | 买家确认收货，订单进入交易完成 |
| 订单项 | 订单中的一行商品，含商品名、单价、数量快照 |
| 整行全退 | 按订单项的“单价 × 数量”全额退款，不拆数量 |
| 已产生退款 | 售后单已完成，且结果为退货并退款或仅退款 |
| 下架例外 | 商品已下架时，买家确认收货不扣库存、允许完成 |
| 手动回补 | 卖家在库存编辑中自行增加库存，系统不自动加回 |
| 支付包 | 独立承载支付、退款流水和渠道适配的实现模块 |

## 2. 需求新增

### 2.1 线上支付

**支付时限**

- 订单提交后进入待支付。从下单时刻起 24 小时未支付，系统自动取消订单。
- 超时取消不改变库存，订单显示已取消，不区分取消原因。
- 支付失败不设失败状态：订单仍停在待支付，买家可以重试，直到超时取消。

**支付渠道**

- 支持银行卡、信用卡、支付宝、微信四类渠道，买家付款时自行选择。
- 订单必须记录实际使用的支付渠道，退款按原渠道退回。
- 四类渠道在交互和订单记录上都要可用；本期以可替换的支付端口和 Mock 为主，支付宝沙箱作为可选实现，其他渠道是否接真实服务视开发情况而定。

**支付结果**

- 支付成功进入已支付。商家仍需在后台手动确认，已支付不等于已确认。
- 支付金额等于订单总额；系统没有运费、优惠、发票，订单总额就是商品金额之和。

**实现边界**

- 支付不假设只有一个接口：可能包含下单支付、支付结果通知、退款、查询等能力，独立成包设计。
- 自动化测试使用短路或 Mock 支付；真实支付和退款接口的具体形态在开发时确定。

### 2.2 收货地址

- 买家可以保存多个收货地址，上限 10 个。
- 第一个地址自动成为默认地址；地址列表提供“设为默认”操作，默认地址不在新增或编辑表单里设置。
- 删除默认地址后，由最近创建的地址补位；没有地址时没有默认地址，下单时提示先新建。
- 地址字段只有三项：收货人、手机号、一行详细地址。不做省、市、区和邮编的结构化。
- 下单必须选择一个已有地址；不支持下单页当场新建或编辑，需要先去地址管理。
- 订单保存地址快照：收货人、手机号、详细地址写入订单。之后修改或删除地址簿中的地址，不影响已下订单。
- 注册时的“默认交易地点”字段取消，不再迁移旧值；地址统一由地址簿维护。

### 2.3 配送与物流

- 卖家发货时必须填写承运商和物流单号；承运商不能为空。
- 承运商使用前端固定清单：顺丰、京东、中通、圆通、申通、韵达、邮政 EMS、其他。选择“其他”时填写名称。
- 后端只保存承运商名称字符串，不维护承运商枚举；历史订单保留提交时的名称。
- 物流单号使用多行文本，允许一个订单填写多个单号；另设物流备注，记录特殊状态或补充说明。
- 发货后，卖家可以修改承运商、单号和备注，订单状态不变，买家看到最新值；已取消订单不再允许修改。
- 买家在订单详情查看承运商、单号和备注文本。
- 不做物流状态枚举、物流轨迹节点，也不对接物流商 API；物流信息由卖家手动维护。

### 2.4 买家确认收货

- 订单进入已发货后，由买家手动确认收货。
- 确认收货是订单进入交易完成的唯一方式；卖家不能确认、不能代确认，也没有“卖家完成订单”的入口。
- 不做超时自动确认。买家长期不确认时，订单停在已发货；卖家仍可在交易完成前取消订单，作为处理出口。
- 买家确认收货时触发成交库存处理：在售商品扣减库存，已下架商品不扣库存（详见“成交与库存”）。

### 2.5 售后服务

**申请范围与粒度**

- 只有交易完成的订单可以申请售后；已取消、待支付、已支付、已确认、备货完成、已发货的订单都不能申请。
- 一张售后单只对应一个订单项，不合并多个商品；按整行数量全退，系统不记录具体退几件。
- 申请单包含标题、描述、图片三项，没有“售后类型”字段。图片可上传，不是必填；最多 9 张，JPG 或 PNG，单张不超过 5MB。
- 退货、退款、换货由卖家线下协商后确定，不在申请时选择；系统不记录协商备注、拒绝理由。

**售后状态**

- 只有三个状态：待处理、已完成、已取消。
- 卖家负责登记状态；买家只能发起和查看，不能改状态，也不能撤销。
- “取消”和“拒绝”是同一个动作：卖家把待处理的售后单置为已取消。
- 已取消的售后单可以再次申请；系统不限制取消次数。

**处理结果**

- 已完成必须带结果，三选一：退货并退款、仅退款、换货。
- 仅退款：不退货，只退该订单项金额。
- 退货并退款：买家退货，卖家确认后完成，退该订单项金额。
- 换货：卖家线下补发，系统不记录新物流，不产生退款。
- 已完成但结果为换货的售后单，之后仍可对同一订单项再申请退款；是否允许由卖家线下判断。

**退款**

- 卖家把售后单标记为完成，且结果为退货并退款或仅退款时，系统自动写退款金额和退款时间。
- 退款金额固定为订单项单价 × 数量，不允许手填；退款时间取完成时的当前时间；退款渠道取订单原支付渠道。
- 每个订单项最多只能有一条“已产生退款”的售后单。服务层在“完成并退款”时强制校验，防止同一订单项重复退款。
- 已取消、结果为换货的售后单不占退款额度，可以再次申请。
- 售后退款字段只放售后单；订单表不存退款字段。

**库存**

- 系统不因售后退货自动增加库存。
- 退货入库由卖家手动修改库存；手动下架的商品是终态，退货也不回补，作为可接受风险。

**页面与编号**

- 买家有“我的售后”列表和详情；卖家有“售后管理”列表和详情；订单详情内嵌该订单的售后单，可进入售后详情。
- 售后单有独立编号，格式为 AS + 日期 + 序号，方便线下协商时引用。

### 2.6 新增的数据对象与页面

| 对象 / 页面 | 新增内容 |
| --- | --- |
| 收货地址簿 | 地址增删改、设为默认、默认地址补位 |
| 订单 | 地址快照、支付渠道、支付时间、承运商、多行物流单号、物流备注 |
| 售后单 | 编号、订单项、标题、描述、状态、结果、退款金额、退款时间 |
| 售后图片 | 最多 9 张，JPG 或 PNG，单张不超过 5MB |
| 买家页面 | 地址管理、支付页、确认收货、我的售后、售后详情 |
| 卖家页面 | 发货与修改物流、售后管理、售后详情、订单状态筛选 |

## 3. 需求变更

### 3.1 订单生命周期

订单状态从原来的 6 个扩展为 7 个：

**待支付 → 已支付 → 已确认 → 备货完成 → 已发货 → 交易完成**，另有**已取消**。

- “已支付”承接原来“待确认”的位置：付款后等待商家确认。商家确认后进入“已确认”，不再单独保留“待确认”状态。
- 商家仍需手动确认、手动备货、手动发货；卖家在待支付阶段不能确认、备货、发货。
- 买家在发货前可以取消；发货后不能取消，只能由卖家在交易完成前取消。
- 买家在已发货后手动确认收货，订单进入交易完成。
- 支付失败不产生新状态，订单仍停在待支付。
- 状态只能按序前进，不能跳级、不能回退；交易完成和已取消是终态。

订单状态的进入、退出和权限见下文状态表。

### 3.2 成交与库存

- 下单只校验商品在售和库存足够，不锁定、不扣减、不占用库存。
- 支付成功、买家取消、卖家取消、超时取消都不改变库存。
- 成交时按商品状态分两种：
  - 在售商品：按订单明细数量扣减库存；库存不足则拒绝确认，订单停在已发货，卖家补货后买家重试。不允许负库存、不部分完成、不自动取消。
  - 已下架商品：不扣库存，直接允许完成。这是“成交减 1”的唯一例外。
- 在售商品库存扣到 0 时自动下架，原因记为已售；补货或手动把库存改回大于 0 时，只有“已售”和“库存耗尽”两种下架原因会自动上架。上架只改商品状态，库存数量仍由卖家手动填写。
- 系统内所有库存增加和回补都手动完成：取消、超时、售后退货都不自动加回。
- 手动下架是终态：手动下架后不接受库存修改；该商品发生售后退货时也不回补。

### 3.3 取消与退款

| 订单状态 | 谁可以取消 | 退款 | 库存 |
| --- | --- | --- | --- |
| 待支付 | 买家、卖家；系统超时 | 不退款 | 不变 |
| 已支付 | 买家、卖家 | 全额原路退款 | 不变 |
| 已确认 | 买家、卖家 | 全额原路退款 | 不变 |
| 备货完成 | 买家、卖家 | 全额原路退款 | 不变 |
| 已发货 | 仅卖家 | 全额原路退款 | 不变 |
| 交易完成 | 不可取消 | 不适用 | 不变 |
| 已取消 | 不可再取消 | 不适用 | 不变 |

- 取消都是整单取消，不做部分商品取消。
- 退款即时完成，没有“退款中”“已退款”订单状态，也没有退款失败状态。
- 取消退款不是售后，没有售后单；它归支付包的退款流水记录，订单详情把售后退款和取消退款合并显示为“已退款 ¥X”。
- 售后退款按订单项金额，取消退款按订单总额，两者都是原路退回。

### 3.4 商品下架与库存

- 删除“有未完成订单时禁止手动下架或把库存改为 0”的限制。卖家可以随时手动下架商品或调整库存。
- 手动下架仍是终态：下架后不能改库存，也不能重新上架。
- 已售、库存耗尽两种下架原因仍然支持补货后自动上架；手动下架不支持。
- 因为限制已删除，可能出现“商品已下架、仍有已发货订单待确认”的情况。此时买家确认收货不扣库存、允许完成；库存账可能不反映这笔成交，属于已接受的风险。
- 售后退货不触发自动上架；卖家如果手动补货，按现有补货规则处理。

### 3.5 订单数据与展示

- 订单新增地址快照：收货人、手机号、详细地址。
- 订单新增支付信息：支付渠道、支付时间。
- 订单新增物流信息：承运商、多行物流单号、物流备注。
- 订单不存退款字段；售后退款在售后单，取消退款在支付包。
- 订单项继续保存商品名、单价、数量快照；订单总额仍为各订单项金额之和。
- 买家订单列表按 7 个状态筛选；卖家订单列表增加待支付、已支付等状态筛选，待支付订单可见但不能推进。
- 卖家订单详情不再有“交易完成”按钮；买家订单详情增加“确认收货”按钮和“申请售后”入口。

### 3.6 售后与订单的关系

- 订单不新增“售后中”状态。售后处理期间，订单仍保持交易完成。
- 售后退款是按订单项的部分金额退款，不改变订单总额，也不回退订单状态。
- 订单详情聚合展示该订单的售后单和已退款总额。
- 同一订单项最多一条已产生退款的售后单；服务层在完成并退款时校验。

### 3.7 地址来源与注册

- 注册不再填写“默认交易地点”，该字段从注册流程删除，也不迁移旧值。
- 地址统一在地址簿维护；下单只能选择已有地址。
- 订单保存地址快照，地址簿的后续修改和删除不影响历史订单。

## 4. 需求删减

### 4.1 删除现有规则和入口

1. **删除“有未完成订单时禁止手动下架、禁止把库存改为 0”的限制。** 卖家可以随时下架或调整库存；由此产生的已下架商品成交，按“不扣库存、允许完成”处理。
2. **删除卖家侧的“交易完成”操作和入口。** 订单完成只由买家确认收货推进；卖家不能确认、不能代确认。
3. **删除注册时的“默认交易地点”字段。** 地址改由地址簿维护，不迁移旧值。

### 4.2 本阶段明确不做

以下内容不进入本阶段范围，避免被误解为遗漏：

- 库存预占、库存锁定、下单即扣库存。
- 取消、超时、售后退货的自动库存回补。
- 买家不确认时的超时自动完成。
- 售后按数量部分退款、部分退货。
- 售后独立的“已拒绝”状态；拒绝合并为已取消。
- 买家撤销售后；售后状态只由卖家登记。
- 物流状态枚举、物流轨迹节点、物流商 API 对接。
- 地址的省、市、区、邮编结构化。
- 多包裹、多物流单的独立结构；多个单号存一个多行文本。
- 运费、优惠、发票、对账、支付流水明细页面。
- 强制接入真实支付网关；本期以 Mock 和可替换端口为主，支付宝沙箱可选。
- 售后协商理由、拒绝理由、协商备注的留痕。
- 订单部分取消、部分完成。

## 5. 用状态模型解释关键规则

主流程：待支付 → 已支付 → 已确认 → 备货完成 → 已发货 → 交易完成；待支付可超时取消。以下状态表和联动表只用于解释以上规则，不是独立需求。真正要交付的是“新增、变更、删减”三部分的能力与约束。

### 5.1 订单状态与迁移

| 当前状态 | 可进入的下一状态 | 触发者 | 说明 |
| --- | --- | --- | --- |
| 待支付 | 已支付 | 买家支付成功 | 支付失败仍停留待支付 |
| 待支付 | 已取消 | 买家、卖家、系统超时 | 不退款，不改库存 |
| 已支付 | 已确认 | 卖家确认 | 商家仍需手动确认 |
| 已支付 | 已取消 | 买家、卖家 | 全额退款，不改库存 |
| 已确认 | 备货完成 | 卖家 | 备货完成只是流程标记，不校验库存 |
| 已确认 | 已取消 | 买家、卖家 | 全额退款，不改库存 |
| 备货完成 | 已发货 | 卖家 | 发货必须填承运商和单号 |
| 备货完成 | 已取消 | 买家、卖家 | 全额退款，不改库存 |
| 已发货 | 交易完成 | 买家确认收货 | 在售商品扣库存；已下架商品不扣 |
| 已发货 | 已取消 | 仅卖家 | 全额退款，不改库存 |
| 交易完成 | 无 | 无 | 终态；可申请售后 |
| 已取消 | 无 | 无 | 终态；不能申请售后 |

**关键不变量**

- 只能按序前进，不能跳级、不能回退。
- 待支付阶段卖家不能确认、备货、发货。
- 买家只能在已发货阶段确认收货；卖家不能完成订单。
- 支付失败不产生状态，仍停留待支付。
- 除超时取消外，没有系统自动推进的状态。
- 库存只在成交时变化；支付、取消、超时都不改库存。
- 成交时只有在售商品扣库存；已下架商品不扣。
- 售后只对交易完成订单开放，售后处理不改变订单状态。

### 5.2 售后状态

| 当前状态 | 可进入的下一状态 | 触发者 | 说明 |
| --- | --- | --- | --- |
| 待处理 | 已完成 | 卖家 | 必须选择结果：退货并退款、仅退款、换货 |
| 待处理 | 已取消 | 卖家 | 取消与拒绝同义，不产生退款 |
| 已完成 | 无 | 无 | 终态；结果为退款类时已写退款 |
| 已取消 | 无 | — | 终态；可新建售后单，不占退款额度 |

- 买家不能改售后状态，也不能撤销。
- 同一订单项最多一条已产生退款的售后单；换货、已取消不占额度。
- 售后单已完成且结果为退款类时，系统按整行金额写退款，退款渠道取订单原支付渠道。

### 5.3 库存与商品状态联动

| 事件 | 库存变化 | 商品状态变化 |
| --- | --- | --- |
| 下单、支付、取消、超时 | 不变 | 不变 |
| 在售商品成交 | 扣减订单项数量 | 扣到 0 时下架，原因记为已售 |
| 已下架商品成交 | 不变 | 保持已下架 |
| 售后退货 | 系统不变；卖家手动改库存 | 手动下架商品不回补、不上架 |
| 卖家手动下架 | 不变 | 进入手动下架终态，之后不能改库存 |
| 卖家补货或手动增加库存 | 手动增加 | 已售、库存耗尽两种原因在库存大于 0 时自动上架；手动下架不自动上架 |
| 卖家手动把库存改为 0 | 改为 0 | 下架，原因记为库存耗尽 |

这张表解释了“为什么取消不改库存、为什么下架商品成交不扣库存、为什么退货要卖家手动处理”，不引入额外的状态机。

## 6. 关键场景

1. **支付超时**：买家下单后 24 小时未支付，系统自动取消订单；库存不变，买家看到已取消，不能申请售后。
2. **已支付后取消**：买家在发货前取消已支付订单，订单变为已取消，系统全额原路退款；库存不变，不产生售后单。
3. **正常履约**：买家支付 → 卖家确认 → 备货完成 → 发货并填写承运商、单号、备注 → 买家确认收货 → 在售商品扣库存 → 交易完成。
4. **成交时缺货**：买家确认收货时，在售商品库存不足，确认被拒绝，订单停在已发货；卖家手动补货后，买家再次确认。
5. **已下架商品成交**：订单已发货后商品被手动下架；买家确认收货时不扣库存、直接完成，库存保持原值，作为已接受的库存账差异。
6. **售后退货并退款**：交易完成后买家对某订单项发起售后，上传标题、描述、图片；卖家线下协商后把售后单标记完成，结果为退货并退款；系统按整行金额原路退款，库存由卖家手动加回；如果商品是手动下架，则不回补。
7. **售后仅退款或换货**：卖家完成售后时选择仅退款，系统只退款不要求退货；选择换货则不产生退款，补发由卖家线下处理，系统不记录新物流。
8. **售后取消与再申请**：卖家取消待处理的售后单，状态变为已取消，不产生退款；买家可以再次发起新的售后单。
9. **地址快照**：买家下单时选择地址，订单保存收货人、手机号、详细地址；之后修改或删除地址簿中的地址，订单地址不变。

## 7. 验收要点

| 领域 | 验收要点 |
| --- | --- |
| 支付 | 四种渠道可选并记录渠道；24 小时超时自动取消；支付失败仍停留待支付可重试；已支付取消全额原路退款；取消不改库存 |
| 地址 | 最多 10 个；首个自动默认；列表可设默认；删默认后最近创建补位；下单必须选地址；订单存快照；注册不再有默认交易地点 |
| 物流 | 发货必须填承运商和单号；支持多个单号的多行文本和备注；发货后可修改；买家可查看；不做状态枚举和 API |
| 确认收货 | 只有买家能确认；卖家不能完成或代确认；没有超时自动确认；确认时在售商品扣库存、已下架商品不扣；缺货拒绝并停在已发货 |
| 售后 | 仅交易完成订单；按订单项、整行全退；三态；已完成必须带结果；退款自动按整行金额写；每个订单项最多一条已退款；取消后可再申请；买家不能改状态 |
| 订单与库存 | 7 个状态；状态不可跳级或回退；取消/超时/支付不改库存；所有库存增加和回补手动；手动下架终态；删除未完成订单阻断 |
| 数据与页面 | 订单存地址、支付、物流字段但不存退款；售后退款在售后单；取消退款在支付包；订单详情聚合已退款；买卖双方售后列表和详情可用 |

## 8. 落地时确认的细节

以下几项是在实现阶段定下来的，需求原文没写、但对前端与测试是硬约束：

1. **售后凭证图**：先调 `POST /api/buyer/media`（`purpose=AFTERSALE_IMAGE`）上传，再把返回的 URL 放进申请；≤9 张、单张 ≤5MB、只接受 JPG/PNG，外链与商品图目录的地址都会被拒。
2. **单号规则**：订单 `SO + yyyyMMdd + 6 位每日序列`，售后 `AS + yyyyMMdd + 4 位每日序列`，日期取 UTC。同日多轮测试序号会继续累加，只断言格式、不断言数字。
3. **完成即终态**：售后单一旦完成就不能取消或改结果；「拒绝」与「取消」是同一个动作，没有独立的已拒绝状态。
4. **退款账分两处**：取消退款写支付流水，售后退款只写售后单，订单详情的「已退款」是两者相加——任何一张表都不存派生的总数。

---

> **总结**：本阶段的交付重点不是“把状态画全”，而是把三条业务链路打通：**订单能收钱、商品能送到、成交后能售后**。状态模型只是把这些规则串起来看；实现时以新增、变更、删减三部分的需求为准。

# 阶段四契约交接（后端 → 前端 / E2E）

> **用途**：阶段四后端交付给前端的接口契约与行为口径。端点清单以 `openapi.json` 为机器可读版本，本文补充文档无法表达的部分：谁能在什么状态做什么、字段为什么这么给、相对阶段三有哪些破坏性变更。
> **基线**：`openapi.json`（50 个路径 / 81 个 schema）、V4 迁移、`simple-shop-backend/README.md`。
> **口径来源**：需求总结 + 团队自决实现项（35 项）。冲突时以团队自决为准。

## 2. 通用约定

- 响应统一 `{code, message, data}`；`code=0` 为成功，业务失败也返回 HTTP 200（`code` 决定语义），只有参数校验失败是 HTTP 400 + `50002`（带 `errors` 数组）、未登录 401 + `10002`、资源不存在 404。
- 时间一律 UTC ISO-8601（`2026-11-27T02:00:00Z`），前端不要用本地时区解析。
- 金额为十进制字符串/数字，两位小数；金额永远由后端算，前端传的金额一律忽略。
- 鉴权：`Authorization: Bearer <token>`；买家与卖家令牌不能互用，用错角色返回 401。会话存在后端进程内，**后端重启即失效**。
- 请求体不接受未定义字段（`failOnUnknownProperties=true`）：多传 `default_location` 这类已删字段会 400，而不是被忽略。

## 4. 行为口径（按钮与状态）

### 4.1 订单七态

`PENDING_PAYMENT` → `PAID` → `CONFIRMED` → `PREPARED` → `SHIPPED` → `COMPLETED`，另有终态 `CANCELED`。只能按序前进一格，不可跳级、不可回退。

| 状态 | 买家可做 | 卖家可做 |
| --- | --- | --- |
| 待支付 | 支付、取消 | 取消（**不能确认**） |
| 已支付 | 取消（全额退） | 确认、取消（全额退） |
| 已确认 | 取消（全额退） | 备货完成、取消（全额退） |
| 备货完成 | 取消（全额退） | 发货、取消（全额退） |
| 已发货 | 确认收货 | 改物流、取消（全额退） |
| 交易完成 | 申请售后 | 处理售后 |
| 已取消 | — | — |

- 支付失败**不改变订单**：仍是待支付，可重试，直到 24 小时超时由系统取消。
- 成交扣减只发生在「买家确认收货」：在售商品按明细数量扣，任一不足整单拒绝（60004），订单停在已发货，卖家补货后可重试。
- 已下架商品成交不扣库存（唯一例外），此时不校验缺货、订单可直接完成。

### 4.2 支付

- 渠道四选一：`BANK_CARD`、`CREDIT_CARD`、`ALIPAY`、`WECHAT`。本期全部走 Mock，**总是成功**；失败只在测试环境用配置注入。
- 支付成功写订单的 `payment_channel` 与 `paid_at`；失败时两者都必须为空（前端不要缓存"上次选的渠道"当已支付）。
- `pay_deadline` 只在待支付订单上出现，用它做倒计时，不要自己按 24 小时算。

### 4.3 取消与退款

- 取消是整单的，不改变库存。
- 已支付订单取消：全额原路退款，写一条 `ORDER_CANCEL` 退款流水；待支付取消不产生流水。
- 重复取消返回成功，但只退一次。
- 超时取消（24 小时）由系统执行，不改库存、不退款。

### 4.4 地址

- 最多 10 条；第一条自动默认；切换默认只能显式「设为默认」，编辑不会顺手改默认。
- 删除默认地址后，由剩余里最新创建的一条补位；全删光则没有默认。
- 下单必须选一条已存在的地址；订单存快照，地址之后改名/删除都不影响历史订单。

### 4.5 售后

- **只有交易完成**的订单可以按订单项申请；同一订单项可多次申请（换货后仍可再申请），申请阶段不拦。
- 申请不选类型：退货退款 / 仅退款 / 换货是**卖家处理时**登记的结果。
- 图片 ≤9 张，必须先走 `POST /api/buyer/media` 上传，申请时只传返回的 URL；外链与商品图目录的 URL 会被拒（20016）。
- 卖家 `complete` 后：
  - `EXCHANGE`：不退款，`refund_amount` 与 `refunded_at` 为空；
  - `RETURN_AND_REFUND` / `REFUND_ONLY`：后端按「订单项单价 × 数量」写退款金额与时间。
- **同一订单项只能退款一次**（81004）；换货不占额度。完成是终态，不能取消或改结果。
- 卖家 `cancel` 与「拒绝」同义；取消后可重新申请，生成新单号。

### 4.6 订单详情里的金额

- `refunded_amount` = 取消退款（支付流水）+ 售后退款（售后单，只算「已完成 + 退款类结果」）。
- `aftersale_count` = 该订单售后条数（含待处理与换货），不等于退款笔数。
- 售后列表不内嵌在订单详情里，按 `order_id` 单独查。

## 5. 字段要点

### 5.1 订单头 `OrderData`

| 字段 | 说明 |
| --- | --- |
| `order_id` / `order_no` | 主键（`O+UUID`）与人类可读单号（`SO+yyyyMMdd+6位`） |
| `status` | 七态之一 |
| `total_amount` / `item_count` | 总额（后端算）、件数（明细行数） |
| `receiver_name` / `receiver_phone` / `receiver_address` | **下单时的快照**，不随地址簿变化 |
| `payment_channel` / `paid_at` | 未支付时都为 `null` |
| `pay_deadline` | 仅待支付时有值 |
| `carrier` / `tracking_no` / `logistics_remark` | 发货后才有；`tracking_no` 可能含换行（多包裹） |
| `refunded_amount` / `aftersale_count` | 见 §4.6 |
| `buyer` | `{id, username}`；卖家列表用它显示客户 |

### 5.2 订单项 `OrderItemData`

`order_item_id`（**售后申请用它，不要用 `goods_id`**）、`goods_id`、`goods_name`、`unit_price`、`quantity`、`amount`（服务端算的小计）。

### 5.3 地址 `AddressData`

`id`、`receiver_name`、`receiver_phone`、`detail_address`（一行文本）、`is_default`、`create_at`、`update_at`。

### 5.4 售后 `AftersaleData` / `AftersaleDetailData`

摘要含 `aftersale_no`、`order_id`、`order_no`、`order_item_id`、`goods_name`、`title`、`status`、`result`、`refund_amount`、`refunded_at`、`create_at`；详情另含 `description`、`image_urls`（按顺序）。

- `status`：`PENDING`、`COMPLETED`、`CANCELED`；`result`：`RETURN_AND_REFUND`、`REFUND_ONLY`、`EXCHANGE`，未完成时为 `null`。

## 6. 破坏性变更（相对阶段三）

| # | 变更 | 前端要做什么 |
| --- | --- | --- |
| 1 | 订单状态：删除 `PENDING_CONFIRM`，新增 `PENDING_PAYMENT`、`PAID`；下单后直接待支付 | 状态枚举与筛选项全部改七态；旧的"待确认"文案与逻辑删除 |
| 2 | 删除 `POST /seller/orders/{id}/complete` | 卖家端去掉"完成订单"按钮；成交由买家确认收货推进 |
| 3 | 下单必填 `address_id`，响应新增 `pay_deadline` | 下单页加地址选择；下单后起倒计时 |
| 4 | 注册不再接受 `default_location`，多传会 400 | 注册表单删掉该字段 |
| 5 | 卖家客户列表/详情不再返回 `default_location` | 客户页去掉该列 |
| 6 | 订单头新增收货快照、支付、物流、退款汇总共 10 个字段；订单项新增 `order_item_id` | 订单详情/列表按新字段渲染；售后入口用 `order_item_id` |
| 7 | 新增地址 5 个端点、售后 7 个端点、买家上传 1 个端点、支付 1 个端点、改物流 1 个端点 | 新增页面/操作 |
| 8 | 错误码新增 80001–83004 一段；`20020`、`10008` 停用 | 错误码映射表更新（未识别的码按通用提示） |
| 9 | 行为放宽：有未完成订单时也可以手动下架、把库存改成 0 | 卖家端去掉相关禁用与提示 |

## 7. E2E 注意事项

1. **数据库必须按 V4 重建**：V4 给订单加的是 `NOT NULL` 无默认值的收货快照列，**订单表必须为空**才能执行；开发库与 E2E 库都按「备份 → 删库 → 启动由 Flyway 跑到 V4」重建。
2. **支付是 Mock**：四渠道恒成功。要测"支付失败仍待支付"，用环境变量 `PAYMENT_MOCK_FAIL_CHANNELS=ALIPAY` 重启后端，而不是改请求参数。
3. **24 小时超时不要等**：E2E 不把定时器纳入主流程。要验证超时可 `update simpleshop_order set create_at = <25 小时前>`，再等一轮扫描（默认 60 秒，可用 `ORDER_TIMEOUT_SCAN_INTERVAL_MS` 调小）；或在用例里直接断言"过期订单支付返回 83002"。
4. **上传文件落在 `media.directory`**（测试为 `./target/test-media`）：E2E 每次运行前清理，否则售后图片会跨轮次累积；`/media/**` 直接可访问，含 `aftersale` 子目录。
5. **会话在进程内**：后端重启后旧 token 全部失效，E2E 要重新登录；不要把 token 跨重启缓存。
6. **限流**：测试环境 `RATE_LIMIT_ENABLED=false`；开启时注册/登录按 IP 计数，容易让批量用例互相影响。
7. **时间**：接口与库内都是 UTC；断言日期时用 `Z` 结尾的字符串，不要转本地时区。
8. **订单号/售后号每日序列**：同日多轮 E2E 时序号会继续累加，不要断言具体数字，只断言格式。

## 8. 已知取舍与未做项

| 项 | 现状 | 影响 |
| --- | --- | --- |
| 真实支付渠道 | 只做 Mock；支付宝沙箱是可选扩展（见《支付包设计》§11） | 无法验证真实签名、回调、渠道错误码 |
| 自动确认收货 | 不做，只由买家手动确认 | 卖家订单可能长期停在已发货 |
| 物流状态/轨迹 | 只存承运商、单号（可多行）与备注，不查快递轨迹 | 前端只展示文本，无节点时间线 |
| 地址省市区 | 不做结构化地址，只有一行详细地址 | 无法按地区统计或筛选 |
| 售后「已拒绝」状态 | 没有独立状态，拒绝 = 取消 | 前端区分"买家撤销"与"卖家拒绝"只能靠文案 |
| 售后退款与支付 | 售后退款只落售后单，不写支付流水、不调网关 | 订单详情靠两处相加；接真实渠道后必须补调用 |
| 退款失败 | 无失败态、无重试、无补偿任务 | 真实渠道下可能出现"已取消但钱没退"，靠人工 |
| 下架商品成交 | 已下架商品成交不扣库存 | 库存账与实际出货存在差异（需求确定的例外） |
| 支付流水 | 只有订单上的 `paid_at`，没有独立支付单表 | 真实对账需要补表 |
| 多副本部署 | 会话、限流、编号都在进程内，按单副本设计 | 不能水平扩容 |

## 9. 变更流程

- 接口契约变更：先改 `openapi.json` 与本文件，再改代码；`OpenApiTest` 会断言端点数量与关键 schema。
- 已发布的 Flyway 脚本不得修改，结构变更只能新增 V5。
- 错误码只增不改：停用的码位保留注释，不复用。

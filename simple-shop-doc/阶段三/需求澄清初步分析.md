## 0. 一页结论

1. **订单取代购买意向**：一笔订单含多商品明细，整单流转；5 个业务状态 + 1 个“已取消”状态。
2. **库存不预占**：下单只校验、不锁库存；交易完成时才扣减；取消订单不影响库存。Q1 答 4 的“取消回补”已被 Q3 明确否定。
3. **商品只有“在售 / 已下架”两态**：没有冻结；但“已下架”下有“已售 / 库存耗尽下架 / 手动下架”三种来源，其中手动下架实际上没有重新上架入口，接近终态。
4. **阶段二的“归档 = 商品 + 意向搬入历史表”不再适用**：订单要长期保留，商品也不能物理删除。建议改为“单表 + 下架原因 + 历史视图”，不再搬表。
5. **阶段二有两处需要修正**：手动下架被实现成“可重新上架”，与 Q11 冲突；限流按 IP 每分钟 10 次，导致 E2E 必须改成 1000 次，保护措施变成了测试阻塞。
6. **需求澄清已结束**：Q12/Q13 之后只剩 B4（商品编辑范围），Q7 已授权团队自决，本轮确认为「沿用阶段二」（§5.2）。剩余 4 项是技术实现决策（数据库重建、限流、旧接口、超卖兜底），不由产品侧拍板，列在 §5.3 待开发/组长确认。

## 1. 需求澄清现状概括

### 1.1 主流程

```
在售商品 → 加入购物车 → 购物车勾选多件 → 下单（1 单多明细）
→ 商家确认 → 备货完成 → 开始发货 → 交易完成

买家：开始发货前可整单取消
商家：交易完成前可整单取消
```

没有在线支付、没有物流、没有收货确认、没有退货/退款/售后、没有超时自动完成。

## 2. “归档”范围重新设计

### 2.1 阶段二的归档做了什么

阶段二的归档是一个**物理搬迁动作**：

- 触发条件只有一个：成交且扣减后库存 = 0（卖出最后一件）。
- 同一事务内，把商品从当前商品表删除、插入历史商品表；把该商品全部意向从当前意向表删除、插入历史意向表。
- 历史表保存类别名、商品名、用户名、电话等字符串快照；当前表不再有该商品及其意向。
- 卖家历史页分“已下架（可复售）”和“已归档（终态）”两个分区。
- 对应表：`simpleshop_goods_history`、`simpleshop_intention_history`；代码里有 `history` 功能包。

阶段二这样设计的原因是：购买意向是“一次交易”的记录，商品售罄后整件商品退出，历史查询不再依赖当前表。这个前提在阶段三不成立了。

### 2.2 阶段三为什么不能沿用

1. **订单必须长期保留**。买家要查下单历史，卖家要按客户、按商品查订单，订单还要支持取消/完成状态。商品如果被搬进历史表，订单明细、库存扣减、商品详情都会失去稳定的引用对象。
2. **没有购买意向了**。`intention_history` 没有存在意义；订单本身就是交易记录。
3. **“已下架”不等于“终态”**。库存归 0 下架可补货复售；手动下架才是终态。阶段二只有一个 `ARCHIVED` 终态，无法表达“可复售的下架”和“不可复售的下架”。
4. **商品不能删除**。Q8 明确商品没有物理删除，只有下架。商品行必须一直在，才能被订单、收藏、购物车引用。
5. **Q8 答 4 明确存量数据迁移不在需求范围**。这给了我们重建表结构的空间，不需要为旧归档数据设计兼容迁移。

### 2.3 建议方案：单表 + 下架原因 + 历史视图

**核心思路：不再搬表，不再有独立的 `ARCHIVED` 状态；“归档”退化为商品行上的下架原因和时间。**

建议的字段：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `status` | `ON_SALE` / `OFF_SHELF` | 仍然只有两态，符合 Q2 |
| `off_shelf_reason` | `MANUAL` / `STOCK_ZERO` / `SOLD_OUT` | 对应“手动下架 / 库存耗尽下架 / 已售”三类 |
| `off_shelf_at` | 时间 | 下架时间，用于历史列表排序 |
| `archived_at`（可选） | 时间或空 | 如果业务坚持要“归档”概念，用它标记不可复售，但不再是独立表/独立状态 |

建议的派生规则：

| 来源 | 触发 | 下架时库存 | 能否复售 | 历史分类 |
| --- | --- | --- | --- | --- |
| `MANUAL` | 卖家手动下架（库存 > 0） | > 0 | **不能**（Q11：无重新上架入口；D6：终态只读） | 手动下架 |
| `STOCK_ZERO` | 卖家手动把库存改为 0 | 0 | **能**，补货 >0 **自动上架**（Q12 答 2） | 库存耗尽下架 |
| `SOLD_OUT` | 交易完成扣减后库存 = 0 | 0 | **能**，补货 >0 **自动上架**（Q12 答 1/2）；“已售”只是历史标签 | 已售 |

配套调整：

- **“历史商品”变成查询视图**：`status = OFF_SHELF`，可按 `off_shelf_reason` 分三类筛选；不再有“已下架（可复售）”和“已归档（终态）”的物理分区。
- **订单明细保存快照**：商品名、单价、数量；主图本期不做（Q12 最小集）。商品行永远在，订单也可以继续用 `goods_id` 关联。
- **不再写 `goods_history` / `intention_history`**。D5 已确认数据库可以重建：V3 直接建新表、删除旧表，不写迁移脚本；有数据的环境执行前备份。
- **“归档”这个词建议只用于 UI 文案**：可以叫“已下架（不可复售）”，不要再用“归档”指代一次数据库搬迁。

### 2.4 备选方案（不推荐）

**方案 B：只为“手动下架”保留历史表。** 手动下架的商品搬进 `goods_history`，库存归 0 下架留在当前表。

不推荐的原因：

- 订单、收藏、购物车仍可能引用该商品；搬表后要么加一套“历史商品引用”，要么让这些功能查两张表。
- “已售”不是终态，补货后仍可自动复售；搬进历史表后还要搬回当前表，复杂度更高。
- 单表 + 原因字段已经能表达同样语义，复杂度低得多。

### 2.5 剩余实现问题

1. `MANUAL` 手动下架是否需要二次确认（因为不可复售）？D6 已建议终态只读，前端还应提示“此操作不可撤销”。
2. `STOCK_ZERO` / `SOLD_OUT` 补货后自动上架，是否需要在卖家 UI 明确提示“已自动上架”，避免卖家以为还在下架。
3. “历史商品”统一展示三类（Q13 答 4）；是独立页面还是商品列表的“已下架”筛选，属于 UI 形态决定。
4. 旧表删除：D5 已确认可重建，V3 直接删除；有数据的环境执行前备份。

## 3. 阶段二的两个偏差

### 3.1 偏差一：手动下架被实现成“可重新上架”

**阶段二现状**

- `GoodsStatus` 有 `ON_SALE / FROZEN / OFF_MANUAL / OFF_ZERO` 四态。
- 手动下架走 `OFF_MANUAL`；重新上架接口要求 `OFF_MANUAL`、`confirm=true`、库存 ≥ 1。
- 状态模型把“手动下架”定义为可复售下架，恢复方式是“重新上架按钮 + 二次确认”。
- 阶段二 E2E 也按这个口径写了“手动下架后重新上架”的用例。

**阶段三口径**

- Q11 明确：手动下架没有重新上架操作，实际是终态；商品进历史商品，但记录保留。
- Q12 答 2 明确：库存归 0 下架（含交易完成扣到 0）补货 >0 后**自动上架**，不用点按钮。阶段二 `OFF_ZERO` 的“改库存 >0 自动上架”方向是对的；错的是 `OFF_MANUAL` 的“重新上架”入口。
- Q5 答 2 又明确：有非终态订单时，不允许手动下架或手动改库存为 0。
- D6：手动下架终态商品只读，不再改库存/类别，避免库存 0→正数误触发自动上架。

**影响**

- `OFF_MANUAL` 不再是“可复售”，而是 `OFF_SHELF(MANUAL)` 终态；`POST /re-list` 不能再对 `OFF_MANUAL` 使用。
- 前端“重新上架”按钮要移除；手动下架要加不可撤销提示，并对该商品禁用库存/类别编辑（D6）。
- 阶段二 E2E `03-seller-goods` 中“手动下架 → 重新上架”的用例要重写。
- 状态模型、README、AGENTS、OpenAPI、错误码都要同步。

**需要区分清楚**

- 手动下架终态，不等于“归档搬表”。商品行保留，订单/收藏/购物车仍可引用；只是不能再回到在售。
- 如果业务希望“手动下架后还能反悔”，就必须推翻 Q11；否则不要保留“重新上架”入口。

### 3.2 偏差二：限流过严，保护措施变成测试阻塞

**阶段二现状**

- `RateLimiter` 是进程内固定窗口，按 `scope + 客户端 IP` 计数，默认 10 次/分钟。
- Scope 有 `REGISTER / LOGIN / SUBMIT_INTENTION`。
- E2E 全部从 localhost 访问，所有请求共享同一个 IP 桶；批量注册/登录很快触发 429。
- E2E README 因此要求把三个限流值都改成 1000，等于在测试环境关掉限流。

**问题本质**

限流是**保护措施**，不是业务规则。阶段二把它做成了默认业务约束，导致：

- 正常开发和 E2E 被误伤；
- 测试通过“调高到 1000”绕过，而不是验证限流本身；
- 多用户共享出口 IP 时（公司/学校/NAT）也会被误伤。

**阶段三建议**

1. 删除 `SUBMIT_INTENTION` scope；订单/购物车/收藏**不新增限流**，因为 Q10 答 2 明确不限制下单频率。
2. 保留注册/登录限流，但改成可配置的**保护开关**：
   - 增加 `simple-shop.rate-limit.enabled`（默认：生产开、开发/测试关）；
   - 登录按“账号 + IP”而不是只按 IP，避免同一出口 IP 下的多个账号互相影响；
   - 注册可按 IP，但默认值放宽到合理范围（例如 30–60 次/分钟），不再用 10 次/分钟卡正常使用。
3. E2E 使用 `RATE_LIMIT_ENABLED=false` 或测试 profile，不再写“把限流调到 1000”。
4. 429 只作为保护性响应，不写进业务验收标准；限流器本身用单元测试覆盖即可。
5. 删除 `AppProperties.Queue`（队列上限 1000）以及相关配置、错误码、测试。

**需要团队拍板**

- 生产环境默认是否开启注册/登录限流；
- 默认阈值；
- 是否保留“按 IP”作为注册的唯一 key，还是改成“IP + 用户名”组合。

这些是工程决策，不需要问客户。

## 8. 附：建议术语

| 术语 | 建议定义 |
| --- | --- |
| 在售 | `ON_SALE`，可被买家浏览、搜索、加购、下单 |
| 已下架 | `OFF_SHELF`，退出买家浏览/搜索；收藏/购物车/订单仍可能引用 |
| 手动下架 | `OFF_SHELF + MANUAL`，卖家主动下架，库存 > 0，不可重新上架；终态只读（Q11、D6） |
| 库存耗尽下架 | `OFF_SHELF + STOCK_ZERO`，卖家把库存改为 0，补货 >0 自动上架（Q12） |
| 已售 | `OFF_SHELF + SOLD_OUT`，订单完成扣到 0；只是历史标签，补货 >0 自动上架（Q12） |
| 自动上架 | 库存从 0 改回 >0 时，商品自动回到 `ON_SALE`；仅适用于库存归 0 下架，不适用于手动下架（Q12、D6） |
| 历史商品 | 卖家后台查看已下架商品的视图，不是独立归档表 |
| 备货完成 | `PREPARED`，流程状态，不代表库存充足；不校验库存（D1） |
| 购物车 | 买家暂存的商品集合，只存 buyer+goods；数量/选中不落库（D3） |
| 订单详情 | 卖家推进状态/取消的统一页面；客户购买历史、商品订单记录、订单管理都从这里进入（D2） |
| 订单 | 买家一次提交的多商品购买记录，整单流转 |
| 订单明细 | 订单中的一行商品，含商品引用和下单时快照 |
| 取消 | 订单在完成前被买家或卖家终止，进入 `CANCELED` 终态，不影响库存 |

# 产品 Backlog（阶段三 · 挑战需求 B）

> **用途**：第三次阶段性评审材料；内容逐条录入禅道「在线购物系统-第14组 → 需求」。
> **范围**：挑战需求 B 的 B.1（订单升级）+ B.2（商品预选升级），以及由此触发的商品状态两态化改造。
> **不含**：数据库重建、限流改造、旧接口下线、后端分包重构——这些属**开发任务**，不进产品 backlog（见《需求澄清初步分析》§5.3）。
> **依据**：《挑战需求B》原文 7 条、《需求澄清记录》Q1–Q14、组长《需求澄清初步分析》v0.4、阶段二《状态模型设计》。

## 口径说明

| 字段 | 口径 |
| --- | --- |
| **ID** | 清单内序号，按「域 → 优先级」排列，与禅道需求编号无关 |
| **Name** | 简短、见名知意 |
| **Importance** | **1 = 最高**（缺了就不算交付），3 = 最低（可延后）。全表用 1/2/3 三档 |
| **Initial estimate** | 单位 **人天**，**初始**估算，评审后可调 |
| **How to demo** | 「先做 → 再做 → 得到什么」，**评审时照着念就能演示** |
| **Notes** | 需求出处（`B.1-1` 等）、关键约束、易错点 |

> ⚠️ 估算合计 **29 人天**（≈232 小时）。比阶段二（24.5 人天）多，因为新增了订单、购物车、收藏三个域。

### 引用编号约定

- `B.1-1`～`B.1-3`、`B.2-1`～`B.2-4`：《挑战需求B》原文条款定位（该文件条款本身无编号，此处为定位用）。
- `Q1`～`Q14`：《需求澄清记录》问题编号。**Q14 是团队内部确认，不是客户答复**。
- `D1`～`D6`：《需求澄清初步分析》§0.1 的**团队决策**，同样不是客户答复。
- `分析§N`：同上文档的章节。

### 估算是怎么来的

按功能点拆，每个点分别估前后端再相加。口径是**熟练开发者的纯开发时间**，不含调试与返工；对不熟悉技术栈的人，实际通常是估算的 **1.5～2 倍**。这是**初始估算**，做完前两条后按实际耗时校准。

### 本版被推翻的阶段二口径（写故事时容易照抄错）

| 阶段二 | 阶段三 |
| --- | --- |
| 购买意向 + 先到先得排队 | **订单**取代意向，排队机制整体下线 |
| 商品四态：在售 / 冻结 / 手动下架 / 库存清零下架 | **两态**：在售 / 已下架（下架原因另记） |
| 手动下架可点「重新上架」 | 手动下架是**终态**，无重新上架入口 |
| 补齐库存后要手动点重新上架 | 库存从 0 改回 >0，**自动上架** |
| 成交且卖完最后一件 → 搬进历史表「归档」 | **不搬表**，单表 + 下架原因 + 历史视图 |

## 一、订单域

| ID | Name | Importance | Initial estimate | How to demo | Notes |
| --- | --- | --- | --- | --- | --- |
| 1 | 购物车多选下单 | 1 | 2 | 买家登录 → 购物车勾选「相机」「三脚架」两件 → 点「结算」→ 生成 **1 笔**订单，详情里有 2 条明细，总金额 = 两件（单价 × 数量）之和 → 卖家「订单管理」里出现的是同 1 笔 | `B.2-3`、`Q1` 答 3：**1 笔订单含多商品明细**，不是每件 1 单。**下单只校验、不锁库存**（`Q3`）；数量在提交时随明细传（`D3`：购物车不落库数量）；任一明细库存不足则**整单拒绝**并提示具体商品（「整单拒绝」这一条是我们的落地口径，客户只规定了「下单校验」与「不允许负库存」，见 `分析§4.1`、`Q13` 答 1） |
| 2 | 我的订单列表（买家） | 1 | 2 | 买家点「我的订单」→ 看到自己的**全部**订单（进行中 / 交易完成 / 已取消），按下单时间倒序 → 每行显示订单号、商品名（多件显示「N 件」）、总金额、下单时间、当前状态 → 点任一行进详情 | `Q4` 答 4、`Q13` 答 5、`D4`：买家看自己的**全部**订单，进行中与已取消**都可见**。**没有超时自动取消**（`Q10` 答 3）；字段按最小集（`Q12` 答 3、`B11`） |
| 3 | 买家取消订单（发货前） | 1 | 1 | 买家打开一笔「待确认」订单 → 点「取消订单」并二次确认 → 状态立刻变「已取消」→ 换一笔「已发货」的订单，取消按钮不可用 | `B.1-2`、`Q13` 答 5：点一下**立即生效**，无对方审批。**取消不影响库存**（`Q3`）——注意 `Q1` 答 4 的「取消回补库存」已被 `Q3` 否定。取消后商品不自动回购物车/收藏 |
| 4 | 订单详情页（买卖双方共用） | 1 | 2.5 | 分别用买家、卖家账号打开同一笔订单 → 是同一页面：订单号、商品清单（名称/单价/数量）、总金额、下单时间、状态 → 买家侧只有「取消」（仅发货前可用），卖家侧有「推进状态 / 取消订单」 | `D2`：三个入口共用同一详情页，操作集中在此。**订单不记地址**（`Q12` 答 3），用户名/电话从账号读；商品已下架也能在订单里看 |
| 5 | 卖家订单管理页 | 1 | 2 | 卖家点「订单管理」→ 按状态 tab（待确认 / 已确认 / 备货完成 / 已发货 / 交易完成 / 已取消）切换 → 每个 tab 出对应订单 → 点任一行进详情 | `D2`：客户未定义全局订单页（`Q13` 答 2），本页是**团队补充**。**已取消的订单也在列表里**（`D4`） |
| 6 | 卖家推进订单状态 | 1 | 2.5 | 卖家打开「待确认」订单 → 依次点「确认订单」「备货完成」「开始发货」「交易完成」→ 状态逐步变化，完成后按钮全部置灰 → 试着跳级或回退：界面上根本没有这种按钮 | `B.1-1`、`Q1` 答 5：全部由卖家手动推进，**按序、不可跳过、不可回退、无超时**。`PREPARED`（备货完成）**不代表库存充足**（`D1`、`Q5` 答 1） |
| 7 | 卖家取消订单（完成前） | 1 | 1 | 卖家打开一笔「已发货」的订单 →「取消订单」仍可用 → 二次确认后变「已取消」→ 换成「交易完成」的订单，取消按钮不可用 | `B.1-3`、`Q1` 答 2：发货后商家**仍可**取消。**无退款、无召回**（系统无在线支付）；取消不动库存（`Q3`） |
| 8 | 交易完成扣库存与缺货拦截 | 1 | 2 | 库存 1 的商品：买家 A、B 各下一单（**两单都成功**，证明下单不锁）→ 卖家先完成 A 的单：库存 1→0，商品自动下架 → 再完成 B 的单：被拒绝，提示具体缺货商品，订单停在「已发货」 | `Q3` 无预占、`Q13` 答 1 不允许负库存、`D1`。**不允许部分完成、不自动取消、不扣成负数**；卖家只能取消订单或补货后重试。这是本版**已知取舍**（一货多单，先完成者得） |
| 9 | 卖家按客户/按商品查订单 | 2 | 1.5 | 卖家「客户管理」点某客户 → 看他的订单列表（含进行中/已取消）→ 进详情；再从某件商品看它的订单记录 → 进的是**同一个**详情页 | `Q13` 答 2 只定义了「客户购买历史」「商品订单记录」两处入口，且没说含不含进行中/已取消；`D2` 统一进同一详情页，`D4` 统一为双方都能看到进行中与已取消 |

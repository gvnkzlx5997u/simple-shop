## 2. 两端联调

### 2.1 联调目标

不是重新设计接口，而是验证：

1. 两个 SPA 对阶段二契约的字段、枚举、错误码理解一致；
2. 买家/卖家/后端三方的状态迁移一致（尤其在售、交易中、归档）；
3. 媒体、分页、时间、鉴权、校验错误在真实浏览器里可用；
4. 发现的问题能定位到前端、后端或契约，而不是“页面不对”这种笼统描述。

### 2.2 契约核对清单

联调开始前先按 [openapi.json](./openapi.json) 与 [前端交接文档](./前端交接文档.md) 对一遍：

| 项 | 阶段二口径 |
| --- | --- |
| 响应外壳 | `{code, message, data}`；参数错误额外带 `errors: [{field, message}]` |
| 业务错误 | 多数为 HTTP 200 + 业务码；只有 401/400/404/500 用 HTTP 状态 |
| 鉴权 | `Authorization: Bearer <token>`；买家/卖家令牌不能互用 |
| 枚举 | `status`（QUEUED/TRADING/SUCCEEDED/FAILED）、`fail_type`（SOLD_OUT/SELLER_VOIDED）、`goods_status`（ON_SALE/ARCHIVED）、`disposal`（VOIDED/REQUEUED） |
| 分页 | 请求 `page` 从 1 起，`page_size` 默认 10、上限 100；响应 `{items, page, page_size, total}` |
| 时间 | 后端 UTC ISO-8601；前端按本地时区展示 |
| 媒体 | 上传走 `POST /api/seller/media`（multipart：`file` + `purpose`），返回相对 URL；展示走 `/media/**` |
| 校验 | 缺字段/超长/越界/非法枚举 → 400 + 50002 + `errors`；语义错误（重名、尖括号、价格精度等）保留领域码 |
| 已删除的旧契约 | 买家 JSP、口令码、`/intent`、`/query`、`/api/seller/session` 等阶段一路径均不可再用 |

> `errors` 是 S4 新增的可选字段；当前前端主要按 `code` 映射文案。联调时不要把“页面未逐字段展示 errors”当成后端缺陷，除非需求明确要求字段级提示。

### 2.3 P0 联调剧本

按顺序执行；每一步记录“操作、期望、实际、结论”。

| ID | 剧本 | 关键期望 |
| --- | --- | --- |
| INT-01 | 卖家登录 → 新建一级/二级类别 | 类别树刷新可见；重复名、空名、一级挂商品被拒 |
| INT-02 | 卖家发布商品（主图 + 图集 + TEXT/IMAGE 描述） | 返回 `ON_SALE`；买家列表/详情可见；图片经 `/media` 可加载 |
| INT-03 | 买家注册 → 登录 → 浏览列表/筛选/详情 | 注册后自动/手动登录；分页、关键字、一级/二级类别筛选正确 |
| INT-04 | 买家提交意向 | 回执不含位次；卖家意向名单出现该买家，队首为最早提交 |
| INT-05 | 卖家对队首“进入交易” | 商品 `FROZEN`；买家详情可看但不可购买；再次进入交易被拒 |
| INT-06 | 卖家“标记失败 + 作废” | 商品回 `ON_SALE`；该意向 `FAILED/SELLER_VOIDED`；买家历史出现失败记录；库存不变 |
| INT-07 | 卖家“标记失败 + 重新排队” | 商品回在售；该意向回到队尾；下单时间不变；买家历史不出现（未终态） |
| INT-08 | 库存 >1 时“标记成功” | 扣 1 件；商品回 `ON_SALE`；该买家历史 `SUCCEEDED`；其余排队保留 |
| INT-09 | 最后 1 件“标记成功” | 商品 `ARCHIVED`；商品详情 404；卖家历史/买家历史可查；其余排队 `SOLD_OUT` |
| INT-10 | 库存改为 0 → 重新上架 | 在售改 0 变 `OFF_ZERO`；清零下架改 >0 自动回在售；有队列时禁止清零/下架 |
| INT-11 | 手动下架 → 重新上架 | 下架要求队列为空；重新上架必须 `confirm:true`，且库存 >0 |
| INT-12 | 买家/卖家令牌互调 | 买家 token 调卖家接口 401/10002；卖家 token 调买家接口 401/10002 |
| INT-13 | 参数校验 | 空 body、缺字段、超长、非法枚举返回 400/50002，`errors` 能定位字段；不出现 500 |
| INT-14 | 媒体边界 | 商品图 >5MB 返回 `20016`；描述视频可到 20MB；错误扩展名/外链被拒 |
| INT-15 | 改密 | 成功后旧 token 失效；用旧口令登录失败；新口令可登录 |
| INT-16 | 客户与历史 | 卖家客户列表/详情包含购买历史；买家历史只含自己的终态记录；分页在并集后 |

### 3.1 现状：旧套件不可复用

`simple-shop-test-e2e` 当前是**阶段一**用例：

- 买家端按 JSP 页面/口令码编写；

**结论：重写，不要逐条修补旧 spec。** 可以保留 Playwright 运行器、报告目录习惯和“真实浏览器 + 接口前置”的思路。

重写前先把旧 tests 移到 `archive/`（或删除），不要让它们留在 `testDir` 下被 `npx playwright test` 误跑。

### 3.2 建议目录

    ├─ helpers/
    │  ├─ config.ts                  # BUYER_URL / SELLER_URL / API_URL / 账号
    │  ├─ api.ts                     # 阶段二接口封装（登录、类别、发布、意向、裁决）
    │  └─ ui.ts                      # 登录、确认弹窗、上传等 UI 辅助

    │  ├─ 01-auth.spec.ts            # 买家/卖家登录、注册、令牌隔离
    │  ├─ 02-buyer.spec.ts           # 列表、详情、提交意向、历史
    │  ├─ 03-seller-goods.spec.ts    # 类别、发布、库存、上下架
    │  ├─ 04-trade.spec.ts           # 队列、进入交易、成功/失败、归档、历史

    │  └─ 06-security.spec.ts        # 绕过前端的负向调用、越权
    └─ fixtures/                     # 小图/小视频/测试数据

### 3.3 测试数据策略

1. 使用**独立 E2E 数据库/Compose 项目**，如 `simple-shop-e2e`；不要连开发库 `simple_shop`。
2. 每轮开始 `docker compose -p simple-shop-e2e down -v` 后重建，Flyway 自动建 12 张表并写入种子卖家。
3. 用**接口做前置**（建类别、发布商品、造意向），用**真实 UI 做被测流程**；避免所有步骤都点页面导致慢和脆。
4. 所有用户名、商品名带唯一后缀；测试结束不必手工清理，靠下一轮重建。
5. 卖家只有一个种子账号；E2E 并行执行会互相抢状态，初期保持 `workers: 1`、`fullyParallel: false`。
6. 运行期限流默认 10 次/分钟；如果套件注册/登录次数较多，给 E2E 后端加环境变量提高阈值，例如
   `SIMPLE_SHOP_RATE_LIMIT_REGISTER_PER_MINUTE=1000`、`...LOGIN...=1000`、`...SUBMIT_INTENTION...=1000`。

### 3.4 接口封装（阶段二）

`helpers/api.ts` 至少覆盖：

| 用途 | 请求 |
| --- | --- |
| 卖家登录 | `POST /api/seller/auth/session` `{account,password}` |
| 买家注册/登录 | `POST /api/buyer/auth/register`、`POST /api/buyer/auth/session` |
| 类别 | `POST /api/seller/categories/l1`、`POST /api/seller/categories/l2` |
| 发布商品 | `POST /api/seller/goods`（name/price/stock/category_id/description/main_image/gallery_images） |
| 商品列表/详情/库存/上下架 | `GET /api/seller/goods`、`GET /api/seller/goods/{id}`、`PUT .../stock`、`POST .../off-shelf`、`POST .../re-list` |
| 意向 | `POST /api/buyer/intentions`、`GET /api/seller/goods/{goodsId}/intentions` |
| 交易 | `POST /api/seller/intentions/{id}/trade`、`/success`、`/failure` `{disposal}` |
| 历史/客户 | `GET /api/seller/history/goods`、`GET /api/seller/customers`、`GET /api/buyer/history` |

注意：`failure` 的 `disposal` 只接受大写 `VOIDED`/`REQUEUED`；缺失/非法是 400/50002，不是旧的 30006。

### 3.5 选择器与可测性

当前前端大量使用 CSS 类名和中文文案，E2E 直接依赖容易随样式/文案变动。建议在联调阶段顺手加少量稳定钩子（不作为发布阻塞）：

- 买家：商品卡片、购买按钮、历史行、登录/注册表单；
- 卖家：发布表单、类别选择、意向行、进入交易/成功/失败按钮、裁决弹窗、历史行；
- 统一用 `data-testid`，例如 `goods-card`、`intention-row`、`trade-success`、`disposal-voided`。

没有 test id 时，优先 `getByRole` + 可访问名称，其次稳定文案，最后才用 CSS 类。

    cp .env.example .env    # 使用独立的 E2E 密码/项目

- **不作为发布/验收条件**；
- 不引入新的性能测试框架到主构建；
- 如时间允许，在**隔离环境**做一次冒烟：商品列表/搜索 20～50 并发、意向提交 10～20 并发、交易裁决 5 并发，记录 P95、错误率、数据库连接数；
- 结果只写“参考”，不设硬阈值；不要对生产库压测；
- 阶段一参考值（仅供对照）：查询 P95 ≤150ms、典型写 P95 ≤59ms；售罄归档满队列曾观测 1.9～2.8s，已按业务口径接受。

## 6. 风险与已知问题

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 旧 E2E 套件直接跑 | 全部失败，误判为回归 | 按 §3 重写，不修补旧 spec |
| E2E 连开发库 | 数据污染、不可重复 | 独立 Compose 项目/库，跑前重建 |
| 限流 10 次/分钟 | 批量注册/登录被 429/50001 | E2E 环境提高阈值或控制次数 |
| 卖家单账号 + 串行 | 并行用例互相抢状态 | 初期 workers=1；后续按商品隔离再并行 |
| 前端选择器脆弱 | E2E 随样式/文案失败 | 增加 `data-testid`，优先 role |
| 复用阶段一 MySQL 卷 | Flyway/表结构失败 | 备份后 `down -v`，按阶段二基线重建 |
| 云端镜像未重推 | 拉到旧 frontend，买家端缺失 | 重新构建推送，或只用 `deploy/` |
| Playwright Edge 依赖 | 若有CI，CI runner 无 Edge | 启用CI时改用 Chromium |
| 媒体孤儿 | 磁盘增长 | 运维监控；后续可选清理任务 |
| 性能数据被误当门禁 | 阻塞发布 | 明确“可选参考” |

## 0.1 阶段二适用性（2026-10-30，先读）

阶段二已移除 JSP，后端只提供 REST；买家端与卖家端是独立前端工程。阶段一的「买家 JSP 在 `/`、
卖家 SPA 在 `/seller/`」描述仅作历史参考，不能直接套到当前代码。

**部署本身没有新增运行时依赖**：

- 生产仍只需要 Docker / Docker Compose、MySQL 8、JDK 21；Testcontainers 只在测试阶段使用，
  不进入 `simple-shop.war`，生产机不需要安装，也不需要 Docker-in-Docker。
- MySQL 基础镜像仍用 `mysql:8.0`；本次开发机实测服务端为 **8.0.44**。测试容器使用同一 tag，
  避免测试与生产版本漂移。
- 镜像构建仍可用 `mvn -Dmaven.test.skip=true clean package`，S6 没有改变构建产物。
- 若在构建机执行测试门禁：默认 `mvn clean verify` 会用 Testcontainers 启动 `mysql:8.0`，
  需要可用的 Docker；无 Docker 时用 `mvn -Plocal-mysql clean verify` 连接本机
  `simple_shop_test`。两者都通过后再交付。
- 阶段二前端拆为 `simple-shop-buyer-frontend` 与 `simple-shop-seller-frontend`；
  `deploy/docker-compose.yml` 已改为阶段二三容器口径（见第 5、8 章）。
- **从阶段一升级**：阶段二重建了 V1 基线，**不能复用阶段一的 `simple-shop_mysql-data`**。
  首次启动前先备份，然后 `docker compose down -v`（或换项目名/卷名）再 `up -d --build`；
  直接挂旧卷会因表结构/ Flyway 校验和不一致而启动失败。

## 1. 部署目标与总体形态

### 1.1 目标与两种部署选项

目标：在**一台宿主机**上得到一套可用系统，包含：

1. **买家端**（Vue 3 SPA，由 nginx 静态托管，挂在根路径 `/`）；
2. **卖家后台**（Vue 3 SPA，由 nginx 静态托管，挂在 `/seller/`）；
3. **后端 REST 接口**（Maven 打成可执行 war，内嵌 Tomcat，`java -jar` 启动；只提供 `/api` 与 `/media`，不输出 HTML）；
4. **MySQL 8** 独立容器（schema 由 Flyway 自动迁移，不手工建表）；
5. **商品图片与审计日志持久化**（容器重建不丢数据）。

落地目录提供**两个等价选项**，按目标机情况**选一**（两者互斥，不要在同一台宿主机上同时运行）：

| 选项 | 目录 | backend / frontend 镜像来源 | 启动命令 | 适用场景 |
| --- | --- | --- | --- | --- |
| **甲：本地构建** | `deploy/` | compose 在宿主机上现构建（`simple-shop-backend/Dockerfile`、`deploy/frontend/Dockerfile`），构建期可用 §3.2 的镜像源加速 | `cd deploy && docker compose up -d --build` | 首次交付、源码有改动、目标机能联网构建；无需预先准备镜像仓库 |
| **乙：云端镜像** | `deploy-cloud/` | 直接从 Docker Hub 拉取预构建镜像 `lrhg173c/simple-shop:backend`、`lrhg173c/simple-shop:frontend`（阶段二镜像需重新构建推送；`mysql:8.0` 仍从 Docker Hub 拉取） | `cd deploy-cloud && docker compose pull && docker compose up -d` | 目标机不装构建工具链、追求快速复现同一份镜像；镜像已由构建方推送 |

两个选项的**服务拓扑、网络、卷、健康检查、端口与 URL 规划完全一致**（见 §1.2、§1.3），差别只在 backend / frontend 两段是 `build:` 还是 `image:`；两者都使用 `name: simple-shop`，因此卷名与网络名相同，**从甲切到乙（或反向）数据自然延续**。

选项乙关于镜像源的取舍（2026-10-16 静态校验）：

- **删去 `IMAGE_PREFIX` 是正确的**：backend / frontend 不再在目标机构建，构建参数 `REGISTRY` 已无作用；且这两个镜像位于 Docker Hub 用户仓库（`lrhg173c/...`），而轩辕免费版只代理 `docker.io` 的 `library/` 官方镜像，前缀对它们无效；
- 选项乙唯一仍需从 Docker Hub 拉取的基础镜像是 `mysql:8.0`：目标机**必须能访问 Docker Hub**（或自建 registry 代理），否则部署会先卡在拉取这一步；
- 选项乙的镜像标签目前是**可变标签**（`:backend` / `:frontend`）：日常重建覆盖没问题，正式上线建议改为版本化标签，以便按 §10.3 回滚。

> 选项乙的 `docker-compose.yml` 已用 `docker compose config` 静态解析通过，与选项甲**逐项等价**（仅镜像来源不同）；
> 但阶段二镜像需重新构建并推送，且**尚未在真实 Docker 上实测**，本轮实测结论以选项甲为准（见 §8.1）。

### 1.2 容器拓扑

三个容器 + 三个命名卷 + 一个自定义 bridge 网络；**只有 nginx 暴露宿主端口**：

| 容器 | 镜像 | 对外端口 | 内部端口 | 持久卷 | 作用 |
| --- | --- | --- | --- | --- | --- |
| `frontend` | nginx:1.27-alpine | **80 -> 80** | 80 | 无（静态资源在镜像内） | 托管买家 `/` 与卖家 `/seller/` SPA，并反代 `/api`、`/media` |
| `backend` | eclipse-temurin:21-jre + war | **不映射** | 8080 | `backend-images`、`backend-logs` | REST + `/media` |
| `mysql` | mysql:8.0 | **不映射** | 3306 | `mysql-data` | 数据库 |

依赖顺序：`mysql`（健康后）→ `backend` → `frontend`。

```
                   宿主机（Docker Engine / Docker Desktop）
  ┌──────────────────────────────────────────────────────────────┐
  │   网络 simple-shop-net（bridge，仅容器间可达）                 │
  │                                                              │
  │   浏览器 ──80──► ┌────────────┐                              │
  │                  │ frontend   │  /            买家 SPA        │
  │                  │ nginx:1.27 │  /seller/    卖家 SPA        │
  │                  └─────┬──────┘  /api /media 反代 backend    │
  │                        │ /  /seller/  /api  /media            │
  │                  ┌─────▼──────┐   JDBC 3306   ┌───────────┐  │
  │                  │ backend    │ ─────────────►│ mysql:8.0 │  │
  │                  │ JRE21 + war│               │simple_shop│  │
  │                  └─────┬──────┘               └─────┬─────┘  │
  │                        │                            │        │
  │        backend-images ─┘                        mysql-data ───┘
  │        backend-logs                                          │
  └──────────────────────────────────────────────────────────────┘
```

### 1.3 URL 规划（买家在 `/`，卖家在 `/seller/`）

| 访问路径 | 由谁处理 |
| --- | --- |
| `http://<host>/`、`/goods`、`/goods/:id`、`/login`、`/register`、`/history` | 买家 SPA（nginx 静态 + history 回退） |
| `/assets/**` | 买家 SPA 构建产物（文件名带 hash，可长缓存） |
| `http://<host>/seller/`、`/seller/login`、`/seller/publish`、`/seller/history`、`/seller/password` | 卖家 SPA（nginx 静态 + history 回退） |
| `/seller/assets/**` | 卖家 SPA 构建产物（文件名带 hash，可长缓存） |
| `/api/**` | 后端 REST（买家与卖家共用） |
| `/media/**` | 商品图片与描述媒体（后端文件系统目录） |

实现方式：

1. 后端**保持默认根 context-path**（即**不设置** `SERVER_SERVLET_CONTEXT_PATH`），只处理 `/api` 与 `/media`；
2. 买家 **构建 base `/`**，卖家**构建 base `/seller/`**（`createWebHistory(import.meta.env.BASE_URL)` 自动跟随）；
3. nginx 规则：`/seller/` 静态 + `try_files` 回退；`/` 静态买家 + `try_files` 回退；
   `/api/`、`/media/` 反代到 `backend:8080`。

> 两个前端 `npm run dev` 不受影响：base 只在 `vite build` 时传入。

### 2.1 D-1 为什么选「可执行 war + java -jar」

仓库的 `pom.xml` 交付的就是**可执行 war**（`spring-boot-maven-plugin` repackage，内嵌 Tomcat + `tomcat-embed-jasper`），
`java -jar target/simple-shop.war` 是交接文档里所有真实端口验证走的路。选它**零改动**。
另一条路（把 war 丢进外部 Tomcat 容器）必须先把 embedded Tomcat 与 `jakarta.servlet-api` 改成 `provided`，
`pom.xml` 注释明确写着这一项「本轮不动，待与组长确认」，故不采用。

### 2.2 D-2 为什么选方案乙

- 买家端 JSP 的所有链接都由 `${pageContext.request.contextPath}` 生成，后端起在根路径时全部是 `/query`、`/intent/new` 这类根路径；
  一旦改成别的 context-path，部署环境就和仓库文档/接口文档产生差异。方案乙**不动后端**。
- 卖家 SPA 是纯静态产物，把 base 换成 `/seller/` 是构建参数级改动，且对本地开发无影响。
- 代价：卖家后台的 URL 是 `http://<host>/seller/`，不是根路径；演示时注意这一点。

### 2.3 D-5 账号与口令（已确认）

- MySQL 应用账号：`simpleshop`，**只授予 `simple_shop` 库权限**，不用 root 跑应用；
- root 口令只用于初始化与运维（备份），**不写进应用配置**；
- `deploy/.env` 存放真实口令，**加入 .gitignore 不提交**；仓库只提交 `deploy/.env.example`（占位值）；
- 卖家初始账号仍是 `seller / Abcd@1234`（写在 V2 迁移脚本里，**不在本次部署改动范围**）；
- 按 AC-29 要求，§10.4 已包含「交付后立即改密」与「忘记口令时的数据库层重置步骤」。

### 2.4 D-7 构建期测试（已确认不跑）

- 镜像构建用 `mvn -B -Dmaven.test.skip=true clean package`（连测试源码都不编译，最快）；
- **212 个后端用例是提交前的门禁**：默认 `mvn clean verify` 用 Testcontainers 启动 `mysql:8.0`，
  需要 Docker；没有 Docker 时用 `mvn -Plocal-mysql clean verify` 连接本机 `simple_shop_test`。
  不要因为镜像里跳过测试就取消这道门禁；
- Testcontainers 只影响测试执行，不会进入 WAR；生产部署不需要 Docker 运行测试容器；
- 前端 `npm run build` 里的 `vue-tsc` 类型检查保留（构建时间可接受）。

## 3. 前置条件与构建期镜像源

### 3.1 前置条件

| 项 | 要求 |
| --- | --- |
| Docker Engine | **23+**（推荐 24+；需要 BuildKit 支持 `RUN --mount=type=cache`，Docker Desktop 默认开启） |
| Docker Compose | **v2**（`docker compose` 子命令，支持 `depends_on.condition: service_healthy`） |
| 宿主机 | Linux x86_64 或 Windows + Docker Desktop（WSL2 后端） |
| 资源建议 | 2 vCPU / 4GB 内存 / 10GB 磁盘（Maven 构建阶段较吃内存） |
| 端口 | 宿主 **80** 必须空闲（Windows 上确认没有 IIS/其它服务占用） |

### 3.2 构建期镜像源（推荐方案，记录日期 2026-10-13）

> ⚠️ **有效期说明**：下表是测试机当前在用的镜像源，记录于 **2026-10-13**。
> 第三方镜像站可能变更、限流或停止服务，**接手人员请自行核对可用性**；
> 不可用时按「回退方式」列退回官方源即可，不影响部署结构。

| 用途 | 推荐源 | 回退方式 |
| --- | --- | --- |
| Maven 依赖 | `https://mirrors.tencent.com/nexus/repository/maven-public/` | 删掉 `settings.xml` 里的 `<mirror>` 即回到 Maven Central |
| npm 依赖 | `https://registry.npmmirror.com` | 删掉 `.npmrc` 或用 `--registry=https://registry.npmjs.org` |
| Docker 基础镜像 | 轩辕镜像**免费版**：`docker.xuanyuan.me`（仅 docker.io、仅 pull） | 去掉 `docker.xuanyuan.me/library/` 前缀，回到 Docker Hub 官方 |

**Maven**：写成 `settings.xml` 的 `<mirror>`（`mirrorOf` 用 `*`），构建镜像时 COPY 到 `/root/.m2/settings.xml` 并用 `-s` 显式指定：

```xml
<mirror>
  <id>tencent</id>
  <name>Tencent Cloud Maven</name>
  <url>https://mirrors.tencent.com/nexus/repository/maven-public/</url>
  <mirrorOf>*</mirrorOf>
</mirror>
```

**npm**：在前端工程放一个 `.npmrc`（`registry=https://registry.npmmirror.com`），或在 Dockerfile 里执行 `npm config set registry https://registry.npmmirror.com`。

**Docker**：⚠️ **不要**用 `daemon.json` 的 `registry-mirrors`——轩辕官方指南明确说明它是兼容方案，
Docker 在镜像源报错时会**自动回退到官方源**，不推荐作为默认；正确做法是**在镜像名里显式写域名**：

```dockerfile
FROM docker.xuanyuan.me/library/mysql:8.0
```

- 免费版**只支持 docker.io**、**只支持 pull**、**不支持 ghcr/gcr 等**专属域；
- 本项目用到的全部基础镜像恰好都是 Docker Hub 官方 `library/` 镜像，免费版覆盖：
  `mysql`、`maven`、`eclipse-temurin`、`node`、`nginx`、`alpine`；
- 建议在 Dockerfile 里用 `ARG REGISTRY=docker.xuanyuan.me/library/`，`FROM ${REGISTRY}mysql:8.0`，
  切换镜像源时只改一个 ARG 即可（这也让回退官方源变成 `--build-arg REGISTRY=`）。

## 5. 组件设计

### 5.1 MySQL 容器

- 镜像：`mysql:8.0`（开发库为 8.0.44；如需与开发完全对齐可 pin `mysql:8.0.44`）。
- 启动参数：`--character-set-server=utf8mb4 --collation-server=utf8mb4_unicode_ci`。
  说明：V1 迁移脚本**对每张表都显式写了** `DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci`，
  所以**表级**排序规则本身有保障；这里仍显式设置服务端默认值，是为了让**库**的排序规则与设计说明书 §3.3 一致
  （`MYSQL_DATABASE` 建库时用的是服务端默认排序规则），避免库/表口径出现隐性差异。
- 环境变量：`MYSQL_ROOT_PASSWORD`、`MYSQL_DATABASE=simple_shop`、`MYSQL_USER=simpleshop`、`MYSQL_PASSWORD`。
- 初始化脚本挂载到 `/docker-entrypoint-initdb.d/`，**只在数据目录为空时执行一次**；
  脚本内容：只做 `ALTER DATABASE ... CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci`（幂等）。
  账号由 compose 的 `MYSQL_USER` 自动建好并授权，脚本**不重复 GRANT**，以免与 `DB_USERNAME` 变量耦合。
- 健康检查：`mysqladmin ping`，供 backend 的 `depends_on: condition: service_healthy` 使用。
- 数据卷：`mysql-data:/var/lib/mysql`（**必须持久化**；不用 Windows 绑定挂载，权限与性能都不稳）。
- **不映射宿主端口**（D-3）；如排障需要临时连库，用 `docker compose exec mysql mysql ...`。

### 5.2 后端容器

多阶段构建：

1. **构建阶段** `maven:3.10.0-eclipse-temurin-21-noble`：
   - 构建上下文是后端工程根目录 `simple-shop-backend/`；
   - `.mvn/` 已被 `.dockerignore` 排除，容器内使用默认 `/root/.m2`，不会把本机相对路径带进去；
   - 执行 `mvn -B -s /build/maven-settings.xml -Dmaven.repo.local=/root/.m2/repository -Dmaven.test.skip=true clean package`；
     配合 BuildKit 缓存挂载 `--mount=type=cache,target=/root/.m2/repository`；
   - 镜像源走 §3.2 的腾讯云 Maven；
   - 产出 `target/simple-shop.war`。
2. **运行阶段** `eclipse-temurin:21-jre`：
   - 非 root 用户运行（自建 `appuser`，uid 10001）；
   - 从构建阶段 COPY 出 `simple-shop.war` 到 `/app/app.war`；
   - 预建并 `chown` 目录：`/app/data/images`、`/var/log/simple-shop`（命名卷首次挂载会继承镜像内目录的属主）；
   - 安装 `curl` 用于容器 healthcheck；
   - `ENV TZ=UTC`、`AUDIT_LOG_PATH=/var/log/simple-shop`；
   - 启动：`sh -c "exec java -Duser.timezone=UTC -DAUDIT_LOG_PATH=/var/log/simple-shop $JAVA_OPTS -jar /app/app.war"`（`exec` 保证信号能传到 JVM）；
   - 卷：`backend-images:/app/data/images`、`backend-logs:/var/log/simple-shop`；
   - **不设置** `SERVER_SERVLET_CONTEXT_PATH`；
   - **不映射宿主端口**（D-3）。

> 阶段二后端不再提供任何 HTML/JSP，只处理 `/api/**` 与 `/media/**`；媒体目录由 `MEDIA_DIR=/app/data/images` 指定。

### 5.3 前端 + nginx 容器

多阶段构建：

阶段二使用**一个组合镜像**同时托管两个 SPA，构建上下文是**仓库根目录**
（`deploy/frontend/Dockerfile`）：

1. **买家构建** `node:24-bookworm-slim`：`npm ci` → `npm run build`（base `/`），产出 `dist/`；
2. **卖家构建** `node:24-bookworm-slim`：`npm ci` → `npm run type-check` →
   `./node_modules/.bin/vite build --base=/seller/`（不要用 `npm run build` 后接 `--base`，`run-p` 的
   `{@}` 传参会把参数弄乱），产出 `dist/`；
3. **运行阶段** `nginx:1.27-alpine`：
   - 买家 `dist/` → `/usr/share/nginx/html`；
   - 卖家 `dist/` → `/usr/share/nginx/html/seller/`；
   - 拷贝 `deploy/frontend/nginx.conf`；暴露 80。

nginx 要点：

- `client_max_body_size 25m;`：后端 multipart 上限 25MB（描述视频 20MB），不能小于它；
- 买家 `location /` 与卖家 `location /seller/` 都用 `try_files ... index.html` 做 history 回退；
- `location = /seller { return 301 /seller/; }` 补上不带斜杠的入口；
- `/api/`、`/media/` 反代到 `backend:8080`，带 `Host`、`X-Real-IP`、`X-Forwarded-For`、`X-Forwarded-Proto`；
- `/assets/`、`/seller/assets/` 长缓存（文件名带 hash）；
- 不需要 `JSESSIONID` 粘滞：鉴权走 `Authorization: Bearer`。

## 7. 数据库初始化与就绪顺序

1. `mysql` 容器首次启动 → 建库 `simple_shop`（utf8mb4 / utf8mb4_unicode_ci）+ 应用账号 `simpleshop`；
2. `mysqladmin ping` 通过后，`backend` 才启动（compose healthcheck 门控）；
3. backend 启动即连库，**Flyway** 执行 `V1__baseline_schema.sql`、`V2__seed_initial_data.sql`（12 张业务表 + 卖家账号）；
4. `ddl-auto=validate` 再核对实体与库结构一致——**应用能起来，本身就是一条结构一致性断言**。

⚠️ 要点：

- **已发布的迁移脚本不得修改**（改注释也会导致 Flyway 校验和失配、启动直接报错）；
- 若后端起得比 MySQL 快而报 `Communications link failure`，靠 `restart: unless-stopped` 自愈，或加 `restart: on-failure:5`；
- 本次**不导入** `simple_shop.sql` 快照（D-4=A）。该文件在 `C:/workspace/simple-shop/simple_shop.sql`，在 git 工程之外，仅作历史参考。

### 10.5 常见故障排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| backend 启动即退出，日志有 `Communications link failure` | MySQL 未就绪或账号/口令错 | 看 `docker compose logs mysql`；确认 `.env` 与实际一致；`restart` 会自动重试 |
| `Flyway validate failed` / checksum mismatch | 迁移脚本被改过 | 恢复脚本原文；已上线库不要改历史脚本 |
| `Schema-validation: missing table` | 库不是 utf8mb4/unicode_ci 或 Flyway 没跑 | 检查库排序规则与启动日志 |
| 图片 404 | `backend-images` 卷未挂载或目录属主不对 | 确认卷挂载在 `/app/data/images`，容器内该目录属主为运行用户 |
| `/seller/history` 刷新 404 | SPA 构建 base 与 nginx 路径不一致 | 确认用 `--base=/seller/` 构建，且 `dist` 拷到 `/usr/share/nginx/html/seller/` |
| `/seller/assets/*` 404 | dist 少拷了一层 seller 目录 | 与上一条同源，检查 COPY 目标路径 |
| 买家页 404/白屏 | 买家 `dist` 未拷到 `/usr/share/nginx/html` 或 `try_files` 回退缺失 | 检查组合镜像 COPY 目标与 `location /` |
| `/api` 返回 nginx 静态页/404 | `/api/` 没有反代到 backend | 检查 `location /api/` 的 `proxy_pass http://backend:8080;` |
| 上传大图报 413 而非 20016 | nginx `client_max_body_size` 太小 | 调到 25m（后端 multipart 上限） |
| 启动报 Flyway checksum/missing table | 复用了阶段一旧 `simple-shop_mysql-data` | 备份后 `docker compose down -v`，按阶段二基线重建 |
| 会话频繁掉线 | backend 被重启 / 多副本 | 本部署为**单副本进程内会话**，不可水平扩容；重启即丢会话（已接受） |
| 拉取基础镜像失败 | 轩辕免费版限流/变更 | 见 §3.2 回退方式，去掉镜像前缀回到官方源 |

## 11. 已知限制与风险（须让评审看到）

1. **单副本会话**：会话在 backend 进程内（`ConcurrentHashMap`），因此 backend **不能多副本、不能负载均衡**；容器重启会丢会话。这是已接受的决策（Q-3 / `9-O`）。
2. **图片必须持久卷**：归档不搬迁图片文件，`backend-images` 丢失即永久性数据丢失（`DEC-09`）。
3. **MySQL 单点**：无主从、无高可用；`12-P4` 的月度可用率 >= 99% 需要额外的运维措施（上游为开放项）。
4. **构建依赖外网**：镜像构建阶段需要访问 §3.2 的镜像源；镜像源不可用会直接导致构建失败。
5. **归档满队列性能**：1000 条意向归档实测 1.7~2.8s，未达 `12-P1`「写 P95 <= 1s」（交接说明 §7.1 已登记）。部署本身不改变该结论。
6. **审计日志无测试保证**：仅基本审计（用户已明确降低要求）。
7. **时间口径**：库内、日志、接口一律 UTC；展示层东八区转换由前端/买家 JSP 完成。
8. **卖家后台不在根路径**：方案乙下卖家入口是 `/seller/`，根路径 `/` 是买家端。这是本次部署引入的约定，已记入附录 C。

```nginx
server {
    listen 80;
    server_name _;
    client_max_body_size 10m;

    root /usr/share/nginx/html;
    index index.html;

    # 卖家 SPA（构建 base=/seller/，产物在 /usr/share/nginx/html/seller/）

        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_pass http://backend:8080;
        expires 7d;
```

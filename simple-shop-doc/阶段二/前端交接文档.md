## 1. 后端现状与 API 文档获取

后端已实现阶段二全部业务接口(30 个路径),按功能分包,前后端分离,后端只提供 REST 与媒体文件,不再输出任何 HTML。

**接口文档的三种获取方式**:

| 方式 | 位置 | 用途 |
| --- | --- | --- |
| Swagger UI | 后端启动后访问 `http://<host>:8080/swagger-ui/index.html` | 在线浏览与调试,可逐接口试调用 |
| OpenAPI JSON | `GET /v3/api-docs` | 机器可读契约;TS 类型与请求封装据此生成 |
| 离线快照 | 本目录 [`openapi.json`](./openapi.json)(v1.0.0,2026-10-30 导出) | 无后端环境时对照;后端接口变更后需重新导出 |

生产环境用 `SPRINGDOC_ENABLED=false` 关闭文档端点;开发环境默认开启。

前端 TS 类型建议直接由 openapi.json 生成(如 `openapi-typescript`、`orval` 等工具),不要手抄字段;后端 DTO 的 JSON 键一律 snake_case(如 `goods_id`、`page_size`、`create_at`)。

## 2. 全局约定(两端一致)

- **统一响应体** `{code, message, data}`;`code=0` 为成功。业务拒绝返回 **HTTP 200 + 业务码**,只有会话失效(401/code 10002)、参数错误(400)、资源不存在(404)、服务端错误(500)使用 HTTP 状态码。前端按业务码映射文案,不直接展示后端 message。
- **字段校验错误**:参数错误为 HTTP 400 + code 50002,并额外返回 `errors: [{field, message}]`;`field` 是请求体 JSON 键(如 `category_id`、`description[0].type`)。成功响应与其他业务错误不带 `errors` 键。
- **枚举字段**:`disposal`(VOIDED/REQUEUED)、`goods_status`(ON_SALE/ARCHIVED)、`status`(QUEUED/TRADING/SUCCEEDED/FAILED)、`fail_type`(SOLD_OUT/SELLER_VOIDED)均按大写枚举值传输;非法值返回 400/50002。
- **鉴权**:`Authorization: Bearer <token>`;买家与卖家令牌不能互用。`/api/public/**` 无需令牌。注册/登录接口除外。
- **分页**:请求 `page`(从 1 起)、`page_size`(默认 10,上限 100);响应 `{items, page, page_size, total}`。
- **时间**:一律 UTC ISO-8601 字符串(如 `2026-10-24T08:30:00Z`),前端按本地时区渲染。
- **媒体**:上传走 `POST /api/seller/media`(multipart,字段 `file` + `purpose=GOODS_IMAGE|DESCRIPTION_MEDIA`),返回相对 URL;图片 `/media/goods/...`、描述媒体 `/media/description/...`;发布商品时回填这些 URL,后端回验。媒体直接经 `/media/**` 访问。
- **开发联调**:Vite dev server 代理 `/api` 与 `/media` 到后端(同源,无 CORS);生产由 nginx 反代。

## 3. 卖家前端任务(改造现有工程)

现有 `simple-shop-frontend` 是阶段一的 Vue 3 + Vite + TypeScript + Pinia 单商品 SPA,需按阶段二模型改造。

### 3.1 实施步骤(按顺序)

1. **阅读 API 文档,同步契约**:打开 Swagger UI 或对照 `openapi.json`,梳理阶段二全部卖家接口与 DTO;更新 `types/` 与 `api/` 层——阶段一的单商品接口(发布/详情/意向/历史)已全部变化,以阶段二契约为准重写,不得沿用旧定义。
2. **改造现有工程**:按 3.2 的保留/重写清单改造 `simple-shop-frontend`(建议更名为 `seller-frontend`);登录态、HTTP 封装与通用组件可复用,业务页面按新模型重写。
3. **连调测试**:启动后端(见第 5 节),逐页面联调;每完成一块跑 `npm run type-check`、`npm run build`;全部页面完成后与后端一起过主流程(发布 → 提交意向 → 进入交易 → 裁决 → 归档 → 历史/客户)。

### 3.2 保留与重写清单

| 处置 | 内容 |
| --- | --- |
| 保留复用 | Vite/Vue/Pinia/Axios 工程骨架、`http.ts`、`token.ts`、auth store、AppLayout、ConfirmDialog、Pagination、ToastHost、StatusTag、base.css |
| 重写 | 路由、`api/product`、`api/intention`、`api/history`、types、validation、Home/Publish/History/Detail 等业务页面 |
| 新增 | 类别管理、客户管理(列表/详情+购买历史)、多商品列表、库存/下架/重上架、交易裁决(进入交易/成功/失败+裁决)、历史记录(历史商品列表/详情+意向名单) |
| 删除 | 单商品槽位假设、口令码相关页面与逻辑、阶段一的交易流水展示 |

### 3.3 页面与接口对照

| 页面 | 接口 |
| --- | --- |
| 登录/退出/改密 | `POST/DELETE /api/seller/auth/session`、`PUT /api/seller/auth/password` |
| 商品列表(按状态/类别/关键字筛选) | `GET /api/seller/goods` |
| 发布(类别/库存/描述块/图片) | `POST /api/seller/media`(先上传)、`POST /api/seller/goods` |
| 商品详情/库存/上下架/改挂 | `GET/PUT/POST /api/seller/goods/{id}` 系列 |
| 类别管理 | `GET/POST/PUT/DELETE /api/seller/categories/**`、`GET /api/public/categories` |
| 意向名单与交易裁决 | `GET /api/seller/goods/{goodsId}/intentions`、`POST /api/seller/intentions/{id}/trade|success|failure` |
| 客户管理 | `GET /api/seller/customers`、`GET /api/seller/customers/{id}` |
| 历史记录 | `GET /api/seller/history/goods`、`GET /api/seller/history/goods/{id}` |

### 3.4 交互要点(易错)

- 进入交易**只能对队首**操作;被拒 `30002`(非队首)/`30004`(已有交易中)时按业务码提示。
- 标记成功的响应 `goods_status` 区分 `ON_SALE`(回在售)与 `ARCHIVED`(已归档,商品从当前列表消失,去历史记录页看)。
- 标记失败必须选裁决方式 `VOIDED`(作废)或 `REQUEUED`(重排队尾)。
- 手动下架、库存清零下架都要求队列为空(后端拒 `20022`);清零下架没有"重新上架"按钮——改库存 >0 提交即自动上架;手动下架的重新上架要二次确认(body `{"confirm":true}`)。
- 交易中(冻结)的商品禁止改库存/改挂/下架(后端拒 `20021`),前端按钮置灰。
- 令牌存储 key:`simple-shop.seller.token`;改密成功后全部卖家会话失效,需跳登录页。

## 4. 买家前端任务(新建工程)

买家端此前不存在,需新建 `buyer-frontend`,技术栈与卖家端一致(Vue 3 + Vite + TypeScript + Pinia),可复制卖家端的 `http.ts`/`token.ts` 模板与基础样式,但不引入 monorepo,两工程独立构建。

### 4.1 实施步骤

1. **阅读 API 文档**:买家端只涉及 6 个接口(见 4.2),先从 `openapi.json` 同步定义。
2. **新建工程**:按 4.2 页面清单实现;无购物车、无支付、无收货地址、无客服。
3. **连调测试**:与后端联调注册/登录 → 浏览/搜索 → 详情 → 提交意向 → 我的历史主流程。

### 4.2 页面与接口对照

| 页面 | 接口 | 说明 |
| --- | --- | --- |
| 商品列表/搜索 | `GET /api/public/goods` | 仅在售;keyword、category_id、分页;类别树 `GET /api/public/categories` |
| 商品详情 | `GET /api/public/goods/{id}` | 在售、交易中可见(交易中只读);下架/归档 404 |
| 注册 | `POST /api/buyer/auth/register` | username、password、phone、default_location(选填) |
| 登录/退出 | `POST/DELETE /api/buyer/auth/session` | 令牌 key `simple-shop.buyer.token` |
| 提交意向 | `POST /api/buyer/intentions` | 详情页"我要购买"一键提交,body 仅 `goods_id`,无表单;回执**不含位次**,界面不得展示排队位置 |
| 我的历史 | `GET /api/buyer/history` | 仅终态(成功/失败);按下单时间倒序分页;只读 |

### 4.3 交互要点(易错)

- 浏览无需登录;提交意向与查看历史必须登录(未登录 401 → 引导登录)。
- 买家**没有**改资料、改密码、找回密码、撤销意向、查看位次的入口(后端也无此接口)。
- 历史字段仅商品名、下单时间、结果、交易时间;不含价格与图片。
- 重复提交允许(同一商品可多次点"我要购买"),不必做前端去重提示;限流阈值 10 次/分钟/IP,超限 `50001`。

## 5. 联调环境

| 项 | 值 |
| --- | --- |
| 后端启动 | `simple-shop-backend/` 下 `mvn spring-boot:run`,默认 `http://localhost:8080`,需要本机 MySQL |
| 数据库 | 开发库 `simple_shop`(Flyway 自动建表);不迁移阶段一数据 |
| 种子卖家 | 账号 `seller`,初始口令 `Abcd@1234`(首次登录后建议改密) |
| 买家账号 | 无预置,经注册接口产生 |
| 限流 | 注册/登录/提交意向各 10 次/分钟/IP(开发期如不便可在 application.yml 调高) |
| 媒体目录 | 默认 `./data/media`;开发期上传的文件落在后端工作目录 |
| 错误码全集 | 见后端 `common/api/ErrorCode.java` 或 Swagger UI 各接口的 code 说明;前端按业务码映射文案 |

## 6. 验收标准

- 两端 `npm run type-check`、`npm run build`(如有单测则 `npm run test`)全绿。
- 卖家主流程 E2E 可走通:登录 → 类别 → 发布 → 名单 → 进入交易 → 成功/失败裁决 → 售罄归档 → 历史/客户查询(Playwright 脚本待 S6 统一编写,前端先保证手工可走通)。
- 买家主流程 E2E 可走通:注册 → 登录 → 浏览/搜索 → 详情 → 提交意向 → 我的历史。
- 界面不出现后端 message 原文,一律按业务码映射;401 统一跳登录。
- 生产构建由 nginx 托管:买家 SPA 在 `/`,卖家 SPA 在 `/seller/`;`/api`、`/media` 反代后端(见 `deploy/frontend/`)。

## 7. 交接后的后端配合事项

- 前端联调中发现契约问题,以后端 `master` 的 springdoc 为准修正文档;若确需接口变更,后端评估后同步更新 `openapi.json` 快照并通知前端重新生成类型。
- S6 测试与部署脚本已收口(Testcontainers + 本机 MySQL 兜底、`deploy/` 组合前端镜像);剩余为两端联调修复、Playwright E2E 与性能测试。

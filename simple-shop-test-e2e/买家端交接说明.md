> 对应代码：`simple-shop-buyer-frontend`（阶段四 B1–B6 完成时的状态）。
> 对应后端：`simple-shop-backend`，契约见 `simple-shop-doc/阶段四/openapi.json` 与《阶段四契约交接》。

### 1.3 固定行为（可直接断言）

- **未登录访问任何需登录路由** → 跳 `/login?redirect=<原路径>`；401 同样统一跳登录。
- **「去结算」现在跳 `/checkout`**，不再直接下单；提交订单在结算页的 `checkout-submit`。
- **下单成功仍跳 `/orders/:id`**（这一跳故意保留，减少用例改动面）；支付入口在详情页 `order-pay-entry`。
- **支付成功从支付页跳回 `/orders/:id?paid=1`**，详情页据此显示「支付成功」notice。
- **取消订单、确认收货、删除地址都是内联二次确认**（「确认 X / 再想想」），没有 `window.confirm`，也没有 dialog。
- **地址表单是弹窗**：`address-form` 在 `role="dialog"` 里，点遮罩或「取消」关闭；Esc **不关闭**（明确不做）。
- **售后入口只在交易完成订单的明细行出现**，跳 `/aftersales/apply?order_id=&order_item_id=`。
- **倒计时来自 `pay_deadline`**，不要按 24 小时自己算；归零只提示 + 给「刷新」，不本地改状态。
- 金额形如 `¥245.50`；购物车合计在 `cart-total`，结算合计在 `checkout-total`。

## 3. 造数据建议（不连库）

买家端阶段四的联调数据全部走接口造，可参考这套顺序：

1. 卖家登录：`POST /api/seller/auth/session`，body 是 **`{account, password}`**（不是 `username`）。
2. 类别为空时先建一级/二级；商品需先 `POST /api/seller/media?purpose=GOODS_IMAGE` 上传主图再发布。
3. 买家注册（**只传 username/password/phone**）→ 登录 → 建地址（首条自动默认）。
4. 下单 `POST /api/buyer/orders` `{address_id, items}` → 支付 `/pay` `{payment_channel}`。
5. 卖家依次 `/confirm` → `/prepare` → `/ship`（ship 必填 `carrier`、`tracking_no`，单号可含换行）。
6. 买家 `/confirm-receipt` 成交；之后按 `order_item_id` 申请售后，卖家 `/complete` `{result}` 或 `/cancel`。

几个可直接用来造边界的开关与口径：

- **支付失败**：`PAYMENT_MOCK_FAIL_CHANNELS=ALIPAY` 重启后端，不要改请求参数。
- **成交缺货（60004）**：订单已发货后，把在售商品库存改到小于明细数量（保持 >0，否则会自动下架，
  而已下架商品成交**不扣库存**、直接完成）。
- **重复退款（81004）**：同一订单项完成过一次退款类售后后，再完成一次退款类即被拒；换货不占额度。
- **超时**：不要把定时器纳入主流程；直接断言「过期订单支付返回 83002」更稳。

## 4. 踩过的坑（写用例前先看）

1. **`vite dev` 只监听 `[::1]`**：写 `localhost:5174` 可以，`127.0.0.1:5174` 连不上。
2. **本机有系统代理**：命令行 `curl` 要加 `--noproxy "*"`。
3. **Playwright 用 `channel: 'msedge'`**；`video` 选项在本机不可用。
4. **后端下单不清购物车**：要测「下单后购物车变化」，看前端有没有删行。
5. **会话在进程内**：后端重启后旧 token 全失效，用例要重新登录。
6. **阶段四必须按 V4 重建库**：V4 给订单加的是 `NOT NULL` 无默认值的收货快照列，**订单表必须为空**。
   开发库与 E2E 库都按「备份 → 删库 → 启动由 Flyway 跑到 V4」重建。**不要用关闭校验的方式硬绕**。
7. **`scripts/db.js` 只用于重建库与手工夹具**，任何测试脚本都不要引用它——前端测试不连库。
8. **单号只断言格式**：订单 `SO+yyyyMMdd+6位`、售后 `AS+yyyyMMdd+4位`，同日多轮序号会累加。

## 5. 已下线 / 已变更的东西（别照着旧用例写）

- **`PENDING_CONFIRM`「待确认」**：删除。下单后直接 `PENDING_PAYMENT`，付款后 `PAID` 才轮到卖家确认。
- **卖家「交易完成」端点与按钮**：删除。`COMPLETED` 只由买家确认收货推进。
- **注册「默认交易地点」**：删除，且后端拒收未定义字段（多传即 400）。地址改由地址簿维护。
- **20020「有未完成订单禁止下架/改 0」**：规则删除，码位停用。
- **10008**：码位停用，前端已删声明与文案。
- 阶段三的 `/history`、「我要购买」、意向与归档相关文案，早在阶段三就已下线。

## 6. 手工夹具的现状

`simple-shop-d1-fixtures.sql` 是**阶段三时期**的商品/类别夹具（`GD-D1-*`、`CL1-D1`/`CL2-D1`）。
它只动商品与类别表，理论上与 V4 兼容，但**本次没有在 V4 库上验证过**，用之前先自己跑一遍。
E2E 造数请一律走接口，不要依赖这份 SQL。

## 7. 还没有自动化 / 没有实测的部分

- 真正的并发渲染（两个浏览器同时改同一份购物车）——本地状态按浏览器隔离，跨标签页不共享。
- 弱网/超时下的加载态（明细失败重试可用 route 拦截覆盖；真实弱网未覆盖）。
- **图片上传的边界拦截**（类型/大小/9 张上限）：前端有校验与单测，浏览器端由人类单独验证。
- 结算页「无地址」空态：代码路径存在，本次未实测（「无勾选行」空态已在回归走查中确认）。
- 移动端适配：暂缓，只做基础响应式。

## 8. 手动自测怎么起环境

```bash
# 后端（库按 V4 重建后）
cd simple-shop-backend && mvn spring-boot:run
# 买家端
cd simple-shop-buyer-frontend && npm run dev      # http://localhost:5174
```

批量造数时给后端加 `RATE_LIMIT_ENABLED=false`。自动化请另起 E2E 环境
（重建 `simple_shop_e2e` + 关限流 + 三个服务），在 `simple-shop-test-e2e` 下跑 `npx playwright test`。
买家纯逻辑另有单元测试：`simple-shop-buyer-frontend` 下 `npm run test:unit`。

按这个顺序点一遍能覆盖主链：
注册 → 建地址 → 逛商品加购 → 购物车去结算 → 结算选地址提交 → 详情去支付 → 选渠道支付 →
（卖家用接口 confirm/prepare/ship）→ 详情看物流 → 确认收货 → 明细行申请售后 → 我的售后看列表与详情。

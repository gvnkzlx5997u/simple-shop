# simple-shop 后端

> 单卖家在线购物系统的后端：商品两态、订单七态、购物车与收藏、地址簿、支付（Mock）、物流与售后。本文写**结构与业务口径**，接口清单与字段不在这里维护。
>
> **阶段进度：阶段四（挑战需求 C）已交付。** 覆盖 `V4` 迁移、七态订单、支付、收货地址、物流、售后、取消与超时退款。整体进度见[根 README](../README.md)。

## 技术基线

| 项 | 取值 |
| --- | --- |
| 构建 | Maven，可执行 war |
| Java | 编译目标 21，构建 JDK ≥ 21 |
| Spring Boot | 3.5.16 |
| 持久化 | Spring Data JPA + Hibernate，MySQL 8.0.16+ |
| 迁移 | Flyway + 手写 SQL |
| 会话 | 进程内 token，买家/卖家按角色隔离 |
| 前端 | 前后端分离，后端只提供 REST 与媒体文件 |

## 目录结构

```text
src/main/java/com/simpleshop/
  common/      统一响应与错误码、鉴权与当前用户、媒体落盘、限流、UTC 时间、主键生成、审计
  account/     买家/卖家账号、卖家客户查询
  address/     收货地址簿
  category/    一级/二级类别
  goods/       商品、图片、描述块、状态与下架原因
  inventory/   库存（独立聚合，商品只存展示属性）
  order/       订单、订单项、七态流转、收货快照、物流
  cart/        购物车行（不含数量与勾选）
  favorite/    收藏
  payment/     支付端口与 Mock 网关、取消退款流水
  aftersale/   售后单、处理结果、售后退款
src/main/resources/
  application.yml      配置（全部可用环境变量覆盖）
  db/migration/        Flyway：V1 基线 → V2 种子 → V3 阶段三 → V4 阶段四
db/阶段三/              阶段三迁移归档（不参与运行，仅供对照）
```

功能包内 `service/` 放接口、`service/impl/` 放实现，`controller/` 下按 `seller` / `buyer` / `publicapi` 分目录；跨功能只依赖对方的 `api/` 端口。

**依赖方向由 ArchUnit 守门**：`common` 保持隔离、Controller 不碰 Repository、功能包之间不允许循环依赖。阶段四三个新包的边界固定：`order` 可用 `address.api` / `payment.api` / `goods.api`；`payment` 是叶子（接真实渠道也不许反向 import 订单）；`aftersale` 只用 `order.api` 与 `order.enums`，不碰订单的实体、仓储、服务与 DTO。

## 构建与运行

在 `simple-shop-backend/` 目录执行：

```bash
mvn clean compile              # 仅编译，不需要数据库或 Docker
mvn test                       # 默认用 Testcontainers 启动一次性 MySQL；需要 Docker
mvn -Plocal-mysql test         # 改用本机 simple_shop_test；不需要 Docker
mvn clean verify               # 默认同上，含迁移测试与 ArchUnit
mvn -Plocal-mysql clean verify # 本机 MySQL 兜底路径
mvn spring-boot:run            # 启动，需要 MySQL；默认使用 simple_shop
```

- 默认测试镜像为 `mysql:8.0`，与部署使用同一 tag；容器只存在于测试 JVM。首次运行需拉取 `mysql:8.0` 与 `testcontainers/ryuk`，之后走本机镜像缓存。
- `-Plocal-mysql` 用 `TEST_DB_URL`（默认 `jdbc:mysql://localhost:3306/simple_shop_test`），迁移测试会创建随机命名临时库并删除；账号取 `TEST_DB_USERNAME`/`TEST_DB_PASSWORD`，缺省回退 `DB_USERNAME`/`DB_PASSWORD`。
- Testcontainers/JUnit/ArchUnit 都是 `test` scope，不进 `target/simple-shop.war`，生产部署无需 Docker。
- 应用启动时 Flyway 依次执行 V1→V4，随后由 `ddl-auto=validate` 校验实体与表结构。
- 构建产物为 `target/simple-shop.war`，可 `java -jar` 启动。镜像由本工程 `Dockerfile` 构建，编排见 [`deploy/`](../deploy/README.md)。

## 业务口径

### 类别与商品

- 类别只有两级；商品必须挂二级类别，一级只做分组。一级类别删除前必须没有二级子类，二级类别删除前必须没有当前商品引用。
- 商品发布后名称、价格、描述、图片不可修改；库存可调、类别可改挂。
- 主图可选；图集最多 8 张且必须先有主图；主图 + 图集合计最多 9 张。
- 描述是 TEXT / IMAGE / VIDEO 的有序内容块，不存 HTML；文本总长 1000 字符，单块同样最多 1000。
- 商品只有 `ON_SALE`、`OFF_SHELF` 两态；已下架必须带原因 `MANUAL` / `STOCK_ZERO` / `SOLD_OUT` 与下架时间，在售时两者都为空。
- 库存是**独立聚合**：商品表只存展示属性，库存变更一律经 `inventory` 服务，不要绕过它直接改商品表字段。
- 在售改库存为 0 → 自动下架（`STOCK_ZERO`）；库存耗尽下架的商品改回大于 0 → 自动上架并清空原因。手动下架是终态：库存只读，类别仍可改挂。
- 没有「有未完成订单就不许下架 / 不许清零」的限制（阶段四删除该规则，`20020` 停用）：库存不预占、成交才扣减，卖家随时可下架或调库存；成交扣减到 0 仍自动下架（`SOLD_OUT`）。
- 卖家列表可按状态与下架原因筛选；原因只能与 `OFF_SHELF` 组合，否则按参数错误拒绝。
- 买家列表与详情只放行 `ON_SALE`；`purchasable` 以后端返回为准，等价于「在售且有库存」。

### 地址

- 三个字段：收货人、手机号、一行详细地址；不做省市区、邮编，也不允许换行。电话沿用账号口径（7~20 位数字与 `-`）。
- 每个买家最多 10 条地址，第一条创建即默认；之后只能通过「设为默认」切换，编辑不动默认标记。
- 同一买家最多一条默认由数据库唯一索引（生成列 `default_key`）兜底；设默认时先清旧默认再置新的，两次 flush 保证不撞索引。
- 删除默认地址后，由剩余里最新创建的一条补位；全部删光则没有默认。
- 订单只存下单时的地址快照，地址之后怎么改、删都不影响历史订单。
- 归属按令牌主体判定，他人地址一律按不存在返回。

### 订单

- 七态：`PENDING_PAYMENT` → `PAID` → `CONFIRMED` → `PREPARED` → `SHIPPED` → `COMPLETED`，另有终态 `CANCELED`；整单流转，只能按序前进一格，不可跳级或回退。
- 交易完成只由买家确认收货推进，卖家没有「完成订单」接口；成交时在售商品按明细数量扣减，任一不足整单拒绝、订单停在已发货，补货后可重试；已下架商品成交不扣库存。
- 买家在进入「已发货」前可取消；卖家在「交易完成」前可取消（含已发货）。取消不改变库存，取消人与时间只记操作日志。
- 已支付订单取消即全额原路退款，写一条 `ORDER_CANCEL` 退款流水；待支付取消不退款。重复取消返回成功但不会重复退。
- 下单起 24 小时未支付由定时任务自动取消（启动即扫、按批处理、每笔独立事务），不改库存、不退款。
- 发货后卖家可以改承运商、单号与备注，订单状态不变。这是高频修正动作，**不写审计**；只有已发货且未取消的订单允许。
- 下单必须选一个已存在的收货地址，订单存收货人/手机号/地址快照；下单只校验商品在售与库存，不锁库存行、不预占。
- 支付走 Mock 网关：四个渠道都成功，失败由 `mock.fail-channels` 注入给测试用；支付失败不写 `payment_channel` / `paid_at`，订单停在待支付。
- 下单只收明细与数量，同一订单内重复商品按参数错误拒绝，不做数量合并。
- 列表与详情只回订单头，**不含订单项**；明细按订单 ID 单独查，列表分页、明细不分页，避免一层返回里出现两层分页。
- 订单头统一返回收货快照、支付（渠道、时间）、物流（承运商、多行单号、备注）与退款汇总：`refunded_amount` = 取消退款 + 售后退款，`aftersale_count` 为售后条数（售后列表按 `order_id` 单独查）。
- `pay_deadline` 只在待支付订单上有值，前端据此倒数，不要自己按 24 小时算；订单项带 `order_item_id`，售后按订单项而不是商品定位。
- 买家只能读自己的订单，他人订单按不存在处理；卖家可读全部订单。
- 「订单管理」「按客户」「按商品」三个入口在后端只是同一个列表的筛选条件（`status` / `buyer_id` / `goods_id` 可组合），进详情一律按订单主键查；按商品筛选经订单项反查订单 ID。

### 售后

- 只有**交易完成**的订单可以按订单项申请售后；同一订单项可以多次申请（换货之后仍可再申请），是否受理由卖家线下判断，申请阶段不拦。
- 申请只填标题、描述与图片。售后类型（退货退款 / 仅退款 / 换货）由卖家处理时登记，买家申请时不选。
- 图片先走买家上传接口（只接受售后凭证用途，单张 5MB、JPG/PNG），申请时只传返回的 URL；外链与跨用途地址都会被媒体服务拒绝。
- 列表按申请时间倒序分页，可按状态、订单 ID 筛选；详情只能看自己的。单号形如 `AS202611260001`。
- 卖家登记结果时三选一：`RETURN_AND_REFUND` / `REFUND_ONLY` / `EXCHANGE`。退款类结果由后端按订单项「单价 × 数量」算金额，不接受前端传值；换货不产生退款。
- **同一订单项只能退款一次**：完成并退款前锁订单项行再判额度，第二次拒绝；额度同时由数据库唯一索引兜底（同一订单项最多一条「已完成 + 退款类」）。换货不占额度。
- **售后退款只落售后单**：不写支付流水、不改库存、不上架——否则订单详情的 `refunded_amount` 会把同一笔钱算两遍。
- 完成是终态：已完成不能再取消或改结果；取消只对未处理的单有效，重复取消按成功返回。取消后可以重新申请，生成新单号；「取消」与「拒绝」是同一个动作，没有独立的已拒绝态。

### 购物车与收藏

- 购物车行只存「买家 + 商品 + 加购时间」；数量与勾选由前端 localStorage 维护，不落库、也不产生接口。
- 「买家 + 商品」由唯一键保证唯一：重复加购不新增行，也不刷新加购时间。移除与取消收藏幂等，行不存在同样返回成功。
- 是否可选在读取时由商品状态派生，不落库：`selectable` 与 `detail_available` 都等价于「商品在售」。**库存不足仍可选中**，缺货由结算时校验拦截。已下架行保留展示并带下架原因，复售自动恢复。
- 购物车列表不分页：前端要算总价与角标，翻页会漏行。收藏列表分页。
- 转收藏整批成功或整批拒绝：入参里有一件不可选就整单拒绝、一行不动；只转本购物车真实存在的行，`moved_count` 恒等于真正转过去的件数。写收藏与删购物车行在同一事务。
- 详情页的「收藏 / 已收藏」按商品查单条状态，不要靠翻收藏列表判断——列表分页，超过一页就会漏。

### 客户

- 客户列表与详情只读：字段仅限用户名、电话与注册时间，不提供搜索、统计或导出。客户资料里**没有收货地址**——地址属买家侧地址簿，订单只存下单时的快照。
- 购买历史不在客户详情里内嵌：卖家订单列表支持按 `buyer_id` 筛选，直接按订单粒度查该客户的订单即可。

## 数据库

- 开发库 `simple_shop`、测试库 `simple_shop_test`、E2E 库 `simple_shop_e2e` 互相隔离，不要混用。
- 活动迁移脚本：V1 基线（12 张表）、V2 种子（卖家账号）、V3 阶段三（删意向与归档四表、商品加下架原因与时间、建订单/订单项/购物车/收藏）、V4 阶段四（订单加收货/支付/物流字段并转七态、删买家默认交易地点、建地址与售后四表）。迁移后共 16 张表。
- `V3` 归档在 `db/阶段三/`，与执行版本保持一致；**已发布的迁移脚本不得修改**，只能追加新版本。
- `V4` 要求订单表为空：开发库与 E2E 库按「备份 → 删库 → 启动由 Flyway 跑到 V4」重建，旧订单不迁移。
- 数据库按阶段重建，旧数据卷不能跨阶段复用。种子卖家账号 `seller`，初始口令 `Abcd@1234`，首次登录后请修改。

## 代码约定

- 时间写入统一使用 `DatabaseTimeProvider`，库内一律 UTC；实体时间字段保留 `@JdbcTypeCode(SqlTypes.LOCAL_DATE_TIME)`。
- 会话区分买家与卖家角色，令牌不能互用。
- 请求 DTO 在边界做存在性、长度与上下界校验（`@Valid` + Bean Validation），失败返回 HTTP 400 + 参数错误码并附 `errors: [{field, message}]`，字段名使用请求体 JSON 键。
- 账号字段的语义校验仍在 Service 层：用户名/账号 1~50 字符且不含空白/控制字符/尖括号；密码至少 8 字符且 UTF-8 不超过 72 字节；电话为 7~20 位数字与 `-`。注册只收用户名、口令、电话，多传未定义字段会 400。
- 类别名、商品名去首尾空白后 1~50 字符，拒绝控制字符、换行与尖括号；价格必须大于 0、不超过 999999.99 且最多两位小数；发布库存至少为 1。
- 描述内容块按 `sort_no` 保存纯文本、图片、视频的混排顺序；纯文本整段 1000 字符上限由应用层校验。
- 媒体 URL 必须指向对应用途目录下已落盘的文件；发布时按用途、扩展名和文件存在性回验，拒绝外链和目录穿越。文件名由服务端生成，数据库只存相对 URL。
- 商品状态与下架原因只经实体的 `offShelf(reason)` / `backOnSale()` 变化，不提供单独写状态或原因的方法。
- 控制器只调用本功能 Service，跨功能读取走 Service 或只读端口。
- 事务内不可回滚的副作用（审计日志、改密后的会话撤销）统一经 `AfterCommit` 推迟到提交成功之后。
- 注释只保留职责与非显然约束，写清「为什么」，不引用文档编号。
- 测试不断言审计日志与运行日志：日志是排查手段，不是契约；测试只断言业务状态、返回码与库内数据。

### 改商品/订单状态或迁移时的检查清单

只改表或只改一处实现最容易留下不一致，涉及状态或表结构时逐项过一遍：

1. 枚举定义与查询条件（筛选、校验、DTO 序列化）；
2. Flyway 新迁移（不改已发布脚本），必要时带旧状态值换算；
3. 状态迁移与并发测试（跳级、回退、重复提交、并发扣减）；
4. 买家端与卖家端的文案、筛选项与按钮显隐；
5. 状态与库存的一致性（在售无原因、已下架有原因；`MANUAL` 库存大于 0，另两类为 0）。

### 1.2 现状的**硬约束**（方案必须绕开的坑）

| # | 约束 | 后果与对策 |
| --- | --- | --- |
| **C1** | **实体无参构造是 `protected`**，Service 在 `com.simpleshop.service` 包内**无法 `new Goods()`** | 发布商品需新建实体。**对策**：在 `persistence.entity` 包内新增 `public` 的**实体工厂**（`GoodsFactory` / `IntentionFactory` / `TradeHistoryFactory`），只暴露「业务创建」所需的最小入口；或由 `Service` 通过仓储 `save()` 传入一个包内构造出的实例。**推荐前者**，理由见 §3.4 |
| **C2** | `GoodsHistory`、`IntentionHistory` **没有任何 JPA 回调**，也无 `public` 构造 | 归档时**必须显式赋值全部字段（含 `id` 原始值、时间列原始值）**。**对策**：同上，用 `public` 工厂 + 显式 setter；**绝不可依赖回调** |
| **C3** | `GoodsRepository` **不提供任何更新名称/描述/图片/价格的方法**，且 `result` 列**恒为 NULL** | 「发布后不可修改」（`BR-15`）由接口层「不存在更新接口」+ Service 层「不调用 setter」共同落实。`Goods.setResult()` **任何业务路径都不得调用** |
| **C4** | `TradeHistoryRepository` **不提供 delete/update**（继承的 `delete*` 约定为「不得使用」） | 流水只追加 |
| **C5** | `IntentionHistoryRepository` **无 `queueOrder`/`token` 属性** | 归档时这两列**不复制**（历史表根本没有）。编译期即杜绝误用 |
| **C6** | `QueueSequence.id` 是 `Integer`，固定为 `1` | 分配序号固定传 `QueueSequence.FIXED_ID` |
| **C7** | `findByGoodsId(goodsId, pageable)` / `findByGoodsHistoryId(id, pageable)` **不内建排序** | 调用的 `Pageable` **必须显式带排序**，否则顺序不确定 |
| **C8** | `countGroupedByIntentionIdIn` 返回 `List<Object[]>`，**未产生流水的意向不出现在结果中** | 调用处须把「缺失」视为 `0`，不是错误 |
| **C9** | `countNonTerminal` **只报数、不判定** | 队列上限 1000 的拒绝判定在 Service |
| **C10** | 全部 `...ForUpdate` 脱离事务即失效 | 所有写方法必须 `@Transactional` |

### 1.3 需要新增的支撑件（本轮要建的）

| 件 | 用途 |
| --- | --- |
| `pom.xml` 依赖补充 | `spring-boot-starter-web`、`spring-boot-starter-validation`（见 §2.1） |
| `application.yml` 调整 | **删除** `spring.main.web-application-type: none`（否则不启 web 容器）；新增 multipart 上限、图片目录、会话超时配置 |
| 实体工厂 | 绕开 `protected` 构造（§3.4） |

| 时间序列化 | Jackson 配置：`LocalDateTime`(UTC) → ISO 8601 `...Z`；价格 → 字符串两位小数 |

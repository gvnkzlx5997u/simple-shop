# 5. 会话（session + token）设计

### 5.1 结论（含「容器化 + 单后端容器是否要引入缓存」这个问题的答复）

> **✅ 已定（Q-3）**：部署形态为**容器化**，大致分为**后端 / 数据库 / 卖家前端**三个容器；**未开发完，暂不实施部署**，但**会话方案现在定下来**：**会话存储在后端容器内解决**。

**结论：容器化 + 单后端容器，会话存储 `不需要` 引入缓存组件（Redis 等），也不需要新建会话表。**

| 问题 | 答复 |
| --- | --- |
| 单后端容器是否需要 Redis 之类的缓存来存会话？ | **不需要。** 进程内 `ConcurrentHashMap<String, Session>` 即可 |
| 那容器化带来了什么新要求？ | **几乎没有**——只要后端**保持单容器（单实例）**。原有的三个硬要求（30 分钟滑动超时、改密后全会话立即失效、401+`10002`）在进程内实现**最简单也最准确** |
| 什么时候必须回头改？ | 后端**扩到多容器 / 多副本 / 负载均衡**时，见 §5.4 的复核触发条件 |

**理由（四条，逐条针对「容器化会不会破坏进程内会话」这个疑虑）**

| # | 理由 |
| --- | --- |
| 1 | **「容器」不等于「多实例」**。会话共享问题的根源是**同一份内存被多个进程各持一份**——只有「多副本 / 负载均衡」才会出现。三容器方案里**后端只有一个容器**，所有请求都落到它，进程内 `Map` 就是**唯一且正确**的会话视图，不存在「A 副本不知道 B 副本发的 token」的问题 |
| 2 | **`C-04` 明确排除缓存组件、`A-04` 要求并发排序完全依赖数据库**。引入 Redis 只为存几 KB 的会话，是**用一个被需求排除的组件去解决一个不存在的问题**，纯属增加部署面、成本与失败点 |
| 3 | **并发压力为零**。系统**只有一个管理员账号**（`FR-01`、`O-10`），会话数量上限是「个位数」——正常情况下**恰好 1 个**。进程内 Map 的容量与并发问题都不存在 |
| 4 | **容器重启丢会话是可接受、甚至更可取的**。后端容器重启（发布 / 崩溃重拉）会让所有 token 失效，用户重新登录一次。这**恰好符合 `DEC-17` 的口径**（改密后全部会话失效 = 会话本来就不追求跨重启存活），也符合 `NFR-04`「30 分钟无操作退出」这种**短生命周期**的设计意图。为「重启后仍保持登录」而持久化会话，收益极低 |

> **一句话**：**「容器化」推不出「要缓存」**——推出「要缓存」的是**多副本**，而当前方案是单后端容器。所以**会话留在后端容器进程内**，与 `C-04` 无冲突。

**⚠️ 与 `OPEN-01` 的关系**：上游 `OPEN-01`（部署形态）此前未决，已明确是**唯一可能反向影响既有约束的开放项**（「容器化多实例 ⇒ 会话需共享存储，而 `C-04` 已排除缓存组件」）。**本次确认的是「容器化 + 单后端容器」，因此该张力被消解**——因为张力只在「多实例」时才成立。复核触发条件见 §5.4。

### 5.2 实现（保持单实例的进程内方案）

| 项 | 决策 | 理由 |
| --- | --- | --- |
| 存储 | **进程内 `ConcurrentHashMap<String, Session>`** | 见 §5.1 的四条理由；`C-04` 排除 Redis；后端为**单容器** |
| token 形态 | **`SecureRandom` 生成的 32 字节 → URL-safe Base64**（≈43 字符） | 无状态、无碰撞风险；**不用 JWT**（JWT 无法「立即全部失效」而不引入黑名单，与 `DEC-17` 冲突） |
| 会话内容 | `token`、`account`、`lastAccessAt`、`expireAt` | 单账号，无需角色/权限字段 |
| **超时** | **30 分钟无操作**：每次请求刷新 `lastAccessAt`；空闲超过 30 分钟即失效（宽容 ±1 分钟，`12-P7`） | `DEC-13`、`NFR-04` |
| **改密后全失效** | `changePassword` 成功后**清空该 `account` 的全部会话** | `DEC-17`、`NFR-04`（清空是同步的，旧凭证**立即**失效，远优于「≤5s」） |
| 清理 | 定时任务（`@Scheduled(fixedDelay = 60s)`）清除过期会话 | 防内存泄漏（虽然量极小，但保留自愈习惯） |
| 失效响应 | `HTTP 401` + `code = 10002` | `11.3.2` |

**实现组件**

```java
public final class Session { String token; String account; Instant lastAccessAt; Instant expireAt; }

@Component
public class SessionStore {
    private final ConcurrentMap<String, Session> sessions = new ConcurrentHashMap<>();

    String create(String account);              // 生成 token 并登记（含 30 分钟 expireAt）
    Optional<Session> validate(String token);   // 校验 + 【原子】滑动刷新 lastAccessAt（返回 empty = 10002）
    void remove(String token);                  // 退出
    void removeAllFor(String account);          // 改密后全失效（value 扫描 + 删除）
    void purgeExpired();
}
```

> **⚠️ `validate` 的滑动刷新必须是原子的**：它是典型的「读—改—写」——若写成 `get(token)` 后立刻 `session.lastAccessAt = now`，而 `Session` 是可变的共享对象，会有可见性问题（读到过期值、或并发下 lost update 导致会话**提前**失效）。
> **正确做法（任选其一）**：
> ① **不可变 `Session`（推荐）**：`Session` 用 `record`，刷新时 `sessions.computeIfPresent(token, (k, old) -> old.touched(now))` —— `computeIfPresent` 对同一 key 是原子的；
> ② 若坚持用可变对象，则 `Session` 内部用 `volatile` 字段，且避免依赖「读后再写」的复合操作。
> **不要**用 `Collections.synchronizedMap` + 手动 `get`/`put` 组合——那只能保证单个操作原子，**保证不了复合操作**。
> **超时判定不要用 `HashMap.get` 的返回值直接判空来隐式过期**：过期必须是**显式**的（`expireAt` 比较），否则「已过期但还没被清理任务删掉」的会话会被放行。

**拦截器**：`SellerAuthInterceptor` 注册在 `/api/seller/**`，**排除** `POST /api/seller/session`（登录）。
- 从 `Authorization: Bearer <token>` 取 token → `SessionStore.validate`；
- 失败 → 抛 `10002`（由 `GlobalExceptionHandler` 输出 401）；
- 成功 → 把 `account` 放入 request attribute。

> **为什么不用 Spring Security**：本项目只有一种凭证（自定义 token）、一个账号、不需要角色/权限模型。引入 Security 会带来过滤器链、CSRF、默认登录页等一整套需要额外解释和关闭的配置，而收益为零。

### 5.3 容器化对其它部分的要求（**会话之外，别漏了这几条**）

> 会话不需要缓存，但容器化**确实**给另外几处提了要求。这些不是本轮代码要写的，但**必须写进部署文档/交接说明**，否则上线时会踩。

| # | 项 | 要求 | 依据 |
| --- | --- | --- | --- |
| 1 | **图片目录必须挂持久卷** | `./data/images`（§6）在容器里，**不挂卷则容器重建即全丢**。而 `pic_url` 已写进库里、**归档也不搬迁图片**（`DEC-09`、`DEC-34`），即**历史商品的图片也依赖这批文件**——丢了就是永久性数据丢失 | `C-08`、`A-06`、`NFR-11`、`OPEN-02`（备份须覆盖图片目录） |
| 2 | **容器时区设为 UTC** | 镜像里 `ENV TZ=UTC`（或 JVM `-Duser.timezone=UTC`）。虽然全项目已禁止 `LocalDateTime.now()`、连接串也写死 `connectionTimeZone=UTC`，但**多一道确定性**能防住将来有人误用系统时区（这正是数据层 §4.1 那个缺陷的成因） | `C-10`、`NFR-18`、风险 R6 |
| 3 | **构建必须在工程根目录** | `.mvn/maven.config` 里的 `-Dmaven.repo.local=.m2/repository` 是**相对 CWD** 解析的（交接说明 §2.1）。多阶段构建（Dockerfile）里 `WORKDIR` 必须落到 `simple-shop-backend/` 再跑 `mvn`，否则依赖会下载到别处、甚至构建失败 | 交接说明 §2 第 1/3 项 |
| 4 | **数据库容器的初始化顺序** | 后端启动即连库 + 跑 Flyway。需用 `depends_on` + 健康检查（或启动重试）保证 MySQL 已就绪，否则后端容器一启动就 `Communications link failure` 退出 | 交接说明 §2 第 6 项 |
| 5 | **不引入 servlet 会话（`HttpSession`）** | 本方案用**自定义 token**（`C-07` 的「session + token」由本方案落地为「服务端会话记录 + token 凭证」）。**不要**用 `HttpSession`——它依赖 `JSESSIONID` cookie，与「前端用 `Authorization: Bearer`」的契约不符，且引入 cookie 语义会带来 CSRF 面 | `C-07`、`11.3.2` |

> **关于 `C-07` 措辞的一处澄清**：`C-07` 写的是「**session + token**，30 分钟无操作自动退出」。本方案把它落地为：**服务端的会话记录（`SessionStore`）+ 客户端持有的 token（`Bearer`）**——这正是「session + token」的实质含义，且**不依赖容器提供的 `HttpSession` 机制**（理由见上表第 5 条）。这样容器化时后端是**无状态**的（会话在进程内、不在 cookie 里），单容器下更简单。

### 5.4 复核触发条件（什么时候必须回头改会话方案）

| # | 触发条件 | 必须做什么 |
| --- | --- | --- |
| 1 | 后端改为**多容器 / 多副本 / 负载均衡**（含 K8s 多 Pod、`docker compose --scale`>1） | **必须**改为共享存储：① 引入 Redis（**须同时复核 `C-04`「不使用缓存组件」这一约束**，走变更记录）；或 ② 新增会话表（**须同时复核 `9-O`「会话不纳入表结构」与 `C-18`**）。**并需要粘性会话或彻底共享** |
| 2 | 需要「后端滚动发布/重启时用户不掉线」 | 同上；或接受「发布即全员重新登录」（**当前方案的选择**） |
| 3 | 引入**买家账号体系**或第二个管理员账号 | 会话量与权限模型变化，须重评 §5.2 与 `R12-01` |

> 以上三条**均与 `OPEN-01` 的复核触发条件对齐**（上游 §12.5.3 第 2 条：「部署形态改为容器化多实例 ⇒ 复评 `R12-01`」）。**当前已确认是「容器化 + 单后端容器」，故不触发。**

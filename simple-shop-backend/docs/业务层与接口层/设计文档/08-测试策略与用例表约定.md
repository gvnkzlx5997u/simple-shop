# 8. 测试策略

### 8.1 与既有测试的关系

**保持既有 24 个数据层用例全绿**（`StructureAndUniqueConstraintTest` 12、`InvariantAndConcurrencyTest` 6、`ArchiveAndUtcTest` 6）。它们跑在 `simple_shop_test` 库；本轮新增 `service`/`web` 包的测试**沿用同一基类思路**（`DataLayerTestBase` 的清理逻辑），必要时抽取一个 `ServiceTestBase`。

> **⚠️ 新增测试的清理注意**：测试库的 `simpleshop_trade_history.fk_intention_id` **刻意无物理外键**，删意向不会连带删流水；清理时必须显式删除指向本测试意向的流水（交接说明 §10.4 第 1 条）。本轮测试会产生**大量**流水，务必处理。

### 8.2 测试分层

| 层 | 方式 | 覆盖 |
| --- | --- | --- |
| **Service 集成测试** | `@SpringBootTest` + 真库（`simple_shop_test`）+ `@Transactional`（**并发用例除外**） | 状态机全路径、不变量、字段校验、归档、口令码 |
| **并发测试** | **不能加类级 `@Transactional`**；线程池 + `CountDownLatch`，各线程独立 `TransactionTemplate` | `NFR-01`（10 并发提交序号不重复）、`INV-02`（并发进入交易）、`INV-03`（冻结期提交被拒） |
| **Controller 测试** | `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `TestRestTemplate`，或 `@WebMvcTest` + Mock Service | 16 个接口的**契约**：路径、方法、`snake_case` 字段名、状态码、`code`、鉴权 401、错误码 |
| **契约回归** | 一份 `.http` 或冒烟脚本（§9.5） | 手工/评审时快速核对 16 个接口 |

### 8.3 必测用例清单（按不变量与状态机组织）

**不变量（`INV-01` ~ `INV-08`）**

| 用例 | 断言 |
| --- | --- |
| `INV-01` | 已有在售商品时再发布 → 拒绝（`20001`）；商品表 `status ∈ {on_sale,frozen}` 行数 ≤ 1 |
| `INV-02` | 并发两次「进入交易」→ 恰一次成功，`trading` 意向数 ≤ 1 |
| `INV-03` | 手动冻结期 / 交易冻结期提交意向 → 一律被拒，**不新增意向行**（两种来源都覆盖） |
| `INV-04` | 存在 `trading` 意向时商品必为 `frozen`；交易冻结下「解冻」→ `20005` |
| `INV-05` | 「标记成功」与「手动下架」两条归档路径后，**历史意向表中 `status ∈ {queued,trading}` 记录数 = 0**（`countActive` 断言） |
| `INV-06` | 标记成功后该商品历史意向中 `succeeded` 数 = 1；手动下架后 = 0 |
| `INV-07` | 商品 `on_sale ⇄ frozen` 变化前后，**同一口令码的返回结果不变** |
| `INV-08` | `queued` 意向的口令码必然有效；**重排队前后查询结果不变** |

**状态机（`PS-01` ~ `PS-08`、`IS-01` ~ `IS-07`）**

| 用例 | 断言 |
| --- | --- |
| `PS-01`/`IS-02` | 进入交易后：商品 `frozen`+`freeze_by=trade`、目标意向 `trading`、`trade_start` 非空、**其余 `queued` 不变** |
| `PS-02` | 在售 + **队列非空**也能手动冻结（澄清 Q18 的回归点） |
| `PS-03`/`IS-04`/`IS-05` | 标记成功：其余 `queued` → `failed`+`sold_out`；本次 → `succeeded`；商品 `off_sale` 并归档 |
| `PS-04`/`IS-06`/`IS-07` | 标记失败+作废：商品 `on_sale`、意向 `failed`+`voided`、追加流水；标记失败+重排：商品 `on_sale`、意向回 `queued`、**`queue_order` 变最大**、**`create_at` 不变**、**口令码仍有效** |
| `PS-05`/`PS-06` | 手动冻结 → 解冻成功；交易冻结 → `20005` |
| `PS-08` | 在售 + 队列空 → 下架成功并归档；队列非空 → `20006` |
| `BR-03` 顺序 | 构造「1 条 trading + 2 条 queued」，标记成功后：`off_sale` 时无任何非终态意向 |
| `BR-12` | 对**非队首**意向调用进入交易 → `30002` |
| `IS-03`/`BR-19` | `queued` 撤销成功；`trading` 撤销被拒 |

**校验与错误码**

- 逐字段走查 §3.6 的校验表：不合法输入 → 对应 `code`。
- **XSS**（`NFR-20`）：`<script>alert(1)</script>` 作为 name/description/fail_reason → 被拒（含 `<`/`>`）。
- **`disposal` 非法值** → `30006`；`fail_reason` 超 300 → `30007`。
- **`price`**：`0`、`-1`、`1000000`、`1.999`、`"abc"` → 全部拒绝或明确处理。
- **`tel`**：`123456`（6 位）→ 拒；`1234567` → 通过；`010-12345678` → 通过；`abcdefg` → 拒。

**会话与鉴权**

- 无 token / 错 token / 过期 token → 401 + `10002`。
- 改密后**旧 token 立即失效**（`NFR-04`：双会话对照——A、B 登录，A 改密，B 的下一次请求被拒）。
- 登录失败 100 次后仍可尝试（`NFR-03`）。

**归档与时间**

- 归档后逐列核对：历史商品 `status=off_sale`、`freeze_by=null`、`trade_end`/`result` 必填、`id` 沿用原值；
- 历史意向**无 `queue_order`/`token`**；`id` 沿用原值；时间列继承原值（**不被回调覆盖**）；
- **UTC 写入校验**：写入后**直接查库**，用 `rs.getObject(col, LocalDateTime.class)` 读**字面值**比对（**不要用 `getTimestamp().toLocalDateTime()`**——会再解释一次时区，交接说明 §10.4 第 3 条）。

**口令码**

- 生成结果匹配 `^[A-Z0-9]{12}$`；连续生成 N 个互不相等；库内 `token` 恒为大写。
- 三态：不存在的码 → 错误口令；终态意向的码 → 失效口令（**响应体不含姓名/电话/商品信息，不含「已售出/交易失败/已撤销」字样**）；`queued` → 位次；`trading` → 已进入交易。
- 归一化：输入含首尾空格与小写 → 仍能查到。

**历史接口**

- `I11-15` 按 `trade_end` 倒序、每页 10、无筛选。
- `I11-16` `intentions[]` 按 `create_at` 升序；**`trade_count` 与 `trades[]` 长度一致**；**「N 次失败」的流水逐条可见**（澄清 Q15 / `BR-22` 的关键回归点）；`queue_order`/`token` **不在响应中**。

**JSON 契约（对应 §4.6，逐条断言，别只看「能调通」）**

| # | 断言 | 为什么必测 |
| --- | --- | --- |
| 1 | **所有响应的 JSON 键名是 `snake_case`**（`pic_url`/`freeze_by`/`create_at`/`trade_end`/`queue_count`/`page_size`/`intention_id`…） | 契约违背；前端静默拿不到值（风险 R2） |
| 2 | **`null` 字段的键必须存在**（如 `I11-04` 在 `on_sale` 时 `"freeze_by": null`） | 反例防线：一旦有人加了 `@JsonInclude(NON_NULL)` 就会静默删键（§4.6.1） |
| 3 | **时间格式恰为 `yyyy-MM-ddTHH:mm:ssZ`**（含末尾 `Z`） | `LocalDateTime` 默认**不带 `Z`**，且若误用系统时区会偏 8 小时（§4.6.4） |
| 4 | **`price` 是 JSON 字符串**且恰好两位小数（如 `"1234.00"`），**不是数字** | `11-F`；数字会被 JS 浮点解析 |
| 5 | **枚举下发小写代码**（`on_sale`/`queued`/`sold_out`），**不下发中文 `label`** | `9-Q` |
| 6 | **`I11-04` 在无商品时 `data` 为 `null` 且 `code = 0`**；`I11-10` 同（§4.5-A） | 前端空态分支 |
| 7 | **`I11-10` 的响应中不含 `token`**；**`I11-16` 的响应中不含 `queue_order`/`token`** | `11-D`、`11-I`（**安全项**，用字符串扫描断言） |
| 8 | **`I11-14` 对终态意向返回 `40002`，且响应体不含 `token`** | `NFR-16` |
| 9 | **`message` 为 ASCII**（不含中文） | §4.6.1；若有人照抄示例的中文文案，此断言会失败——是有意的提醒 |
| 10 | **HTTP 状态码**：业务拒绝 = `200`；`10002` = `401`；`20011` = `404`；`50002` = `400` | `11.3.4`、风险 R11 |

**归档 / 流水 / 并发（真库用例，不能只做 Mock 单测）**

| # | 断言 | 对应 |
| --- | --- | --- |
| 11 | **归档的写入顺序**：历史商品**先于**历史意向落库 | §3.3.6 步骤 4。顺序反了会撞 `fkey_intention_history_fk_goods_history_id`（物理外键，`ON DELETE RESTRICT`），**只有真库用例能发现** |
| 12 | **归档前后计数一致**：`goods_history` 行数 +1、`intention_history` 行数 = 归档前当前表意向数 | `NFR-08` |
| 13 | **流水条数**：某意向经历 N 次「标记交易结果」⇒ **恰好 N 条**流水；**手动下架 ⇒ 0 条**流水；`trade_count == trades.length` | `BR-22`、`§9.7.2`、`§9.9.5` |
| 14 | **归档后当前表清空**：`simpleshop_goods` 与 `simpleshop_intentions` 均无该商品及其意向（**硬删除，非软删除**） | `DEC-04` |
| 15 | **加锁顺序无死锁（风险 R3）**：并发执行「标记失败 + 重新排队」与「买家提交意向」，两者**都要成功、不超时** | 交接说明 §5.2。**用例不能加类级 `@Transactional`**，各线程独立 `TransactionTemplate` |
| 16 | **原位 `result`/`trade_end` 从未被写入**：归档后 `GoodsHistory.result` 正确，且**归档路径从未调用 `Goods.setResult`**；当前表 `result` 恒 NULL | `DEC-DB-11`、`9-H`、风险 R8 |
| 17 | **`freeze_by` 的严格校验（Q-1）**：把商品置成 `frozen` + `freezeBy = manual` 后调 `I11-12`/`I11-13` → **被拒（`20004`）**；正常路径（`enterTrade` 产生的 `frozen`+`trade`）→ 成功 | §3.7、§11 Q-1。**必须真库构造**（不能只靠 Mock），因为要验证「`frozen(manual)` + 无 `trading` 意向」这一组合的拒绝行为 |
| 18 | **手动冻结会挡住交易（Q-1 的业务含义）**：在售 + 队列非空 → 手动冻结 → 此时调 `I11-11`（进入交易）**被拒（`20003`，要求 `on_sale`）** → 手动解冻 → 再调 `I11-11` **成功** | §3.7。**这是 Q-1 的端到端回归用例**，覆盖「队列非空也能冻结」+「必须先解冻」两个口径 |
| 19 | **「查看口令码」的日志不含码值（Q-4/Q-9）**：调用 `I11-14` 成功后，审计日志命中 1 条记录，且**日志文本中不出现该 token 的任何子串** | `NFR-12`、`12-H`。**用文本扫描断言**，不是看日志「有没有记录」 |

### 8.4 性能验证（`12-P1`）

| 指标 | 目标 | 条件 |
| --- | --- | --- |
| 查询类响应 | **P95 ≤ 500ms** | 1 件商品 + **1000 条意向** + 100 条历史 |
| 写操作响应 | **P95 ≤ 1s** | 同上 |

> **`I11-10`（意向名单）与 `I11-16`（历史详情）是唯二的性能风险点**：前者分页 10 条会触发 10 次 `countQueuedAhead`；后者逐条查流水会触发 N 次查询。**建议在造数（1000 条）环境下实测**，若不达标再优化（优化方案见 §3.3.3、§3.3.4）。

> **⚠️ S6 补充的两条约定**（沿用过程中发现，写进约定避免重犯）：
> 1. **「前置状态」用<b>词表</b>（`goodsSetup`/`targetKind`）描述，由测试代码去造，而不是把库里的列值直接写进表**。
>    S6 的三张表都有 `goodsSetup ∈ {on_sale, manual, trade, NONE}` 与 `targetKind ∈ {head, second, none, missing}`：
>    这样表里写的是**业务前置条件**（「商品处于交易冻结、目标是队首」），而不是「怎么造出它」。
>    ⚠️ 其中 `trade` 必须**通过真实接口**推进（`I11-11`），不能直接插库——「交易冻结」由 `enterTrade` 产生，
>    且它顺带写入 `goods.trade_start`，而后者是追加流水时 `NOT NULL` 的必填列（见 §8.11 B-8）。
> 2. **「期望值」列不要用 `NULL` 表示「不校验」**：`@CsvFileSource(nullValues = "NULL")` 会把它转成 `null`，
>    于是「期望这一列是 `null`」与「这一列不适用、跳过断言」**无法区分**。S6 的做法是**另设一列**决定是否断言
>    （`goodsSetup = NONE` 或 `targetKind = missing` 时才跳过），而不是让 `NULL` 兼职两种含义。
>    ——与 S5 那条「『未被拒』不要用 `NULL` 表示」是同一类坑，只是换了个位置。

> **⚠️ S5 补充的两条约定**（沿用过程中发现，写进约定避免重犯）：
> 1. **「未被拒」不要用 `NULL` 表示**：`@CsvFileSource(nullValues = "NULL")` 会把该列的 `NULL`
>    也转成 `null`，于是「通过」与「该列没写」无法区分。S5 的用例表统一用 **`OK`** 当「通过」记号。
> 2. **需要引号的三种字段**：含**首尾空格**的、含**列分隔符**的、以及**空串**（空串必须写 `""`，
>    不加引号的空字段是 `null`——这两者含义完全不同，S5 有专门用例区分它们）。

**取值写法**（由 `testing/CsvValues.expand` 展开）

| 写法 | 含义 |
| --- | --- |
| `NULL` | `null`（`@CsvFileSource(nullValues = "NULL")` 直接转换） |
| `""` | 空串（引号空字段，长度 0；**不加引号的空字段是 `null`**，二者必须分清） |
| `{LF}` / `{CR}` / `{TAB}` | 换行 / 回车 / 制表符 |
| `REPEAT(商:50)` / `REPEAT(U+1F600:50)` | 该字符重复 50 次（按**码点**重复） |

**⚠️ 三条踩过的坑（写进约定，避免重犯）**

| # | 坑 | 规则 |
| --- | --- | --- |
| 1 | **`REPEAT` 里不能用逗号**——逗号是 CSV 的列分隔符，`REPEAT(商,50)` 会让**整行向右错位**，报出 `Failed to convert String "50)" to type int` 这种与被测逻辑无关的错误 | 分隔符用**冒号**；且 `CsvValues.expand` 在展开后若仍发现 `REPEAT(` 一律**抛异常**——否则用例会拿字面量去比对、校验器也原样接受，**边界用例在什么都没测的情况下变绿** |
| 2 | **`@CsvSource`（内联）会静默 trim 未加引号的值**（`ignoreLeadingAndTrailingWhitespace` 默认为 `true`），且**不做转义处理** | 凡涉及空格的用例**一律用 `@CsvFileSource`**（文件形式不加引号也不 trim）；确需内联时显式设 `ignoreLeadingAndTrailingWhitespace = false` |
| 3 | **二进制内容不要写进 CSV** | 用记号（如 `file:test.jpg` / `jpeg` / `ffd8`）表示「构造什么内容」，由测试代码 switch 构造；CSV 只管「应当识别成什么」 |

**⚠️ 用例表的自检不可省**：边界信息（`50`、`501`）现在是**数据**，而数据会写错。
`CsvValuesTest` 因此显式断言「`REPEAT(😀:50)` 是 100 个 UTF-16 单元、50 个码点」等事实——
没有它，`GoodsValidatorTest` 里那条边界用例的绿是**没有说服力**的。

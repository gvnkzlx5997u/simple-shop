# 4. 卖家端接口层（Controller）设计

### 4.1 全局约定（严格对齐第 11 章）

| 项 | 约定 |
| --- | --- |
| 协议 / 编码 | HTTP；除图片上传外一律 `application/json; charset=utf-8` |
| **字段命名** | **小写下划线 `snake_case`**（`9-E`）——**实体/Java 侧是驼峰，DTO 用 `@JsonProperty` 显式映射** |
| **枚举取值** | **小写英文代码**（`on_sale`、`queued`…），**不下发中文**（`9-Q`） |
| 时间格式 | **ISO 8601、UTC**，形如 `2026-10-05T12:34:56Z` |
| 金额格式 | **字符串**、两位小数 |
| 分页 | 请求 `page`（**从 1 起**）、`page_size`；响应含 `total`、`page`、`page_size` |
| 空值 | 可选字段无值时返回 `null`，**不省略键** |
| 鉴权 | `Authorization: Bearer <token>`；**`I11-01` 登录除外** |

> **`snake_case` 的实现建议**：**不要**全局配置 `PropertyNamingStrategy.SNAKE_CASE`——它会连带影响实体（若误序列化）并让代码与 JSON 隐式耦合。**推荐在 DTO 字段上显式写 `@JsonProperty("pic_url")`**，一眼能核对契约。

### 4.2 统一响应结构与错误处理

**成功**：
```json
{ "code": 0, "message": "ok", "data": { } }
```
**业务失败**：
```json
{ "code": 20006, "message": "队列非空，无法下架", "data": null }
```

| 字段 | 说明 |
| --- | --- |
| `code` | `0` 成功；非 0 业务错误码 |
| `message` | **服务端调试用**；**前端不得直接展示**（`11.3.3`、`UX-07`）。界面文案由前端按 `code` 映射 `M10-xx` |
| `data` | 业务数据；无数据时 `null` |

**HTTP 状态码使用规则**（`11.3.4`，**注意与常规 REST 直觉相反的地方**）：

| HTTP | 场景 | 携带业务 `code` |
| --- | --- | --- |
| **200** | 请求被正常处理——**业务成功与业务规则拒绝均返回 200** | 是 |
| 400 | 报文本身不合法（JSON 解析失败、必填缺失、参数格式错误） | 是（`50002`） |
| 401 | 未携带 token / token 无效 / 会话超时 | 是（`10002`） |
| 403 | 已认证但无权访问（本项目单账号，实际不会触发，保留语义） | 是 |
| 404 | 路径不存在，或所查资源不存在（如 `20011` 历史商品不存在） | 是 |
| 500 | 服务端内部错误 | 否（通用结构，`50000`） |

> **设计取舍**：业务规则拒绝（「队列非空」「商品非在售」）**用 200 而非 4xx**——它们是**业务语义的正常分支**，用 200 + 业务码让前端统一在 `code` 分支处理，避免与网络异常混淆。
> **实现方式**：`BusinessException` 携带 `(code, httpStatus, message)`；`GlobalExceptionHandler` 据此设置响应状态。**默认 `httpStatus = 200`**，仅 `10002`→401、`20011`→404、`50000`→500、`50002`→400 例外。

> **⚠️ 上述 6 个状态码是「枚举式」的——三处契约未规定的分支，实现时按如下口径收敛（v8 补充两处、v12 补一处）**
>
> | 情形 | 处理 | 理由 |
> | --- | --- | --- |
> | 报文的**媒体类型协商失败**（`Content-Type` 不是 `application/json`，或 `Accept` 无法满足） | **400 + `50002`** | 它**与「JSON 解析失败」是同一类**（报文不可消费），而 §11.3.4 对 400 的定义正含「参数格式错误」，故归入 400 属于**沿用已有定义**而非新造状态码。⚠️ 若不显式处理，它会落到兜底分支变成 **500 + `50000`**，把「客户端写错 `Content-Type`」这个联调期最常见的错误**误报成服务端内部错误**，既误导排查方向，也会污染 500 的监控告警 |
> | **HTTP 方法不支持**（对已存在的路径用了错的动词） | **405**（保留 REST 惯例，**不**改写为 400） | 契约**完全未规定**该场景，且它与上一条**不同类**：媒体类型错误属「报文不可消费」，方法不匹配属**路由**层面。405 更有信息量，且前端不可能偶然触发（每个端点的动词是固定的） |
> | **Controller 方法参数上的约束注解不通过**（`@Min(1) page`、`@RequestParam` 上的 `@NotBlank` 等，**S6 真实端口实测发现**） | **400 + `50002`** | Spring Framework 6.1 起这类校验由**内建的方法校验**执行并抛 `HandlerMethodValidationException`——它**自己就带着 400 的语义**（Spring 默认渲染为 400）。但它**不在**上面任何分支里，于是落到兜底分支被改写成 **500 + `50000`**：实测 `?page=0` 与 `?intention_id=` 都返回过 500。这与上一条媒体类型问题是**同一类缺陷**（客户端写错请求、却报成服务端内部错误），故同样收敛到 400 + `50002`。见 §8.11 D-1 |
>
> 三条都**不是**新增错误码——`50002` 已在 §4.3 表内，未触碰「不得增删编号」的红线。

### 4.4 16 个接口的逐条实现要点

| 编号 | 方法 路径 | 鉴权 | 出参 `data` | 关键实现要点 |
| --- | --- | :---: | --- | --- |
| `I11-01` | `POST /api/seller/session` | ✗ | `{token, expire_at}` | 入参 `account`/`password`；失败一律 `10001`；**不做**限次/验证码 |
| `I11-02` | `DELETE /api/seller/session` | ✓ | `null` | 幂等退出 |
| `I11-03` | `PUT /api/seller/account/password` | ✓ | `null` | 成功后**全部会话立即失效**（含当前 token）→ 前端跳 `P10-05` |
| `I11-04` | `GET /api/seller/product` | ✓ | 商品对象或 `null` | **无当前商品时 `data = null`**（`P10-07` 空态）；**必须下发 `freeze_by`** |
| `I11-05` | `POST /api/seller/product/image` | ✓ | `{pic_url}` | `multipart/form-data`；字段名 **`file`**；**服务端生成文件名，不采用原始文件名** |
| `I11-06` | `POST /api/seller/product` | ✓ | `{id}` | `20001` 冲突、字段校验、**无对应「修改」接口**（`BR-15`） |
| `I11-07` | `POST /api/seller/product/freeze` | ✓ | 更新后商品对象 | **不校验队列为空**（澄清 Q18） |
| `I11-08` | `POST /api/seller/product/unfreeze` | ✓ | 更新后商品对象 | **`20005` 是核心拦截项，服务端必须拒绝，不得依赖前端禁用** |
| `I11-09` | `POST /api/seller/product/offline` | ✓ | `null` | `20006` 在**事务内**校验队列为空；同事务归档 |
| `I11-10` | `GET /api/seller/product/intentions` | ✓ | 分页 + `queue_count` + `items[]` | `items[]` 按 `queue_order` **升序**；**不下发 `token`**；`trading` 的 `rank` 为 `null` |
| `I11-11` | `POST /api/seller/intention/trade` | ✓ | `null` | `30002` 非队首是**服务端防线**；`30003` 状态；`30004` `INV-02` |
| `I11-12` | `POST /api/seller/intention/success` | ✓ | `null` | **整体一个事务**；**顺序不可调换**（`BR-03`） |
| `I11-13` | `POST /api/seller/intention/failure` | ✓ | `null` | `disposal` 枚举校验；**重排队不改 `create_at`、口令码保持有效** |
| `I11-14` | `GET /api/seller/intention/passcode` | ✓ | `{token}` | 入参 `intention_id` **在 query string**；终态 → `40002`；**须记操作日志（不记码值）** |
| `I11-15` | `GET /api/seller/history/products` | ✓ | 分页 + `items[]` | 按 `trade_end` **倒序**、每页 10；**不支持筛选** |
| `I11-16` | `GET /api/seller/history/products/{id}` | ✓ | 详情 + `intentions[]` | `intentions[]` 按 `create_at` **升序**；**不含 `queue_order`/`token`**；**必须返回 `trades[]`**；不存在 → `20011`+404 |

**路径与入参位置的几处易错**

| 接口 | 易错点 |
| --- | --- |
| `I11-01`/`I11-02` | 同一路径 `/api/seller/session`，**`POST` 登录、`DELETE` 退出** |
| `I11-03` | 路径是 `/api/seller/account/password`（**不是** `/seller/password`） |
| `I11-05` | 路径 `/api/seller/product/image`，`multipart` 字段名 **`file`** |
| `I11-07`/`I11-08`/`I11-09` | **POST + 无请求体**（不是 PUT、不是 PATCH），靠「当前商品」定位 |
| `I11-10` | **无路径参数**（单一商品槽位，`BR-11`），分页走 query |
| `I11-11` ~ `I11-13` | 请求体含 `intention_id`（`snake_case`！） |
| `I11-14` | **GET + query 参数 `intention_id`** |
| `I11-16` | **唯一带路径参数 `{id}` 的接口** |

### 4.5 两处需与前端对齐的口径（本方案的建议）

| # | 情形 | 建议 |
| --- | --- | --- |
| **A** | `I11-10`（查名单）在**当前无商品**时返回什么 | 契约未规定。**建议返回 `data = null`**（与 `I11-04` 空态一致：无商品即无名单），`code = 0`。**不使用 `20002`**——`20002` 在契约中只列给 `I11-07`/`I11-11` |
| **B** | `I11-04` 在**无当前商品**时 | 契约明确 `data = null`、`code = 0`（`P10-07` 空态） |

> 两者都**不影响前端逻辑**（前端都走空态分支），但需要一句话写进接口交接说明。列入 §11 待确认 **Q-2**。

### 4.6 DTO 设计（请求 / 响应 / 统一包装）

#### 4.6.1 三条全局口径（先定，避免逐接口重复）

| 项 | 决策 | 依据 / 理由 |
| --- | --- | --- |
| **统一包装** | 所有响应都包在 `ApiResponse<T>` 里：`{code, message, data}` | `11.3.3` |
| **`data` 无值时** | 下发 **`null`**（**不省略键**） | `11.3.1`「可选字段无值时返回 `null`，**不省略键**」 |
| **⚠️ 禁用 `@JsonInclude(NON_NULL)`** | **绝不可**在类级或全局配置 `NON_NULL`/`NON_EMPTY` | 它会把 `null` 字段**整个删掉**，直接违反「不省略键」。这是最容易在无意中（例如从别处抄一份 Jackson 配置）破坏契约的一处 |
| **`message` 的语言** | **`message` 必须是 ASCII 英文**（如 `"passcode expired"`、`"queue not empty"`），**不得下发中文** | `11.3.3` 明确 `message` 「**仅供日志与排查**，**前端不得直接展示**」，界面文案由前端按 `code` 映射 `M10-xx`。若下发中文，在 `snake_case`/UTF-8 协商出问题时反而变成前端乱码来源，**收益为零、风险非零** |

> **关于 `message` 的额外说明**：第 11 章 §11.3.3 的示例写成 `"队列非空，无法下架"`（中文）。本方案**有意偏离示例、改用英文**，理由是契约正文对 `message` 的定位是「**服务端调试用**」且「**前端不得直接展示**」——既然是给开发/运维看的日志字段，英文比中文更符合它在日志检索、grep、告警规则里的实际用途，也避免与「前端必须按 code 映射文案」这条硬规则产生「那我能不能直接显示 message」的歧义。**若你希望严格照抄示例的中文，改 `ErrorCode` 的字面量即可，不影响其它设计**（列入 §11 **Q-13**）。

#### 4.6.2 响应 DTO 清单（逐接口）

> 字段名一律 `snake_case`，通过 `@JsonProperty` **显式声明**（不依赖全局命名策略，见 §4.1）。

**`ApiResponse<T>`**（统一包装）

```java
public class ApiResponse<T> {
    @JsonProperty("code")    private int code;        // 0 = 成功
    @JsonProperty("message") private String message;  // ASCII 英文，仅供调试
    @JsonProperty("data")    private T data;          // 无数据时为 null，但键必须存在
}
```

**`PageData<T>`**（分页响应内层，供 `I11-10`/`I11-15` 复用）

```java
public class PageData<T> {
    @JsonProperty("total")     private long total;
    @JsonProperty("page")      private int page;       // 从 1 起
    @JsonProperty("page_size") private int pageSize;
    @JsonProperty("items")     private List<T> items;
}
```

| 接口 | `data` 类型 | 字段（逐条按第 11 章） |
| --- | --- | --- |
| `I11-01` | `LoginData` | `token`(string)、`expire_at`(string, ISO 8601 UTC) |
| `I11-02` | `null` | — |
| `I11-03` | `null` | — |
| `I11-04` | `GoodsData` **或 `null`** | `id`、`name`、`description`、`pic_url`(**可 null**)、`price`(string)、`status`、`freeze_by`(**`on_sale` 时为 null**)、`create_at`、`trade_start`(**可 null**，仅内部用) |
| `I11-05` | `ImageData` | `pic_url`(string) |
| `I11-06` | `PublishResultData` | `id`(string) |
| `I11-07`/`I11-08` | `GoodsData` | 同 `I11-04` |
| `I11-09` | `null` | — |
| `I11-10` | `IntentionPageData` 或 `null`（见 §4.5-A） | 继承 `PageData` 的 4 字段 + **额外 `queue_count`**(int)；`items[]` = `IntentionItemData` |
| `I11-11`/`I11-12`/`I11-13` | `null` | — |
| `I11-14` | `PasscodeData` | `token`(string，**原文，仅非终态**) |
| `I11-15` | `HistoryPageData` | `PageData<HistoryGoodsItemData>` |

> **⚠️ 硬规则：DTO 注解只判「有没有」，不判「对不对」（v8 修正）**
>
> 这条规则是 S3 实现时发现的：**方案原稿的写法会产出与契约不符的实际结果**（不是风格问题）。
>
> | 位置 | 负责判什么 | 违规时返回 |
> | --- | --- | --- |
> | DTO 上的 `jakarta.validation` 注解 | **字段在不在、是不是空白、类型能不能转换** | `50002`（HTTP **400**）——§11.3.4 对 400 的定义正是「报文本身不合法（JSON 解析失败、必填缺失、参数格式错误）」 |
> | Service 内的独立校验 | **取值对不对**（长度上下限、字符规则、区间、枚举取值） | 该字段**专属的业务码**，HTTP **200**（业务拒绝属正常分支） |
>
> **为什么必须这样分**：§11.6.1 为一批「取值规则」专门分配了业务错误码，且它们的 HTTP 状态是 **200**。若在 DTO 上再写一遍同名注解，请求会在**进入 Controller 之前**就被 Bean Validation 拦下，经 `GlobalExceptionHandler` 变成 `50002` + **HTTP 400**，后果是：
> ① 契约指定的业务码在 HTTP 路径上**永不可达**（成为死码）；② 前端按 `code` 映射文案（`UX-07`、`NFR-09`）时拿到的是通用的「参数错误」，而**不是**该字段的专属提示——**界面文案直接错了**。
>
> 同时这也**不会**造成「漏校验」：Service 侧本来就必须独立校验（§3.6 的 `G6-02`，且买家端 JSP 下一轮直接调 Service、不过 DTO 校验链）。两处都写才是重复的双源；**只有 Service 一处**才是唯一正确的落点。
>
> **逐字段对照（`account`/`new_password` 已随 S3 实现；`name`/`description`/`price`/`pic_url` 已随 S4 实现；`fail_reason`/`disposal` 已随 S6 实现）**
>
> | 字段 | §4.3 里有专属码？ | DTO 注解（修正后） |
> | --- | --- | --- |
> | `account`（登录） | 无 | `@NotBlank` + `@Size(max = 50)`（可保留） |
> | `password`（登录） | 无 | **仅** `@NotBlank`（§3.6：登录侧不设长度限制） |
> | `new_password` | **`10004`** | **仅** `@NotBlank`（**删掉 `@Size(min = 8)`**） |
> | `name`（发布商品） | **`20007`** | **仅** `@NotBlank`（**删掉 `@Size(max = 50)`**） |
> | `description` | **`20008`** | **不加注解**（可选字段） |
> | `fail_reason` | **`30007`** | **不加注解**（可选字段） |
> | `price` | **`20010`** | **仅** `@NotBlank`（区间/两位小数由 Service 判） |
> | `disposal` | **`30006`** | 不加（按 `String` 收，Q-14） |
> | `page`／`page_size` | 无 | `@Min(1)`；`@Min(1) @Max(100)`（**保留**） |
>
> **一句话判据**：**先查 §4.3 错误码表里该字段有没有专属码**——有，注解就只留 `@NotBlank`；没有，注解可以照写长度/区间。


> **`disposal` 的接法与错误码映射**：契约的 `30006`（`disposal` 取值非法，HTTP 200）与 `50002`（参数格式错误，HTTP 400）**语义不同**。
> **✅ 已定（Q-14）**：`disposal` **按 `String` 接收**，在 **Service 里显式判定**并抛 `30006`。
> **不要**声明成 Java 枚举——那样非法值会在 Jackson 反序列化阶段就抛 `HttpMessageNotReadableException`，必须在 `GlobalExceptionHandler` 里靠解析异常消息去关联字段名，**脆弱且错误码归属不准**。
> 实现：`String disposal` → `if (!"voided".equals(d) && !"requeued".equals(d)) throw new BusinessException(ErrorCode.INVALID_DISPOSAL);`（`30006`，HTTP 200）；随后转成内部枚举（或直接用字符串常量）供裁决分支。
> **请求 DTO 与实体字段名不同**：请求侧是 `intention_id`（`snake_case`），Java 是 `intentionId`；`PublishGoodsRequest` 的 `pic_url` ↔ `picUrl`。**逐个 `@JsonProperty`**。

#### 4.6.4 DTO ↔ 实体 的边界规则

| 规则 | 说明 |
| --- | --- |
| **实体绝不出 Service 边界** | `open-in-view: false`（§2.2），实体带出事务会触发 `LazyInitializationException`（风险 R9） |
| **映射手写，不用框架** | 16 个接口的映射量小；手写静态工厂（如 `GoodsData.from(Goods)`）更可控、更好审（§2.1 不引入 MapStruct） |
| **映射必须显式列字段** | **不要**用 `BeanUtils.copyProperties` 或反射式拷贝——它会**静默**把实体新增字段带进响应，而契约要求「接口层不得引入第 9、11 章未登记的持久化字段」（`11.1`）。显式赋值 = 编译期保证契约字段集合 |
| **枚举 → `String` 的转换点** | 统一在 `GoodsData`/`IntentionItemData` 等 DTO 的静态工厂里做 `status.name()`（枚举常量名**即**库中代码，`9-Q`）；**不配** `WRITE_ENUMS_USING_TO_STRING`（`toString` 不是代码） |
| **时间 → `String` 的转换点** | `LocalDateTime`(UTC) → ISO 8601 带 `Z`。**DTO 字段直接用 `String`**，在静态工厂里 `dt.atOffset(ZoneOffset.UTC).format(DateTimeFormatter.ISO_OFFSET_DATE_TIME)` 转换（见下方「`LocalDateTime` + `Z` 的坑」） |
| **`price` 的转换点** | `BigDecimal` → `toPlainString()`。DTO 字段类型用 `String`，在静态工厂里转换（**不是** Jackson 的 `WRITE_BIGDECIMAL_AS_PLAIN`——那是全局开关，会影响将来可能出现的其它 `BigDecimal`） |

> **`LocalDateTime` + `Z` 的坑**：`LocalDateTime` **本身没有时区**，Jackson 默认会序列化成 `2026-10-05T12:34:56`（**没有 `Z`**），而契约要求 `2026-10-05T12:34:56Z`。
> **✅ 已定：DTO 时间字段一律用 `String`**，在静态工厂里显式转：
> ```java
> private static String iso(LocalDateTime utc) {
>     return utc == null ? null : utc.atOffset(ZoneOffset.UTC).format(DateTimeFormatter.ISO_OFFSET_DATE_TIME);
>     // → "2026-10-05T12:34:56Z"
> }
> ```
> **为什么选这个而不是「`LocalDateTime` + 自定义 `Serializer`」**：格式**完全受控**、不依赖任何全局 Jackson 配置；**不需要**去关掉 `WRITE_DATES_AS_TIMESTAMPS` 之类的开关；也不会因为将来有人改了全局配置而静默变格式。
> **⚠️ 绝对禁止**在转换里出现 `ZoneId.systemDefault()` / `ZoneOffset.systemDefault()`——开发机是 `Asia/Shanghai`，会**静默偏 8 小时**，正是数据层 §4.1 那个缺陷的同类（而且 `validate` 查不出来）。
> **本项已把 §8.3 的「时间格式断言（含末尾 `Z`）」列为必测项。**

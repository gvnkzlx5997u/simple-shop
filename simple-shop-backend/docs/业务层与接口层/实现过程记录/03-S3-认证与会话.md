**B. 关键实现决策（评审会问的地方）**

1. **`changePassword` 的入参由 `(token, ...)` 改为 `(account, ...)`**（**对 §3.3.1 签名的修正**）。
   认证的**唯一**入口是拦截器（§5.2：校验 token 后把账号放进请求属性）。若 Service 再拿 token 去 `SessionStore` 解析一遍，就出现了**第二处鉴权逻辑**——两处将来可能不一致。改为收「已认证的账号」后：鉴权只有一处实现，Service 也**与传输层解耦**。契约口径**不变**（`I11-03` 仍需 Bearer token，否则在拦截器就被 `10002` 拒掉——已用真实端口验证）。
2. **`logout` 必须自己解析 token，且绝不抛 401**。它与 `I11-01` 共用路径，而 `excludePathPatterns` 只能按**路径**排除 ⇒ 退出登录拿不到「已认证账号」。因此 `SellerSessionController#logout` 直接调 `SellerAuthInterceptor.extractToken(request)`（同包可见），**不能**用 `requireAccount`。token 缺失时传 `null`，`SessionStore.remove` 是无操作 → 仍返回 `code 0`。已用真实端口验证「不带 token / 无效 token / 错 scheme 一律 200 + `code 0`」。
3. **`10001` 的「不区分」做成【结构性】保证，而不是纪律要求**（`SellerAuthService.login`）：
   ```java
   String passwordHash = user.map(ShopUser::getPassword).orElse(null);
   if (!PasswordHasher.matches(password, passwordHash)) { throw ... LOGIN_FAILED; }
   ```
   账号查不到时 `passwordHash` 为 `null`，而 `matches(x, null)` 恒为 `false` ⇒ **两条路径汇合到同一个 `if` 分支**。不存在「某天有人给『账号不存在』加了个专属错误码」这种可能。用例 `unknownAccountIsIndistinguishableFromWrongPassword` **逐字节比对**两个响应体来钉住它。
4. **改密的会话清空放在事务提交【之前】**——**有意的不对称选择**。两种失败模式不对等：提交失败 ⇒「会话清了、密码没改成」⇒ **过度失效，可恢复**（重新登录即可）；改成「提交后再清」⇒ 一旦该步出问题 ⇒「密码已改、旧会话仍有效」⇒ **失效不足，是安全缺陷**。选可恢复的那一种。这也是契约要求「≤5s 失效」而实际为 **0** 的原因（同步、同线程，无补偿窗口）。
5. **`UtcIso8601` 无条件截断到秒**——这不是洁癖，是**必需**：库列是 `datetime`（无小数秒），而 `DatabaseTimeProvider.utcNow()` 内部是 `LocalDateTime.now(ZoneOffset.UTC)`（**带纳秒**）。同一 DTO 字段两种来源都会走到（「刚 persist 未重读」vs「从库重读」），**不截断就必然在某条路径上输出 `...T12:34:56.123456Z`**，违反 §8.3 断言 #3。用例 `truncatesSubSecondPrecisionSoDbAndMemoryAgree` 直接对照这两种来源。
6. **`login` 用 `readOnly` 事务，`logout` 不加事务注解**。`logout` **不访问数据库**（会话在进程内），加注解会让人误以为有 DB 写入。§3.1「事务边界在 Service 方法上」针对的是**涉及 DB 的**动作。
7. **`changePassword` 不显式 `save()`**，依赖事务内托管实体的脏检查（提交时发 `UPDATE` 并触发 `ShopUser.@PreUpdate` 刷新 `update_at`）。⚠️ 这**依赖 `@Transactional` 存在**：若注解被去掉，`findByAccount` 会各自开事务返回**游离态**实体，`setPassword` 将**静默丢失**。用例 `changePasswordUpdatesHash`（改密后用**新**口令必须能登录）是这条的护栏——**Mock 掉仓储的写法永远发现不了它**。

**D. S3 期间发现并处理的四件事**

1. **⚠️ DTO 注解会「吃掉」专属业务码（已回写 §4.6.3，并影响 S4/S6）**
   §4.6.3 原稿给 `new_password` 写了 `@Size(min = 8)`，与契约**冲突**：请求会在**进入 Controller 之前**被 Bean Validation 拦下 → `50002` + **HTTP 400**，于是契约指定的 **`10004`（HTTP 200）在 HTTP 路径上永远不可达**（成为死码），前端按 `code` 映射的「新密码至少 8 位」就地提示**永远不会出现**。
   **同一类问题在后续步骤还有三处**：`goods.name` 的 `@Size(max=50)` 与 `20007`、`description` 的 `@Size(max=500)` 与 `20008`、`fail_reason` 的 `@Size(max=300)` 与 `30007`。
   **已提炼为一条硬规则并逐字段列表**（§4.6.3）：**DTO 注解只判「有没有」，Service 判「对不对」**；判据是「§4.3 错误码表里该字段有没有专属码」。用例 `changePasswordWithShortNewPasswordReturns10004OverHttp200` 是这条的**回归护栏**（它会在有人"顺手"加回 `@Size` 时立刻失败）。
2. **媒体类型协商失败原本会变成 500**（已回写 §4.2）
   登录是本轮第一个接收 JSON 体的端点，于是这条路径第一次变得可达：`Content-Type: text/plain` 会让 Spring 在进 Controller 前抛 `HttpMediaTypeNotSupportedException`，原先落到兜底分支 → **`500` + `50000`**，把「客户端写错 `Content-Type`」（联调期最常见的错误）**误报成「服务端内部错误」**，既误导排查方向也污染 500 告警。已新增分支 → **`400` + `50002`**（§11.3.4 对 400 的定义本就含「参数格式错误」，属**沿用已有定义**，未新增错误码）。用例 `loginWithWrongContentTypeIsParamInvalidNotInternalError` 覆盖。
3. **⚠️ 报文解析失败的日志会**回显请求体**——口令明文可能因此进日志**（本次新发现的安全问题）
   实测日志原文：
   ```
   request body unreadable: path=/api/seller/session cause=Unrecognized field "rememberMe"
   (class com.simpleshop.web.dto.LoginRequest), not marked as ignorable (2 known properties: "password", "account")
   ```
   Jackson 的解析异常消息是**从请求体原文生成的**。实测 `{"password":Abcd@1234}`（值少了引号）会得到 `Unrecognized token 'Abcd': was expecting (...)` ⇒ **客户端只要把报文写坏，口令明文就会落进服务端日志**，而审计日志留存 **3 个月**（`C-18`、`12-P7`）。这直接违反本项目反复申明的硬规则（`12-H`、`NFR-12`、Q-4/Q-9）。
   解析失败发生在「字段语义尚未建立」的阶段，**无法按字段选择性脱敏**，因此改为只记：**异常类别 + 行列号 + 未知字段名**（字段名是**元数据**、不是用户数据）。
   修复后实测：`cause=JsonParseException(line=1, column=32)`、`cause=UnrecognizedPropertyException(property=rememberMe)`——**既不回显请求体，又保留了排查所需的线索**。两条用例分别钉住「不回显」与「不丢线索」。
4. **`WebMvcConfig.LOGIN_PATH` → `SESSION_PATH`**（命名修正）
   该路径同时承载 `I11-01`（`POST`）与 `I11-02`（`DELETE`），旧名会误导。同时把 Controller 的 `@RequestMapping` 改为**直接引用该常量**——这是有意的：若两边各写字面量，一旦有人只改一处致使登录路径落入拦截器覆盖范围，就会形成**「登录需要会话、会话需要登录」的死锁**，而共享常量让这种错误在编译期不可能。

**E. 已登记的已知限制（须让评审看到，不是遗漏）**

| # | 限制 | 处置与理由 |
| --- | --- | --- |
| 1 | **BCrypt 只使用口令的前 72 字节**，超出部分被忽略 | **不**据此拒绝超长口令：§3.6 只规定「≥ 8 位」这一个下限，§11.6.1 **没有**「过长」对应的错误码，擅自新增会违反 §4.3「不得增删编号」。实际影响可忽略（单账号、口令由本人设定，不存在「两个口令前 72 字节相同」的现实场景）。已写进 `SellerAuthService` 类注释 |
| 2 | 账号不存在时会**跳过 BCrypt**（响应比口令错误快），理论上构成时序侧信道 | **不处理**：`DEC-25` 本就禁止失败次数限制，且账号名 `seller` 是**公开且固定**的（初始化脚本、README 都写着），枚举本身没有意义。加一次「哑哈希」只会白耗 CPU 而收益为零 |
| 3 | `NFR-03` 的用例真的打满 **100 次**失败登录，每次约一次 BCrypt | 有意为之：契约的可测指标就是「100 次」，任何「第 N 次锁定」的实现都会在它上面露出。代价约 **10 秒**构建时间；若将来构建时延成为问题，可下调次数——但**这属于削弱已指定的验收指标**，需显式决策，故此处保持并登记 |

## B. 关键实现决策

1. **买家端用**`BuyerPrompt`**承载文案，而不是沿用卖家端的 `ErrorCode`**。
   §11.6.2 的标题原文是「买家端业务结果对照（**服务端内部约定，非契约**）」——买家端服务端渲染，
   **不用 HTTP 业务码**，服务端**直接选文案**。故：
   - 不并入 `ErrorCode`（那是卖家 REST 的契约表，§4.3 明确「不得增删编号」）；
   - **文案直接是中文**，而不是像卖家端那样只给 ASCII 英文。这**不**违反已定 Q-13——
     Q-13 管的是**卖家 REST 响应里的 `message` 字段**（给日志看、前端不许展示）；
     买家端是服务端渲染，文案本来就由服务端产生。两处「谁负责渲染」不同，故语言不同。

2. **常量用含义命名（`GOODS_FROZEN`），不叫 `B11_01`**。
   上游第 11 章里 `B11-01`~`B11-07` **同时**是**页面端点编号**（§11.x：`B11-01` = 当前商品页 `GET /`）
   与**结果编号**（§11.6.2：`B11-01` = 冻结期提交被拒）。若常量叫 `B11_01`，
   代码里就再也分不清它指哪一个。上游编号仅作为**注释**记在常量上（S6 起不再有 `upstream()` 访问器，见 §8.11 D-4）。
   （该编号撞车已补入附录 D。）

3. **失败用「密封返回值」而不是异常**（与卖家端相反）。
   卖家端有 `GlobalExceptionHandler` 把 `BusinessException` 统一翻译成 HTTP，故用异常是对的；
   买家端**没有**那一层。用返回值可让下一轮 JSP 用 **Java 21 穷尽 `switch`** 处理，
   **漏写一个分支就编译不过**——比「记得 catch」可靠。这与方案对 `PasscodeQueryResult` 的取向一致。
   > **⚠️ 由此产生一条必须遵守的规则**：返回 `Rejected` 是**正常返回**，`@Transactional` **会提交、不会回滚**。
   > 故三个写方法都严格分成「判定段 → 写阶段」，**所有拒绝分支都在写之前**。已写进 `BuyerResult` 与
   > `BuyerIntentionService` 的类注释，并在方法里标出「写阶段起点」。

4. **`BR-29` 做成类型级：`Expired`／`NotFound` 是【零字段】记录**。
   方案要求它们「只带一个提示类型字段」；本实现连那个字段也省了，改由 `prompt()` 从**类型本身**推导。
   想要「顺手带出失败原因」**没有地方放**。`PasscodeQueryResultTest` 直接检查 record 的组件清单——
   谁加一个 `status` 字段，用例立刻失败。

5. **`isWellFormed` 内部先归一化**（与 §3.3.7 那行 `^[A-Z0-9]{12}$` 的字面写法略有出入）。
   §3.6 对该字段的原文是「`^[A-Z0-9]{12}$`（**归一化后校验**）」。把归一化并进来后，
   调用方可以直接喂用户原样输入；否则**忘了归一化**会把 `" abc123def456 "` 判成「格式不符」，
   而查库时它又能命中——同一个输入在两处得到相反结论。

6. **限流落在 Service 且 `submitIntention` 增加 `clientKey` 参数**。
   上游 `12-P6` 写「接口层拦截实现」，而用户已定 Q-8：**本轮在 Service 层实现最小版本**（以 Q-8 为准）。
   但 `submitIntention(name, tel)` **没有客户端标识**，限流无从算起——这是方案的一处遗漏，故补参。
   参数名取 `clientKey`（而非 `ipAddress`）：Service 不该知道 HTTP，调用方传「客户端的限流身份」。

7. **`browseCurrentGoods` 不过滤冻结商品，且无商品返回 `null`**。
   冻结商品**照样返回**——页面要展示卡片 + 「已冻结」标签 + `M10-01`，
   并据此禁用提交入口。若这里过滤掉，买家会看到「暂无在售商品」（`M10-02`），
   与「商品交易中，暂停接收新意向」的含义完全不同。

8. **`Active` 用紧凑构造器把「`trading` ⇔ 无位次」变成构造期断言**。
   否则可构造出 `Active(3, true)` 这种「既在交易中又排第 3 位」的自相矛盾对象，
   渲染出「您已进入交易（当前排第 3 位）」，直接违反 `AC-11`。

## D. S5 期间发现并处理的问题

1. **⚠️ 缺陷：`SubmitRateLimiter` 的多构造器使 Spring 上下文起不来**（测试当场拦下）。
   本类有一个生产构造器 `(AppProperties)` 和一个私有构造器 `(int, Clock)`（供测试拨钟）。
   Spring 遇到**多个**构造器且无 `@Autowired` 时，会去找**无参**构造器，找不到就
   `No default constructor found` → **整个应用启动失败**。
   表现是 50 条集成用例**全部**以「ApplicationContext 加载失败」报错——一眼就能看出不是业务逻辑问题。
   **修复**：在公开构造器上显式 `@Autowired`（`PasscodeService` 因为同样的原因也已加）。
   > 这条值得记下来：**「加一个测试用的重载构造器」是一个会破坏生产启动的动作**，
   > 而它看起来完全无害。加上 `@Autowired` 后两处都有注释说明为什么必须写。

2. **⚠️ 有意偏离方案：不做 `DataIntegrityViolationException` 的同事务重试**。
   §3.3.7 要求「并捕获 `DataIntegrityViolationException` 做一次重试」。**未实现**，理由是一条硬约束：
   唯一约束冲突一旦抛出，当前事务已被标记 **rollback-only**，同一事务里换个码再插只会在提交时得到
   `UnexpectedRollbackException`。要真重试必须把插入放进 `REQUIRES_NEW` 独立事务，
   那又引入「外层序号已消耗、内层回滚」的补偿问题。
   **代价评估**：撞码概率约 `1/36¹²` ≈ `2×10⁻¹⁹`；且**数据一致性并不依赖这个重试**——
   `uk_intention_token` 会挡住重复，调用方得到一个明确失败（**失败安全**，不是静默错误）。
   已写进 `PasscodeService#generateUnique` 的类注释。

3. **把「不可达」的两条分支变成可验证的**。
   撞码重试与「5 次都撞」的耗尽分支在真实随机下永远跑不到，等于**不可验证的死代码**。
   为此给 `PasscodeService` 加了一个包内可见的重载以注入随机源，
   测试用一个「固定输出同一码」的 `SecureRandom` 子类走通两条分支。
   > 期间写错过一次：`nextInt` 每个码要调 **12** 次（每位一次），
   > 我最初只让「第一次调用」返回固定值，得到的首个码是 `ABBBBBBBBBBB`——**与库里的码不同，
   > 重试分支根本不会触发，用例会「绿着什么都没测」**。已改为「前 12 次固定」。

4. **口径拆分：冻结 与 无商品/非在售 是两件事**。
   §3.3.5 原稿把两者写在一行：「空 或 `goods.status != on_sale` → `B11-01` / `M10-13`」。
   但 §11.6.2 的 `B11-01` 条件明确是「**商品处于交易冻结**」，文案 `M10-01`；
   而 `M10-13`（「商品状态已变化，无法提交」）是另一回事。本实现**按条件拆成两条提示码**：
   冻结（手动／交易任一）→ `GOODS_FROZEN`/`M10-01`（`AC-17` 明确要求两种来源都给 `B11-01`）；
   无商品或非在售 → `GOODS_UNAVAILABLE`/`M10-13`。
   **不擅自给 `M10-13` 编一个 `B11-11`**——编号只由上游分配（注释里记为 `—`）。

5. **`createAt` 的「显式赋值」是不可观测的（诚实登记）**。
   §3.4 末要求业务时间由 Service 显式写。但 `@PrePersist` 的兜底会给出**完全相同**的入库结果，
   因此**无法用黑盒断言区分**「显式写了」与「靠回调写了」。故该用例只断言
   「`create_at` 已写、且属于合理时刻」，并在用例注释里**说明这是代码评审项**。
   （不写一条假装能验证它的用例。）

## E. 已登记的已知限制

| # | 限制 | 处置与理由 |
| --- | --- | --- |
| 1 | 限流是**固定窗口**，相邻窗口交接处可短时翻倍 | Q-8 明确要**最小版本**；限流是缓解措施而非正确性约束（`R12-10` 已登记「仅基础限流」为已接受风险，兜底是队列上限）。**已有一条用例固化该行为**，将来改滑动窗口时它会失败以提醒同步更新注释 |
| 2 | 限流计数器在**进程内**，多副本下阈值会变成 `10 × 副本数` | 与 `SessionStore` 同一前提（方案 §5）：后端单容器。改多副本时**必须**改共享存储并复核 `C-04`（§5.4） |
| 3 | **格式不符（`B11-09`／`M10-28`）本轮不由 Service 产出** | §3.3.5 明确「由调用方先调 `isWellFormed`，不进入查询方法」。故格式不符的输入在本轮**退化为 `B11-04`（错误口令）**——安全的降级（不泄漏信息），但文案是 `M10-05` 而非 `M10-28`。**⚠️ 下一轮 JSP 必须先判格式**，已列为遗留待办 |
| 4 | `M10-01` 的措辞是「商品**交易中**…」，但 `AC-17` 要求**手动冻结**时也用它 | `AC-17` 是逐字规定的（两种冻结来源都返回 `B11-01` + `M10-01`），实现不自行改文案。已登记为**口径观察项**，供业务方决定是否补一条手动冻结的文案 |
| 5 | `tel` 的 `^[0-9-]{7,20}$` 允许 `"-------"`（7 个连字符）通过 | 契约给的就是这个字符集与长度区间；多判一条（如「必须含数字」）就是发明约束。已写成用例 `正常-纯连字符7位契约字面允许` 明示该行为 |

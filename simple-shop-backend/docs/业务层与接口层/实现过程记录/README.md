## 为什么要单独留这部分

设计文档回答「**应该**怎么做」，但实施过程中一定会出现三类东西，它们**不属于设计**：

| 类型 | 例子（都真实发生过） | 若不记下来的后果 |
| --- | --- | --- |
| **设计被推翻** | `changePassword` 的入参由 `(token,…)` 改为 `(account,…)`；`markTrade*` 收紧为要求 `freezeBy == trade` | 后来的人照着旧设计改回去 |
| **只有真机才暴露的缺陷** | 超限上传的 `20009` 因 Tomcat `max-swallow-size` 默认 2MB 而**根本送不到客户端**；MockMvc **结构上测不到** | 删掉那条「看起来没用」的配置，缺陷静默复发 |
| **有意接受、但必须让评审看到的限制** | BCrypt 只用口令前 72 字节；并发发布竞态（`DEC-DB-06`）；超过 10MB 的上传仍会断连 | 评审时被当成「没察觉到」，或后来的人误以为可以实现 | 

**每条记录里的「D. 期间发现并处理的问题」与「E. 已登记的已知限制」就是为这三类内容准备的。**

## 记录的统一结构

九篇都用同一套小节，便于横向查找：

| 小节 | 内容 |
| --- | --- |
| **A. 交付物** | 新增/修改的每个文件及其职责与关键口径（能看出「这个类为什么存在」） |
| **B. 关键实现决策** | 设计之外或与设计不同的选择，**每条都写清理由**（评审会问的地方） |
| **C. 验证证据** | `mvn clean verify` 结果、真实端口实测明细、静态检查结果——**都是实跑出来的数字** |
| **D. 期间发现并处理的问题** | 缺陷、口径冲突、做错又改回来的地方（含「原方案会产出错误结果」的修正） |
| **E. 已登记的已知限制** | **有意不解决**的问题与理由；供评审与风险清单移交 |

>

> ③ 「`createAt` 由 Service 显式写」**无法用黑盒断言区分**（已诚实登记为代码评审项，见 §8.10 D-5）；

> 它**没有**被伪造一条用例去覆盖（见 §8.11 B-7／O-4），因为那会制造假证据。
